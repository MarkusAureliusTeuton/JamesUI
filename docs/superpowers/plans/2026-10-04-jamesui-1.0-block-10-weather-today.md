# JamesUI 1.0 – Block 10 Weather Today + Forecast Overlay Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `widget.weather-today` as the first visible JamesUI 1.0 hero, with truthful Block-9 weather data, retained Alpine imagery and a live Hourly/Daily modal forecast, while keeping Core weather-neutral and r11 in production.

**Architecture:** One widget consumes the six existing weather capabilities and owns stable hero/forecast DOM. A narrow additive Block-9 metadata change exposes the validated HA timezone needed for UI formatting. Core shell gains only generic same-document DOM overlay hosting, while the shared overlay primitive gains generic stacking above sticky navigation.

**Tech Stack:** Vanilla ES modules, existing JamesUI Module/Capability/Overlay APIs, Block-6 design tokens/primitives, Block-7 semantic icons, Node `node:test`, Python architecture gates, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-04-jamesui-1.0-block-10-weather-today-design.md`

## Global Constraints

- Primary visual target is OnePlus Pad 2 portrait; Fully is kiosk shell only.
- `widget.weather-today` consumes capabilities only; it never accesses raw `hass` or imports the Home Assistant Adapter.
- Widget context remains exactly `events`, `overlays`, `capabilities`, `actions`, `module`.
- V1 widget config is strict and empty; unknown keys are rejected.
- Required capabilities are exactly `weather.current`, `weather.daily`, `weather.hourly`, `weather.sun`, `weather.moon`, `weather.atmosphere`.
- Missing data remains explicit; never turn missing/unavailable values into plausible weather values or `0`.
- Weather/Sun/Forecast time formatting uses only capability-provided validated Home Assistant timezone metadata; browser timezone is intentional only for the large device clock/date.
- Alpine imagery is restricted to the eight retained local WebPs listed in the spec; no remote/dynamic assets, data URI or legacy `assets/weather/*.svg` use.
- Weather and moon graphics use the existing semantic icon registry only.
- Overlay Core changes are generic and contain no weather vocabulary, widget-ID branch or forecast behavior.
- Overlay uses structural `z-index: 100` in the shared design primitive so it remains above persistent sticky navigation; no new design token is introduced for this structural layer.
- No final Start composition, Block-11+ modules, settings UI, production bootstrap change or cutover in Block 10.
- r11 remains the running production/reference runtime.
- No monkey-patches, Prototype overrides, version-polish layers, duplicate runtime paths or permanent compatibility shims.

## Review Focus

1. **Partial-data truthfulness:** Current unavailable while Daily/Hourly remains available must keep high/low/forecast usable without inventing current values. Pin in Tasks 3 and 5.
2. **Timezone split:** Device clock may use browser/device local time, but Sun/precipitation/Hourly/Daily labels must never silently fall back to browser timezone. Pin in Tasks 1, 3 and 4.
3. **Overlay replacement race:** A stale close callback from this widget must never close a newer unrelated overlay. Pin in Tasks 2 and 5.
4. **Unknown provider/scene values:** Unknown weather condition or atmosphere scene must produce neutral copy/fallback, never guessed icon/image. Pin in Task 3.
5. **Long-running kiosk cleanup/drift:** Exactly one minute-aligned timeout and six active capability subscriptions must remain after repeated updates; destroy must clear all widget-owned resources. Pin in Task 5.
