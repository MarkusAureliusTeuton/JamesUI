# JamesUI 1.0 Block 5 – Versioned Configuration Store and Migrations Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace JamesUI's flat `config_entry.options` persistence with one structured, versioned, transactional configuration store while keeping the running r11 panel compatible until controlled cutover.

**Architecture:** Persist the canonical shared configuration in Home Assistant `.storage` through `homeassistant.helpers.storage.Store` with atomic writes. Keep schema validation, migration logic and transactional service behavior in small testable units; the Home Assistant-specific store wrapper is thin. Existing r11 WebSocket commands become a temporary projection/patch compatibility layer over the same canonical store, with an explicit removal point at Block 20/21. The new frontend Core receives a read-only Config Service that talks only through the Home Assistant Adapter.

**Tech Stack:** Python 3 / Home Assistant `Store` / `voluptuous` WebSocket API / `unittest`; JavaScript ES modules / Node test runner.

**Spec:** `docs/superpowers/specs/2026-10-02-jamesui-1.0-foundation-design.md`

## Global Constraints

- Variant B remains binding: r11 stays production/reference until controlled cutover.
- Canonical config schema version starts at `1`.
- Canonical top-level sections are exactly `schema_version`, `pages`, `layouts`, `widget_instances`, `dynamic_buttons`, `data_sources`, `module_settings`.
- Shared configuration has exactly one persistence source after Block 5: the versioned Home Assistant Store.
- Existing r11 configuration values are migrated once from `config_entry.options`; known legacy option keys are removed after successful store initialization.
- Temporary r11 API compatibility may translate to/from the structured store, but it must not maintain a second copy of configuration and is deleted at Block 20/21.
- Device-local display calibration (`jamesui-display-calibration`: `top`, `right`, `bottom`, `left`, `scale`) remains browser-local and is never part of shared config or migration.
- No Start widgets, provider discovery, design-system work or production bootstrap cutover in Block 5.
- No new third-party dependency; use Home Assistant and Python/JS standard facilities already available.
- Frontend config access goes through the Block-4 Home Assistant Adapter only; no new raw `hass` access.
- Modules continue receiving configuration through the existing `create(context, config)` / `update(nextContext, nextConfig)` arguments. Do not add Config Service to module context.

## Canonical schema v1

```json
{
  "schema_version": 1,
  "pages": {},
  "layouts": {},
  "widget_instances": {},
  "dynamic_buttons": {},
  "data_sources": {},
  "module_settings": {}
}
```

The six containers are generic mappings in Block 5. Later blocks own their domain-specific schemas; Block 5 validates the container contract and JSON-safe values without pre-designing future widget/page models.

## Review Focus

1. **Existing structured store plus stale legacy options:** stored structured config wins; legacy options are not re-imported, but known legacy keys are cleaned from the config entry.
2. **Invalid replacement/update:** validation fails before persistence; the previous in-memory and stored config remain unchanged and the API reports `invalid_config`.
3. **Concurrent writes:** Config Service serializes updates; every transform starts from the latest committed snapshot so unrelated changes are not lost.
4. **Unknown/newer schema version:** never overwrite or silently downgrade; raise a clear unsupported-version error and preserve stored data.
5. **r11 after migration:** legacy `jamesui/config` GET and `jamesui/config/update` continue to expose/update the same values through projection/patch logic even after `config_entry.options` has been cleaned.

### Task 3: Transactional Config Service and Home Assistant Store integration

**Files:**
- Create: `custom_components/jamesui/config_service.py`
- Create: `custom_components/jamesui/config_store.py`
- Modify: `custom_components/jamesui/__init__.py`
- Create: `tests/test_config_service.py`
- Create: `tests/test_config_storage_architecture.py`

**Interfaces:**
- `config_service.py` remains Home-Assistant-free and defines a storage backend protocol with `async_load()` and `async_save(data)`.
- Produces `JamesUIConfigService(storage)` with:
  - `async_initialize(initial_config) -> bool`: load existing storage when present; otherwise validate/save `initial_config`; return `True` only when a new store was created.
  - `snapshot() -> dict[str, Any]`: detached current config; raises if not initialized.
  - `async_replace(config) -> dict[str, Any]`: validate first, then save, then publish the new in-memory snapshot.
  - `async_update(transform) -> dict[str, Any]`: serialize with one `asyncio.Lock`, run the synchronous transform against a detached latest snapshot, validate/save all-or-nothing, then publish.
- Failed validation or failed storage writes do not modify the current snapshot.
- `config_store.py` defines `JamesUIConfigStore(Store[dict[str, Any]])` with storage key `jamesui.config`, major version `CONFIG_SCHEMA_VERSION`, `atomic_writes=True`, and `_async_migrate_func(...)` delegating to `migrate_stored_config`.
- `async_setup_entry()` creates Store + Config Service, initializes from `migrate_legacy_options(entry.options)` only when storage does not already exist, stores the service in `hass.data[DOMAIN][entry.entry_id]["config"]`, then removes only `LEGACY_OPTION_KEYS` from `entry.options` after successful initialization. Unknown/non-legacy options are preserved.
- If structured storage already exists, it wins over any stale legacy values; known legacy keys are still cleaned afterward.

## Exit criteria

Block 5 is complete only when:

- the canonical configuration persists in one structured versioned Home Assistant Store;
- invalid config cannot partially replace the current config;
- schema migration has an explicit versioned framework;
- all 15 relevant r11 values migrate deterministically and idempotently;
- known legacy option keys are removed after successful migration without overriding an existing structured store;
- r11 config GET/UPDATE still work through temporary projection onto the same structured store;
- local display calibration remains outside shared configuration;
- the new Core Config Service can read/replace structured config through the HA Adapter;
- module context boundaries remain unchanged;
- production r11 bootstrap remains untouched;
- branch and merged `main` CI are green.
