# JamesUI 1.0 Block 0 Baseline and Preservation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Capture the exact r11 behavior, assets and configuration inputs that JamesUI 1.0 intentionally preserves so later blocks can replace and delete the old implementation without guessing.

**Architecture:** Block 0 is characterization only. It adds durable behavior tests and one baseline document around the existing runtime; it does not refactor production frontend code, introduce JamesUI 1.0 runtime modules, or add compatibility layers. Preservation tests must describe behavior that the future implementation can satisfy without retaining r11 file names or monkey-patching.

**Tech Stack:** Home Assistant custom integration (Python), browser JavaScript, Node.js built-in test runner, Python `unittest`, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-02-jamesui-1.0-foundation-design.md`

## Global Constraints

- Variant B only: build the new JamesUI 1.0 foundation in parallel; r11 remains reference/runtime until controlled cutover.
- No product-code refactor or new UI in Block 0.
- No new monkey-patches, `Panel.prototype` overrides, version-polish modules, duplicate production implementations or permanent compatibility shims.
- OnePlus Pad 2 portrait is the primary visual acceptance viewport; Fully is only the kiosk shell.
- Home Assistant remains the backend/source of truth; no fake runtime data is added.
- Intentionally red tests never go to `main`. Characterization tests in this block are expected to PASS against the current r11 baseline; a failure means the test or inventory is wrong and must be corrected on the block branch before merge.
- Keep `PROJECT_STATUS.md` and `docs/JAMESUI_1_0_EXECUTION_ROADMAP.md` current when the block is completed.

## File Structure

- Create: `docs/JAMESUI_1_0_BASELINE.md` — single baseline/retain-delete/migration/visual-acceptance inventory for Block 0.
- Create: `tests/jamesui-entry-preservation.test.js` — executable behavior characterization of the guarded Home Assistant panel bootstrap, independent of r11 visual modules.
- Modify: `tests/test_alpine_assets.py` — extend existing asset validation to the committed SHA-256 manifest.
- Modify: `.github/workflows/validate.yml` — run the new bootstrap preservation test in CI.
- Modify at block completion: `PROJECT_STATUS.md` and `docs/JAMESUI_1_0_EXECUTION_ROADMAP.md` — mark Block 0 complete only after all checks are green.
- Do not modify production files under `custom_components/jamesui/` in this block.

## Review Focus

- **Home Assistant assigns panel properties before custom-element upgrade:** the loader must replay own `hass`, `narrow`, `route`, and `panel` values after the stable panel class becomes available.
- **Panel nested below Home Assistant shadow roots:** discovery must traverse nested open shadow roots rather than only the light DOM.
- **Missing/corrupt Alpine image:** asset tests must fail on a missing file, invalid WebP container, size mismatch or SHA-256 mismatch.
- **Legacy configuration migration input drift:** the baseline must list every currently persisted shared option and separately identify device-local display calibration so Block 5 cannot silently omit a value.
- **Useful logic mixed with legacy rendering:** the baseline must distinguish portable behavior (normalization/classification/routing rules) from r11 markup, CSS and prototype wrappers so later blocks do not copy structural debt.

### Task 2: Characterize the guarded Home Assistant bootstrap behavior

**Files:**
- Create: `tests/jamesui-entry-preservation.test.js`
- Modify: `.github/workflows/validate.yml`
- Read only: `custom_components/jamesui/frontend/jamesui-entry.js`

**Interfaces:**
- Consumes: current classic-script contract of `jamesui-entry.js`.
- Produces: runtime behavior tests that future bootstrap code must continue to satisfy without asserting `jamesui-home-entry.js`, `jamesui-v11-polish.js`, release numbers or r11 selectors.

- [ ] **Step 1: Add a minimal fake-DOM harness inside the test file**

The harness must provide only `window.location`, `document.currentScript`, `document.createElement`, `document.head.appendChild`, recursive `querySelectorAll`, fake elements with optional `shadowRoot`, and captured script `load`/`error` listeners. Execute the real entry source with Node `vm` rather than reimplementing the loader logic in the test.

- [ ] **Step 2: Add test `finds JamesUI panels through nested shadow roots`**

Build a light-DOM host → shadow root → nested host → shadow root → `jamesui-panel` fixture. Assert `window.__jamesUIFindPanels()` returns the nested panel exactly once.

- [ ] **Step 3: Run the new test file**

Run:

```bash
node --experimental-default-type=module --test tests/jamesui-entry-preservation.test.js
```

Expected: PASS against current `main`. If it fails, correct the characterization test; do not change production code in Block 0.

- [ ] **Step 4: Add test `replays predefined Home Assistant panel properties after runtime load`**

Create a panel with own values for `hass`, `narrow`, `route`, `panel`; install prototype setters before firing the captured runtime-script `load` callback; assert each setter receives the original value and the stale own property no longer shadows the setter.

- [ ] **Step 5: Add test `propagates the entry revision to the first runtime script`**

Set `document.currentScript.src` to `/jamesui_static/jamesui-entry.js?v=baseline-token`; assert the first appended runtime script URL contains `v=baseline-token`. Do not assert the name/version of later r11 enhancement modules.

- [ ] **Step 6: Add test `logs runtime load failure without throwing the shell harness`**

Fire the captured first-script `error` callback and assert one `console.error` is emitted containing the failed runtime URL.

- [ ] **Step 7: Run both preservation and existing entrypoint tests**

Run:

```bash

python -m unittest tests/test_frontend_entrypoint.py
```

Expected: both PASS. The old Python test may remain r11-specific for now; Block 21 removes/supersedes release-specific assertions after cutover.

- [ ] **Step 8: Add the preservation test to CI**

In `.github/workflows/validate.yml`, add a step immediately after `Test Home Assistant panel entrypoint`:
