# JamesUI 1.0 Block 9 Weather Provider Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `provider.weather` as the canonical JamesUI 1.0 weather data provider with truthful current/forecast/sun/moon/atmosphere capabilities and no UI or production cutover.

**Architecture:** Keep Home Assistant access behind the existing adapter, extend that adapter only with a narrow timezone accessor, and keep all weather calculations in pure helper modules. `provider.weather` owns subscriptions, capability publication, source selection and one five-minute time-derived refresh timer; pure helpers own normalization, day grouping, astronomy and atmosphere mapping.

**Tech Stack:** JavaScript ES modules, Node built-in test runner, existing Module Registry/Loader + Capability Registry + Home Assistant Adapter, `Intl.DateTimeFormat` with explicit IANA timezone, local astronomy formulas adapted from SunCalc v1.9.0 under BSD-2-Clause attribution. No npm/runtime dependency.

**Spec:** `docs/superpowers/specs/2026-10-03-jamesui-1.0-block-9-weather-provider-design.md`

## Global Constraints

- Module ID: `provider.weather`, type `provider`, version `1.0.0`, Core API `1.x`.
- Exact provided capabilities: `weather.current`, `weather.daily`, `weather.hourly`, `weather.sun`, `weather.moon`, `weather.atmosphere`.
- Provider context stays `events`, `overlays`, `capabilities`, `actions`, `module`, `homeAssistant`; no raw `hass`, Config Service, Router, Health, Module Registry/Loader, Design System or asset internals.
- Explicit configured `weather.*` source never silently falls back; automatic mode may deterministically reselect.
- True Hourly remains true Hourly; Daily fallback priority is usable `daily` → `twice_daily` → `hourly`.
- Precise `next_precipitation_at` comes only from true Hourly data, threshold `>= 40%`, positive precipitation or canonical precipitation conditions.
- Every Daily `YYYY-MM-DD` key and “today” decision uses Home Assistant's configured IANA timezone; no browser/process timezone fallback.
- Daily publishes at most seven calendar days.
- Sun period thresholds are exactly `< -6 night`, `-6..<1 twilight`, `1..<12 golden`, `>=12 day`.
- Moon has eight canonical phases, local fallback, no network/runtime package, no moonrise/moonset/observer-position calculations.
- Moon formula provenance is SunCalc v1.9.0 / BSD-2-Clause; checked-in attribution is required if formulas are adapted.
- Moon reliability references use US Naval Observatory 2026 UTC primary-phase times. Illumination acceptance at primary events is fixed at ±3 percentage points around the physical 0/50/100% expectation.
- Atmosphere publishes semantic scene keys only, never WebP/SVG paths.
- Exactly one five-minute provider timer per mounted instance; it recalculates only local time-derived values and never polls HA.
- r11 product files and `jamesui-entry.js` remain unchanged; Block 10 UI is out of scope.

## Review Focus

1. **Stale async forecast callback after a source/config switch** — it must be ignored and must not overwrite the new generation; pinned in Task 6.
2. **HA-local day around UTC/local-midnight and DST boundaries** — grouping and “today” must use the explicit HA timezone; pinned in Task 3.
3. **Configured weather source becomes unavailable while another source is healthy** — provider must remain on the configured source and publish unavailable; pinned in Tasks 2 and 6.
4. **Moon cycle wrap near new moon plus primary-phase accuracy** — new moon must bucket correctly on both sides of cycle zero and USNO events must meet the fixed tolerance; pinned in Task 5.
5. **Timer/destroy race** — one timer only, no HA polling, and no callback may publish after destroy; pinned in Task 6.
