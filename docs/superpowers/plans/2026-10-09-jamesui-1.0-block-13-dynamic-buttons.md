## Task 1 – Control-state manifest and source configuration

**Files:**
- Create `provider.control-state/manifest.js`
- Create `provider.control-state/config.js`
- Test `tests/jamesui-control-state-manifest-config.test.js`

### Interfaces

Manifest:

```text
id: provider.control-state
type: provider
version: 1.0.0
core_api: 1.x
depends_on: []
requires_capabilities: []
provides_capabilities: [control.states]
config_schema: provider.control-state/v1
```

Provider runtime config:

```text
{
  sources: [
    {
      id,
      entity_id,
      attribute?,
      active_values,
      inactive_values,
      intermediate: [
        { id, values }
      ]
    }
  ]
}
```

The later Block-14 composition layer can derive this provider config from canonical `data_sources.control_states`. Block 13 does not wire the global Config Service into the provider.

Raw mapping values may be JSON scalar values: string, finite number or boolean. `null`, objects and arrays are not valid mapped signal values.

### Validation rules

- config must contain only `sources`;
- source IDs unique/non-empty;
- entity ID non-empty;
- optional attribute non-empty;
- `active_values` and `inactive_values` non-empty;
- intermediate IDs unique/non-empty;
- each intermediate values list non-empty;
- no duplicate value inside one mapping;
- no raw value may overlap active/inactive/intermediate mappings;
- mapped values are detached/deep-frozen.

Use type-aware equality for configured values so numeric `1` and string `"1"` are not silently conflated.

## Task 3 – `control.states` provider service and revision semantics

**Files:**
- Create `provider.control-state/provider.js`
- Create `provider.control-state/index.js`
- Test `tests/jamesui-control-state-provider.test.js`

### Provider context requirements

Require:

- `context.capabilities.register`
- `context.homeAssistant.connectionState`
- `context.homeAssistant.getState`
- `context.homeAssistant.subscribeEntity`
- `context.homeAssistant.subscribeConnection`

No DOM/design/icon access.

### Capability service

When configured and connected, publish an immutable service:

```text
{
  version: 1,
  configured_sources: [{ id }],
  subscribe({ source_ids }, listener) -> unsubscribe
}
```

Listener payload:

```text
{
  states: [
    {
      source_id,
      status,
      detail,
      revision,
      reason
    }
  ]
}
```

The returned states preserve the request `source_ids` order.

### Subscription semantics

- request must contain a non-empty unique `source_ids` array;
- every requested source must be configured;
- immediate initial emission;
- source records are shared across consumers;
- underlying HA entity subscriptions are shared/ref-counted when multiple active source records use the same entity;
- releasing the final consumer removes no-longer-needed HA subscriptions;
- listener exceptions are isolated.

### Revision semantics

For each active provider generation/source:

- initial normalized snapshot starts at revision `0`;
- revision increments only when the normalized relevant signal changes:
  - status changes;
  - intermediate detail changes;
  - unavailable reason changes where it represents a changed bound-signal condition;
- unrelated changes to the HA entity object/other attributes must not advance revision;
- repeated identical normalized updates do not notify consumers as fresh acknowledgement.

This prevents a stale pre-command state from becoming a false post-command response.

### Top-level lifecycle

- zero configured sources -> `not_configured("no_control_state_sources")`;
- HA disconnected -> top-level `unavailable("home_assistant_disconnected")`;
- reconnect creates a fresh service generation;
- old service rejects new subscriptions after replacement;
- old callbacks cannot notify current consumers;
- update/destroy clears consumers/entity subscriptions;
- mounted update validates next config/context before destructive rebind;
- if rebind fails, restore previous runtime atomically.

### Review-focus tests

Include explicit tests for:

1. two consumers sharing one source;
2. two configured sources sharing one HA entity with different attributes;
3. repeated HA update with unchanged bound value does **not** increment revision;
4. intermediate -> previous terminal transition increments and is observable;
5. disconnect/reconnect replaces service;
6. old service use rejects after replacement;
7. late old-generation callback is ignored;
8. failed mounted rebind restores old capability/runtime.

### TDD steps

1. Write provider tests.
2. Verify RED.
3. Implement provider/index.
4. Verify targeted provider suite GREEN.
5. Commit:
   `feat: add control state capability`

## Task 4 – Dynamic Button library, generic actions and instance resolver

**Files:**
- Create `widget.dynamic-buttons/manifest.js`
- Create `widget.dynamic-buttons/config.js`
- Test `tests/jamesui-dynamic-buttons-config.test.js`

### Manifest

```text
id: widget.dynamic-buttons
type: widget
version: 1.0.0
core_api: 1.x
depends_on: []
requires_capabilities: [control.states]
provides_capabilities: []
config_schema: widget.dynamic-buttons/v1
```

The widget requires the capability contract but must still render triggers if the capability is unavailable.

### Central library validator

Export:

`validateDynamicButtonDefinitions(value)`

Input is the canonical `dynamic_buttons` object keyed by stable button ID.

Common definition fields:

- `name` required;
- `mode` exactly `toggle` or `trigger`;
- optional registered semantic `icon`;
- optional positive finite `timeout_ms`; default `5000`.

Generic action validator:

- plain object;
- non-empty string `type`;
- any JSON-safe provider-specific fields are preserved;
- deep-detach/deep-freeze;
- do **not** duplicate provider-specific validation.

Toggle requires only:

- `state_source_id`;
- `activate_action`;
- `deactivate_action`;
- optional `presentation`.

Trigger requires only:

- `action`;
- optional one-line `description`.

Reject fields belonging to the other mode.

### Presentation validator

Toggle presentation supports:

```text
active: { text?, icon? }
inactive: { text?, icon? }
intermediate:
  <detail-id>: { text?, icon? }
```

- text is trimmed/non-empty when present;
- icons must exist in the existing semantic icon registry;
- intermediate detail keys are non-empty;
- no additional display rows/fields.

### Per-widget instance selector

Export:

`validateDynamicButtonInstanceConfig(value)`

Shape:

```text
{
  buttons: [
    {
      id,        // stable local use identity
      button_id, // central definition reference
      size       // compact | normal | wide
    }
  ]
}
```

Rules:

- local use IDs unique;
- button reference non-empty;
- size required and one of the three classes;
- array order is preserved as deterministic content order only; Block 14 later owns actual grid coordinates.

Export pure resolver:

`resolveDynamicButtonInstance({ definitions, instance })`

It validates both sides, rejects missing references, and produces a deeply frozen resolved widget runtime config without giving the widget Config Service access.

Repeated central `button_id` uses are allowed when local use IDs differ; each use owns independent transient interaction state.

2. Verify RED.
3. Implement manifest/config.

### Pure interfaces

At minimum expose pure helpers equivalent to:

```text

  { action, target_status } | null

  use,
  sourceState?,
  interaction
}) -> immutable view model
```

`interaction` is local runtime state such as:

```text
idle | pending | success | error
```

### Required behavior

Toggle:

- inactive -> activate action / expected active;
- active -> deactivate action / expected inactive;
- intermediate/unavailable -> non-actionable;
- active uses standard active presentation status;
- inactive neutral;
- unavailable gives `Nicht verfügbar`;
- intermediate uses configured text/icon or generic `In Ausführung`;
- base icon fallback;
- fixed name always present;
- max one secondary line.

Trigger:

- neutral when idle;
- optional description is secondary line;
- pending may show `Wird ausgeführt …`;
- success/error are transient feedback overlays/presentation flags, not real state.

Mode indicator:

- model always exposes `toggle` or `trigger` for permanent compact mode indication.

Sizing:

- preserve `compact | normal | wide` in model;
- do not convert to concrete Block-14 grid spans.

## Task 6 – Dynamic Button DOM and interaction state machines

**Files:**
- Create `widget.dynamic-buttons/widget.js`
- Create `widget.dynamic-buttons/index.js`
- Test `tests/jamesui-dynamic-buttons-widget.test.js`

### Widget context

Require:

- `context.capabilities.subscribe`
- `context.actions.execute`
- correct `context.module.id`

Explicitly reject/avoid raw Home Assistant use.

### Capability binding

- subscribe to `control.states`;
- when a valid service appears, create one per-widget subscription for the unique state source IDs used by toggles;
- triggers remain usable even if `control.states` is unavailable;
- release old source subscription on capability service replacement;
- capability unavailability maps toggle sources to unavailable without blanking triggers/healthy siblings.

### Local runtime state

Maintain local interaction state keyed by local use ID.

Each operation gets a monotonically increasing local token/generation. Timer callbacks, Action Registry completions and feedback callbacks must verify that token before mutating UI.

### Toggle click flow

On click when terminal and idle:

1. capture current source revision;
2. choose action/target from the current real state;
3. create operation token;
4. enter pending;
5. start one timeout using button `timeout_ms`;
6. execute action through Action Registry.

Action handling:

- `success`: keep pending;
- `rejected | unavailable | error`: fail immediately;
- thrown/rejected Promise: treat as error;
- completion after operation already succeeded/failed/was replaced: ignore.

Feedback handling for revision > baseline:

- expected target terminal -> success and clear pending immediately;
- intermediate -> stay pending and rerender detail;
- opposite terminal -> transient error immediately;
- unavailable -> transient error immediately.

No new revision -> continue pending until timeout.

### Trigger click flow

- enter pending;
- block repeated click;
- execute action;
- race against timeout;
- success -> transient success for **650 ms**;
- any failure/timeout -> transient error;
- late Action completion after timeout ignored.

### Error feedback

Use one implementation constant for a short multi-pulse window, planned approximately **1500 ms / three visual pulses**.

After feedback window:

- toggle returns to latest real-state presentation;
- trigger returns neutral.

No retry/history/escalation.

### Service replacement/update/destroy

- a pending toggle loses revision continuity when `control.states` service is replaced; terminate it safely with transient error then bind the new real state;
- widget update validates next resolved config before rebinding;
- update clears obsolete local operations/timers;
- destroy clears every timer/subscription and prevents late callback resurrection.

### Multiple instances

Directly create two widgets using the same central definition/source.

Prove:

- both receive the same real source update;
- pending/error/success on instance A does not appear on instance B;
- both remain independently destroyable.

### Future long-press compatibility

Block 13 adds **no** pointer/long-press/drag handler.

DOM must expose stable identity attributes such as:

- widget marker;
- local use ID;
- central button ID;
- mode;
- size;
- real status;
- local feedback state.

Native click is the only action activation path so Block 14 can later intercept long-press/drag at the host/editor layer and suppress click.

### Review-focus tests

Include:

1. stale initial status does not acknowledge command;
2. Action success before feedback stays pending;
3. target feedback before Action Promise resolves wins and late Action result is ignored;
4. intermediate feedback keeps pending;
5. intermediate -> opposite terminal fails immediately;
6. unchanged bound status eventually times out;
7. source becomes unavailable during pending -> fail;
8. repeated click during pending causes one action call only;
9. trigger timeout ignores late success;
10. update/destroy cancels pending timers and callbacks;
11. service replacement during pending cannot carry old revision continuity forward.

1. Write widget tests.
2. Verify RED.
3. Implement widget/index.
4. Verify GREEN.
5. Commit:

## Final Block-13 acceptance checklist

Before reporting `✅ Fertig` after implementation:

- `control.states` exists and is owned by `provider.control-state`.
- Status provider is HA-adapter-backed but consumer contract is HA-independent.
- One explicit source signal is mapped to active/inactive/intermediate/unavailable.
- Unmapped values are unavailable.
- Revision advances only on meaningful bound-signal changes.
- Central Dynamic Button definitions and per-instance uses are separated.
- Generic Action Registry payloads are preserved without duplicating provider validation.
- Toggle requires activate + deactivate + state source.
- Trigger requires one action.
- Toggle stays pending after Action `success` until new real target feedback.
- Real target feedback can complete before the Action Promise and wins that race.
- Intermediate feedback keeps pending.
- Wrong terminal/unavailable feedback fails immediately.
- Timeout gives transient error and no retry/history.
- Trigger success lasts about 650 ms then neutral.
- Trigger/toggle repeat taps are blocked during pending.
- External intermediate and unavailable toggles are non-actionable.
- Shared real state synchronizes across instances.
- Pending/success/error remains local to the pressed use instance.
- Fixed name, optional icon, one secondary line and visible mode indicator are enforced.
- Active matches standard JamesUI active styling.
- No widget header is introduced.
- `compact | normal | wide` are exposed without final grid-span decisions.
- No long-press/drag editor implementation is pulled forward.
- No raw HA widget access, no r11 changes, no monkey patches.
- Targeted tests, architecture guard, whole-branch review, unchanged-head CI and merged-main CI are green.
