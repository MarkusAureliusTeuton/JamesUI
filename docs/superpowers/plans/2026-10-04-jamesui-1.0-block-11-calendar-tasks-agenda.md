# JamesUI 1.0 – Block 11 Calendar, Tasks and Agenda Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement `provider.calendar`, `provider.tasks`, `action.task-update` and `widget.calendar-agenda` exactly to the approved Block-11 design, with truthful Home Assistant time/source semantics, task completion/editing, JamesUI-owned advance notices and bounded host-aware rendering, while leaving r11 production and final Start composition untouched.

**Architecture:** Calendar is a range-based read capability, tasks are a live normalized snapshot, mutations go through one semantic `task.update` action, and the Agenda widget owns only presentation/transient UI. Providers/actions alone use the Home Assistant Adapter. A small pure shared zoned-time helper prevents duplicate DST/date arithmetic across Calendar and Agenda without introducing domain behavior into Core.

**Tech Stack:** Vanilla ES modules, existing JamesUI Module/Capability/Action/Overlay contracts, Home Assistant Adapter, Block-6 design tokens/primitives, Block-7 semantic icon registry, Node `node:test`, Python architecture gates, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-04-jamesui-1.0-block-11-calendar-tasks-agenda-design.md`

## Global Constraints

- Primary visual target remains OnePlus Pad 2 portrait; Fully is kiosk shell only.
- r11 remains production/reference. Do not change `jamesui-entry.js` production behavior or perform Start composition/cutover.
- `widget.calendar-agenda` has no raw Home Assistant access and never imports the Home Assistant Adapter.
- Providers/actions may use only the existing `context.homeAssistant` adapter; do not add raw `hass` shortcuts.
- User commands go through the Action Registry. Todo mutation from the widget is only `task.update`, never generic `ha.service`.
- Calendar and task source selection is explicit. No auto-discovery fallback content.
- All Agenda domain date/time semantics use the validated Home Assistant timezone. Browser timezone is never a silent fallback.
- Missing/unavailable backend data stays explicit. Do not reuse stale event/task values as current after source failure/disconnect.
- Page scrolling and widget allocation remain layout responsibilities. Agenda may scroll internally but may not grow its host merely to expose more content.
- Generic multi-instance loader/page orchestration stays Block 14. Block 11 proves the widget implementation itself is safe for multiple direct `create()` instances.
- No task create/delete/move/reorder and no calendar mutation in this block.
- No source reminder/alarm claims. Advance notices are explicitly JamesUI-owned.
- No monkey-patches, Prototype overrides, release-polish layers, parallel implementations or permanent compatibility shims.
- TDD is mandatory. Intentionally red tests stay on the implementation branch and never reach `main`.

## Exact V1 configuration names

Provider configs use:

```text
provider.calendar/v1
{ source_entity_ids: ["calendar.family", ...] }

provider.tasks/v1
{ source_entity_ids: ["todo.household", ...] }

```

Agenda config uses these exact V1 field names:

```text
{
  instance_id,
  presentation_mode,
  calendar_enabled,
  tasks_enabled,
  visible_items_mode,
  max_visible_items,
  lookahead_days,
  lookback_days,
  show_all_day,
  show_location,
  task_order_mode,
  untimed_task_position,
  calendars: [
    {
      entity_id,
      lookahead_days: null | 1..365,
      icon_id,
      accent: null | "#RRGGBB",
      advance_notice_days: 0..365,
      rules: [
        {
          operator: "exact" | "contains" | "starts_with",
          query,
          include_description,
          include_location,
          icon_id: null | <semantic icon id>,
          accent: null | "#RRGGBB",
          advance_notice_days: null | 0..365
        }
      ]
    }
  ],
  task_lists: [
    {
      entity_id,
      icon_id,
      accent: null | "#RRGGBB"
    }
  ]
}
```

`instance_id` is required, stable and non-empty. It is infrastructure identity for independent widget state/local notice dismissal; Block 14 later supplies it from `widget_instances` orchestration.

Defaults when a field is omitted:

```text
presentation_mode = grouped
calendar_enabled = true
tasks_enabled = true
visible_items_mode = auto
max_visible_items = 5
lookahead_days = 30
lookback_days = 7
show_all_day = true
show_location = false
task_order_mode = chronological
untimed_task_position = after
calendar.icon_id = home.calendar
calendar.accent = null
calendar.advance_notice_days = 0
calendar.rules = []
task_list.icon_id = home.task
task_list.accent = null
```

The source arrays themselves are not auto-populated. An enabled domain with zero matching configured sources is invalid.

## Review Focus

1. **Timezone/DST truthfulness:** local calendar-day arithmetic, range boundaries, midnight, timed multi-day projections and advance thresholds must stay correct across DST without browser-time fallback.
2. **Stale-data isolation:** source removal/unavailability, reconnect, config update and late remote callbacks must never republish stale event/task data.
3. **Calendar range ownership:** identical remote range subscriptions may be shared, but unsubscribe/ref-count races must not disconnect an active sibling consumer.
4. **Todo clearing semantics:** clearing due must identify whether the real item currently has date or datetime due; never send both HA due fields.
5. **Optimistic task state:** completion/Undo/edit failures must reconcile back to capability truth; multiple Undo entries cannot overwrite each other.
6. **Advance notices:** extra retrieval horizon must not leak future events into normal Agenda rows, and DST lead calculations use local calendar days rather than fixed 24-hour milliseconds.
7. **Host sizing:** no partial rows, no page-growth side effect, no unstable row geometry when status/notices/location are present.
8. **Instance isolation:** two direct Agenda instances with different sources/modes/local dismissals must never share transient state.

```text

  time_zone,
  configured_sources: [{ entity_id, name }],
```

- Exact remote message:

```text
{
  type: "calendar/event/subscribe",
  entity_id,
  start: <zonedStartOfDate(start_date)>,
  end: <zonedStartOfDate(end_date)>
}
```

- Local `subscribeEntity()` tracks missing, `unknown`/`unavailable`, friendly-name and recovery state.


**Sizing:**
- `computeVisibleCapacity({ hostHeight, chromeHeight, rowHeight }) -> integer >=0`.
- Measure an actual rendered row/probe height; do not hard-code a separate JS row pixel value that can drift from CSS.
- Fixed mode limits normal viewport to at most `max_visible_items` rows when space allows; smaller host allocation keeps full rows and scrolls internally.
- Auto uses all complete rows that fit.
- If chrome + one complete row cannot fit → `data-jui-agenda-state="too_small"` and no partial row.
- Status/notice/header regions consume height but never item budget.

**Scheduler:**
- one widget-owned timeout only;
- schedule earliest future boundary among event start/end, next notice threshold, HA-local midnight and active Undo expiry;
- after callback, recompute view model/ranges and schedule the next one;
- no minute/second polling loop.

**Midnight selected-day rule:**
- if day mode was showing the old Today, follow to new Today;
- if user was browsing another absolute date, retain that date when still within new bounds, otherwise clamp to nearest valid bound.

**Undo:**
- exact `UNDO_DURATION_MS = 5000`;
- independent map key `source_entity_id + uid`;
- completion action success creates optimistic hidden state and Undo entry;
- Undo sends only `status: needs_action`;
- stream state remains authoritative;
- late action completions after destroy/generation change cannot touch detached DOM.
