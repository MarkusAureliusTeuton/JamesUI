# JamesUI 1.0 Block 2 Module System Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Introduce the JamesUI 1.0 modular runtime contract: validated manifests, an immutable Module Registry, lifecycle-safe module loading, module-specific version tokens, isolated reload and module health reporting, without implementing capabilities, actions, Home Assistant access or configuration storage.

**Architecture:** Block 2 extends the parallel Core created in Block 1. Manifest validation is a pure contract layer; the Registry owns immutable manifest/source descriptors and dependency/declaration checks; the Loader owns import, `create/mount/update/destroy`, per-module reload generations and health isolation. Capability fields are validated as metadata only in this block; actual capability availability/subscription remains Block 3. The current r11 production entry remains untouched and the new Core stays parallel/unwired.

**Tech Stack:** Browser JavaScript ES modules, dynamic `import()`, standard DOM APIs, Node.js built-in test runner, Python `unittest`, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-02-jamesui-1.0-foundation-design.md`

**Roadmap:** `docs/JAMESUI_1_0_EXECUTION_ROADMAP.md`

## Global Constraints

- Variant B remains binding: new JamesUI 1.0 infrastructure is built in parallel while r11 remains production/reference until the controlled cutover.
- Block 2 must not modify `jamesui-entry.js`, `jamesui-panel.js`, the current r11 Start modules, panel registration, frontend revision or production bootstrap.
- Block 2 must not implement the Capability Registry or Action Registry from Block 3.
- `requires_capabilities` and `provides_capabilities` are declaration metadata only in Block 2. A required capability may be unresolved at registration/load time without being treated as a runtime error.
- Block 2 must not add raw Home Assistant access or expose `hass`, registries, WebSocket/service APIs or host-context objects to module context; the HA Adapter remains Block 4.
- Block 2 must not introduce structured shared configuration/migrations from Block 5, Design System from Block 6, Icon Registry from Block 7 or domain-specific modules.
- Module dependency metadata and capability metadata remain separate: no ambiguous `requires` field.
- Initially supported module types are exactly `layout`, `widget`, `provider`, `action`. `page-extension` remains deferred until a proven future use case.
- Every registered module has an ID, type, semantic module version, compatible Core API declaration, `depends_on`, `requires_capabilities`, `provides_capabilities`, `config_schema` reference and an import entry URL.
- Every loaded module exports `create(context, config)` and returns an instance implementing synchronous `mount(target)`, `update(nextContext, nextConfig)` and `destroy()` lifecycle methods. Dynamic import/reload is asynchronous; lifecycle methods themselves remain synchronous in Block 2.
- Module errors are isolated and reported through the existing Health Service using health ID `module:<moduleId>`; one module failure must not corrupt the Registry, Loader or other loaded modules.
- Module imports use the manifest module version as a `v=` query token. Reloading one module adds/changes only that module's reload-generation token and must not reload unrelated modules.
- No runtime monkey-patching, `Panel.prototype` overrides, release-version production paths or compatibility shims.
- TDD for behavior changes; intentionally red tests never go to `main`.
- Keep `PROJECT_STATUS.md`, roadmap and next-chat handover current after successful Block 2 validation.

## Review Focus

1. **Malformed or ambiguous manifest metadata:** wrong types, duplicate array values, unsupported module type/version/API range or ambiguous `requires` must be rejected before Registry state changes; pinned in Task 1.
2. **Registry consistency under conflicts:** duplicate module IDs, missing concrete dependencies, duplicate capability providers and removal of a dependency still used by another module must not leave partial state; pinned in Task 2.
3. **Import/create/lifecycle failures:** one throwing module must produce `module:<id>` health error without breaking another module or leaving stale runtime state; pinned in Task 3.
4. **Version-token/reload URL edge cases:** existing query/hash content must survive; `v=` must match only that module's manifest version and reload generation must affect only the requested module; pinned in Task 3.
5. **Core destroy/context boundary:** Core destruction must clean all loaded module lifecycles and module context must not expose raw Home Assistant host values; pinned in Task 4.

### Task 2: Immutable Module Registry and dependency/declaration checks

**Files:**
- Create: `custom_components/jamesui/frontend/core/module-registry.js`
- Create: `tests/jamesui-module-registry.test.js`

**Interfaces:**
- `createModuleRegistry({ coreApiVersion = CORE_API_VERSION } = {})` returns `register`, `unregister`, `get`, `has`, `list` and `getCapabilityProvider`.
- `register(manifest, { entryUrl }) -> frozenRecord` validates/normalizes the manifest first, requires a non-empty string `entryUrl`, then atomically stores `{ manifest, entryUrl }` as an immutable record.
- Module IDs are unique.
- Every `depends_on` module must already be registered. A failed registration must not partially claim the ID or any capability.
- `provides_capabilities` is declaration ownership only in Block 2. Two registered modules may not claim the same provided capability.
- `requires_capabilities` does **not** require a matching provider in Block 2; unresolved requirements are valid metadata for Block 3.
- `getCapabilityProvider(capability) -> moduleId | null` reports declaration ownership only; it is not a Capability Registry implementation.
- `unregister(id) -> boolean` returns `false` for unknown IDs and refuses removal when another registered module names the ID in `depends_on`; successful removal releases its capability declarations.
- `get()`/`list()` return immutable stored records; callers cannot mutate Registry state through returned objects.

### Task 3: Versioned Module Loader, lifecycle and isolated reload

**Files:**
- Create: `custom_components/jamesui/frontend/core/module-loader.js`
- Create: `tests/fixtures/modules/layout-minimal.js`
- Create: `tests/fixtures/modules/widget-minimal.js`
- Create: `tests/fixtures/modules/provider-minimal.js`
- Create: `tests/jamesui-module-loader.test.js`

**Interfaces:**
- `buildModuleImportUrl(entryUrl, version, reloadGeneration = 0) -> string` preserves existing query parameters and hash fragments, sets/replaces `v=<moduleVersion>`, and adds `r=<generation>` only when generation is greater than zero.
- `createModuleLoader({ registry, health, importer = (url) => import(url), getContext = () => Object.freeze({}) } = {})` requires Registry and Health Service dependencies.
- Loader exposes `load(id, { config = {} } = {}) -> Promise<boolean>`, `mount(id, target) -> boolean`, `update(id, nextConfig) -> boolean`, `destroy(id) -> boolean`, `reload(id) -> Promise<boolean>`, `destroyAll()` and `isLoaded(id) -> boolean`.
- `load()` uses the Registry record and manifest version, dynamically imports the versioned URL, requires an exported `create(context, config)` function, calls it with the current context/config, validates that the returned instance implements `mount`, `update`, `destroy`, and stores runtime state only after the full create/contract step succeeds.
- Module lifecycle methods are synchronous in Block 2. If `create()` returns a Promise instead of a lifecycle instance, treat it as an invalid Block-2 contract and report module health error.
- `mount()` remembers the target only after successful mount.
- `update()` calls the instance with a fresh `getContext()` result and the supplied next config, then stores the config only after successful update.
- `destroy()` removes loader runtime state even when the module's `destroy()` throws; the error is reported, preventing a broken module from becoming an undeletable stale runtime.
- `reload()` affects only one ID: preserve its latest config and mounted target, destroy the old runtime, increment only that module's reload generation, re-import it with the same manifest `v=` and new `r=`, then remount only if it was mounted before.
- All importer/create/mount/update/destroy/reload failures are caught and reported as `health.report("module:<id>", { status: "error", ... })`; they return `false` and do not throw through the Core/module caller.
- Successful load/mount/update/reload clears stale `module:<id>` health error.
- `destroyAll()` attempts every loaded module even if one destroy fails.
