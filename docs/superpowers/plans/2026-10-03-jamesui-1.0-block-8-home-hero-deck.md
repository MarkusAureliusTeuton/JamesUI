# JamesUI 1.0 Block 8 `layout.home-hero-deck` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the reusable `layout.home-hero-deck` module with four stable Start-page slots, token-driven hero/deck geometry, CSS-only responsive behavior, and full compatibility with the existing JamesUI Module Registry/Loader without introducing Start business logic or a production cutover.

**Architecture:** The layout lives entirely under `frontend/modules/layout.home-hero-deck/` and follows the existing synchronous module lifecycle. It derives DOM creation from the mount target's `ownerDocument`, owns only its root/style/structural DOM, exposes stable slot elements through `getSlot()`/`listSlots()`, and never loads widgets itself. Core, Home Assistant, capabilities, actions, config service, r11 production code and Start route composition remain unchanged.

**Tech Stack:** Browser ES modules, DOM API, CSS Grid + CSS Container Queries, existing JamesUI Module Registry/Loader, Block-6 design tokens, Node `node:test`, Python `unittest` architecture guards, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-03-jamesui-1.0-block-8-home-hero-deck-design.md`

## Global Constraints

- Module ID is exactly `layout.home-hero-deck`; type is `layout`; version is `1.0.0`; Core API requirement is `1.x`.
- Exactly four semantic slots exist: `hero`, `widget-left`, `widget-right-main`, `widget-right-footer`.
- Slot elements must retain identity and children across `update()`.
- Default `hero_ratio` is `0.42`; accepted range is `0.35` through `0.50` inclusive.
- Configuration is strict: only optional `hero_ratio` is accepted; arbitrary CSS/device/widget/entity fields are rejected.
- Responsive behavior is CSS-only with one layout-local `44rem` container breakpoint.
- Primary deck presentation is two columns; narrow semantic order is `widget-left`, `widget-right-main`, `widget-right-footer`.
- Deck is one continuous surface with rounded upper corners and square lower corners.
- Visual values consume existing Block-6 `--jui-*` tokens; no duplicate raw palette/spacing/radius system is introduced.
- No Home Assistant access, capability/action/config-service use, widget loading, domain logic, Alpine background selection, Core Start markup or r11 production changes.
- No `window.innerWidth`, resize listeners, Home Assistant `narrow`, device sniffing, `!important`, data-URL/inline SVG, external fetch or release-specific polish layer.
- r11 remains production/reference throughout Block 8.

## Review Focus

1. **Atomic invalid update:** an invalid `hero_ratio`/unknown config key must throw before changing the current ratio, slot identity or mounted slot contents. Task 2 pins this.
2. **Repeated mount/destroy:** remount must remove the old owned root/style and create one fresh slot set; repeated destroy must be harmless. Task 2/3 pin this.
3. **Document ownership:** the module must use `target.ownerDocument` rather than expanding module context or depending on browser-global `document`. Task 2 pins this.
4. **Responsive semantic order:** the CSS breakpoint must never hide/reorder semantic content incorrectly; DOM order remains left → right-main → right-footer. Task 3 pins this.
5. **Boundary containment:** layout code must stay free of HA/domain/widget/composition behavior and the legacy production entry must not load it. Task 5 pins this.
