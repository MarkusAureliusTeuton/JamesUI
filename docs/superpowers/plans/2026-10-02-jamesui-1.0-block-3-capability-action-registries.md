# JamesUI 1.0 Block 3 Capability and Action Registries Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the JamesUI 1.0 runtime contracts that let provider modules publish named capabilities and consumer modules subscribe to them, while interactive modules dispatch configured actions through a normalized Action Registry without direct provider imports or raw Home Assistant access.

**Architecture:** Block 3 extends the parallel Core and Module System from Blocks 1–2. The Capability Registry turns manifest capability declarations into runtime provider state and subscriptions while preserving the Module Registry as declaration ownership. The Action Registry is independent from Home Assistant: it owns action provider registration, dispatch and normalized results; only `navigate` and `url.open` receive real Core implementations in this block, while `entity.toggle`, `ha.service` and `scene.activate` are contract-tested with test providers only. Module context is widened only to safe registry interfaces and immutable module identity.

**Tech Stack:** Browser JavaScript ES modules, standard DOM/browser APIs, Node.js built-in test runner, Python `unittest`, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-02-jamesui-1.0-foundation-design.md`

**Roadmap:** `docs/JAMESUI_1_0_EXECUTION_ROADMAP.md`

## Global Constraints

- Variant B remains binding: the JamesUI 1.0 Core remains parallel and unwired from the production r11 Home Assistant panel until the controlled cutover.
- Block 3 must not modify `jamesui-entry.js`, `jamesui-panel.js`, current r11 Start modules, frontend revision or production bootstrap.
- Capability names remain manifest declarations in `provides_capabilities` / `requires_capabilities`; the runtime Capability Registry must not collapse them back into module dependencies.
- Capability runtime states are exactly `available`, `unavailable`, `not_configured`.
- Absence/removal of an active provider is represented explicitly as `unavailable`; it must not throw or return an ambiguous missing value to consumers.
- The Action Registry normalized result statuses are exactly `success`, `unavailable`, `rejected`, `error`.
- Real Block-3 action implementations are limited to `navigate` and `url.open`.
- `entity.toggle`, `ha.service` and `scene.activate` may be registered only as test/fake providers in Block 3; production implementations belong to Block 4 and must use the future Home Assistant Adapter.
- Block 3 must not add raw `hass`, `hass.states`, service calls, WebSocket access, registry access or Home Assistant host context to module context.
- The Event Bus remains limited to transient technical/UI/lifecycle events and must not become the capability data channel or action dispatch channel.
- Block 3 must not introduce structured shared config/migrations, design tokens/icons or domain-specific weather/calendar/house/media/climate/door logic.
- Module context remains immutable and contains only approved Core services plus immutable module identity.
- No runtime monkey-patching, `Panel.prototype` overrides, release-version production paths or compatibility shims.
- TDD for behavior changes; intentionally red tests never go to `main`.
- Keep `PROJECT_STATUS.md`, roadmap and next-chat handover current after successful Block 3 validation.

## Review Focus

1. **Capability ownership mismatch:** a module must not publish a capability it did not declare, nor impersonate another module's declaration owner; Task 1 tests this atomically.
2. **Provider disappearance:** unregistering a live provider must notify consumers with an explicit `unavailable` snapshot and never leave stale available data; Task 1 pins this.
3. **Subscriber isolation:** one throwing capability subscriber must not block other consumers or mutate registry state; Task 1 pins this without using the Event Bus as the data channel.
4. **Action provider failure/invalid return:** thrown providers, unknown action types and malformed result objects must always become one of the four normalized result statuses rather than escape through the caller; Task 2 pins this.
5. **Safe module context / HA boundary:** widening context must not expose `hass`, host `route`, `panel`, raw router or any direct Home Assistant API while still allowing provider/widget/action cooperation; Task 4 pins this end-to-end.

### Task 1: Runtime Capability Registry

**Files:**
- Create: `custom_components/jamesui/frontend/core/capability-registry.js`
- Create: `tests/jamesui-capability-registry.test.js`

**Interfaces:**
- `createCapabilityRegistry({ moduleRegistry, onSubscriberError = null } = {})` requires the Block-2 Module Registry.
- `register(moduleId, capability) -> frozenProviderHandle` requires both non-empty strings and validates `moduleRegistry.getCapabilityProvider(capability) === moduleId` before any state change.
- Only one active runtime provider handle may exist for a capability at a time.
- A new provider starts with snapshot `{ capability, status: "unavailable", value: null, reason: null, provider: moduleId }`.
- Provider handle methods are `available(value)`, `unavailable(reason = null)`, `notConfigured(reason = null)`, `unregister()`.
- Every state update replaces the immutable snapshot and synchronously notifies current subscribers.
- `get(capability) -> frozenSnapshot` returns the active snapshot or an explicit synthetic `{ capability, status: "unavailable", value: null, reason: null, provider: null }` when no provider is active.
- `subscribe(capability, listener, { emitCurrent = true } = {}) -> unsubscribe` immediately emits `get(capability)` by default, then future changes; unsubscribe is idempotent.
- A throwing subscriber is isolated. If `onSubscriberError` is supplied, call it with `{ capability, error }`; remaining subscribers still receive the update.
- `unregister()` removes the provider only if the handle is still current, publishes one final synthetic `unavailable` snapshot to consumers, then invalidates that handle so stale handle calls return `false`.
- `destroy()` invalidates all handles, clears provider state and listeners.
- Capability Registry stores runtime data only; it does not import provider modules, inspect Home Assistant or dispatch actions.

- [ ] **Step 1: Write failing capability-registry tests**

Tests must prove:

- a manifest-declared provider can register and begins explicitly `unavailable`;
- `available(value)`, `unavailable(reason)` and `notConfigured(reason)` publish immutable snapshots;
- a module that is not the Module Registry declaration owner is rejected without partial runtime state;
- duplicate live registration for one capability is rejected;
- unresolved required capabilities elsewhere in Module Registry do not block provider registration or consumer subscription;
- default subscription immediately receives the current snapshot and unsubscribe stops later notifications;
- one throwing listener invokes `onSubscriberError` while another listener still receives the same update;
- provider unregister emits explicit synthetic `unavailable` with `provider: null`, removes stale available value and invalidates stale handle writes;
- `destroy()` leaves later `get()` calls explicitly unavailable and prevents old handles from republishing.

### Task 2: Action Registry and normalized dispatch

**Files:**
- Create: `custom_components/jamesui/frontend/core/action-registry.js`
- Create: `tests/jamesui-action-registry.test.js`

**Interfaces:**
- Export `ACTION_RESULT_STATUSES = Object.freeze(["success", "unavailable", "rejected", "error"])`.
- `createActionRegistry({ health = null } = {})` returns `register`, `unregister`, `has`, `execute`, `destroy`.
- `register(type, handler) -> unregister` requires a non-empty action type and function handler, rejects duplicate live providers and returns an idempotent unregister callback.
- `execute(action, context = Object.freeze({})) -> Promise<frozenResult>` accepts a plain action object containing non-empty string `type`.
- Missing/unregistered type returns `{ status: "unavailable", type, value: null, error: null }` without throwing.
- Malformed action input returns `rejected` without invoking any provider.
- A provider may return synchronously or asynchronously.
- A valid provider result contains one of the four statuses and may include `value`; the registry normalizes it to `{ status, type, value, error }`.
- Provider-thrown/rejected errors become `{ status: "error", type, value: null, error }` and never escape `execute()`.
- Provider results with an unknown/missing status become normalized `error` results with a `TypeError`.
- When Health Service is supplied, dispatch errors are reported under `action:<type>` and a later non-error result clears stale health for that type.
- `destroy()` unregisters all providers; later execution returns `unavailable`.
- The registry itself contains no `navigate`, URL or Home Assistant behavior.

- [ ] **Step 1: Write failing Action Registry tests**

Tests must prove:

- register/has/unregister lifecycle and duplicate rejection;
- malformed action object returns `rejected` and does not invoke a provider;

- sync and async providers normalize successful results;
- providers can explicitly return `rejected` and `unavailable`;
- thrown/rejected provider errors normalize to `error` and are written to `action:<type>` Health;
- malformed provider result normalizes to `error`;
- later success clears stale action health;
- fake handlers registered for `entity.toggle`, `ha.service` and `scene.activate` execute through the generic registry, proving these contracts require no raw HA code in Block 3;

**Files:**
- Create: `custom_components/jamesui/frontend/core/core-action-providers.js`
- Create: `tests/jamesui-core-actions.test.js`

**Interfaces:**
- `registerCoreActionProviders({ actions, router, openUrl } = {}) -> cleanup` registers exactly `navigate` and `url.open` and returns one cleanup callback that unregisters both.
- `navigate` action shape is `{ type: "navigate", route: <non-empty route id> }`.
- Valid route uses `router.navigate(route)` and returns `success`; unknown/invalid route returns `rejected` without throwing.
- `url.open` action shape is `{ type: "url.open", url: <absolute http/https URL> }`.
- Only `http:` and `https:` URLs are accepted in Block 3; malformed URLs or other schemes return `rejected`.
- `openUrl(url)` is injected and may be sync/async; false return means `rejected`, thrown/rejected errors are allowed to bubble only to the Action Registry where they normalize to `error`.
- No provider for `entity.toggle`, `ha.service` or `scene.activate` is registered here.

**Interfaces:**
- Module Loader `getContext` contract changes from zero-argument to `getContext({ id, manifest })`.
- `load(id)` calls `getContext({ id, manifest: record.manifest })` for `create(context, config)`.
- `update(id, nextConfig)` calls the same module-specific context factory again so updates receive current shared services plus the same immutable module identity.
- `createJamesUICore({ document, renderPage, openUrl } = {})` composes one Capability Registry and one Action Registry in addition to existing services.
- Default `openUrl` may delegate to browser `globalThis.open(url, "_blank", "noopener,noreferrer")` only when available; absence of a browser opener must cause `url.open` to normalize to `unavailable`/`rejected` rather than crash Core construction.
- Core registers the Task-3 `navigate`/`url.open` providers once and unregisters them on `core.destroy()`.
- Core exposes read-only `capabilities` and `actions` properties using the same non-writable pattern as existing Core services.
- Module context is frozen and contains exactly `events`, `overlays`, `capabilities`, `actions`, `module`.
- `module` is frozen `{ id, type, version }` derived from the loaded manifest.
- Module context must not expose `hass`, `narrow`, host `route`, `panel`, raw `router`, Health Service, Module Registry/Loader or future HA Adapter.
- `core.destroy()` order is: `moduleLoader.destroyAll()`, unregister Core action providers, `capabilities.destroy()`, `actions.destroy()`, then shell destroy. This lets loaded providers/widgets clean up their registry handles before registries themselves are destroyed.
