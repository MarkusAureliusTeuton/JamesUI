# JamesUI 1.0 Block 4 Home Assistant Adapter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Isolate all new JamesUI 1.0 Home Assistant runtime access behind one testable adapter and wire the three HA-backed Action Registry providers exclusively through that adapter.

**Architecture:** Add a dedicated `frontend/ha/` boundary. The adapter owns the raw `hass` object and exposes narrow state/query/subscription/service/WebSocket methods; Core receives `hass` from the Home Assistant panel and forwards it into the adapter. Only `provider` and `action` modules receive the adapter in module context; layouts/widgets remain HA-free and continue to use Capabilities/Actions. The existing production r11 panel bootstrap remains unchanged.

**Tech Stack:** Browser JavaScript ES modules, Node built-in test runner, Python `unittest` architecture guards, Home Assistant frontend `HomeAssistant`/WebSocket runtime APIs.

**Spec:** `docs/superpowers/specs/2026-10-02-jamesui-1.0-foundation-design.md`

## Global Constraints

- Variant B remains binding: JamesUI 1.0 is built in parallel; r11 stays production/reference until controlled cutover.
- All direct new-runtime Home Assistant access lives under `custom_components/jamesui/frontend/ha/`.
- Core, layouts and widgets must not read `hass.states`, call `hass.callService`, call `hass.callWS`, or use `connection.subscribeMessage` directly.
- Widgets consume Capabilities and execute Actions; layouts remain visual-only.
- Provider/action modules may receive the Home Assistant Adapter; layout/widget module contexts may not.
- Real `entity.toggle`, `ha.service`, `scene.activate` providers are introduced only through the adapter.
- `navigate` and `url.open` remain unchanged Core actions.
- Event Bus remains transient technical/UI/lifecycle infrastructure and is not a HA state/data channel.
- No Config Store, domain provider, visual, Start-page or production-bootstrap work belongs in Block 4.
- No monkey-patches, `Panel.prototype` overrides, version-specific polish files or compatibility shims.
- Intentionally red tests never go to `main`.

## Review Focus

1. **Missing/disconnected HA host:** reads return explicit empty/null state and commands fail as adapter-unavailable rather than dereferencing `hass`.
2. **State replacement/removal:** entity/domain subscribers react only to relevant object changes, additions or removals when Core receives a new `hass` snapshot.
3. **Subscriber/subscription cleanup:** one throwing local subscriber or one failing remote unsubscribe must not block other listeners/cleanup; destroy is idempotent.
4. **Action input safety:** malformed entity IDs, domains/services, `data`, `target` and scene transition inputs are rejected before any HA call.
5. **Architecture leakage:** layout/widget module contexts never receive the adapter or raw HA host values; raw HA access cannot spread back into Core.

### Task 1: Home Assistant Adapter host, state and connection model

**Files:**
- Create: `custom_components/jamesui/frontend/ha/home-assistant-adapter.js`
- Create: `tests/jamesui-home-assistant-adapter.test.js`

**Interfaces:**
- Produces `createHomeAssistantAdapter({ onSubscriberError = null } = {})`.
- Produces `HomeAssistantUnavailableError` for async operations attempted without an available/connected HA host.
- Adapter methods introduced in this task:
  - `setHass(hass)`
  - `connectionState()` → `"unavailable" | "connected" | "disconnected"`
  - `getState(entityId)` → HA state object or `null`
  - `entities(domain = null)` → current state objects, optionally filtered by exact domain prefix
  - `subscribeEntity(entityId, listener, { emitCurrent = true } = {})` → idempotent unsubscribe
  - `subscribeDomain(domain, listener, { emitCurrent = true } = {})` → idempotent unsubscribe
  - `subscribeConnection(listener, { emitCurrent = true } = {})` → idempotent unsubscribe
  - `destroy()`
- `setHass()` receives the panel-supplied HA object; local state subscribers are driven from successive HA object snapshots, not from Event Bus.
- `connectionState()` uses current HA availability and the official `hass.connected` flag when present; an older host with `connection` but no boolean `connected` is treated as connected for compatibility with the currently running panel environment.
- Entity/domain notifications compare previous/current state-object identity and also detect additions/removals.

### Task 2: Adapter commands, registries and WebSocket subscriptions

**Files:**
- Modify: `custom_components/jamesui/frontend/ha/home-assistant-adapter.js`
- Modify: `tests/jamesui-home-assistant-adapter.test.js`
- Create: `tests/helpers/fake-home-assistant-adapter.js`

**Interfaces:**
- Extends the adapter with:
  - `callService(domain, service, data = {}, target = undefined)`
  - `callWS(message)`
  - `subscribeMessage(listener, message, options = undefined)` → Promise of idempotent async unsubscribe
  - `listAreas()` → `callWS({ type: "config/area_registry/list" })`
  - `listDevices()` → `callWS({ type: "config/device_registry/list" })`
  - `listEntities()` → `callWS({ type: "config/entity_registry/list" })`
- `callService()` delegates to current HA `callService(domain, service, data, target)`.
- Generic WebSocket commands delegate to current HA `callWS(message)`; do not introduce direct `sendMessagePromise` usage in new runtime code.
- Streaming subscriptions delegate to `hass.connection.subscribeMessage(listener, message, options)` because that is the HA WebSocket subscription API.
- Commands/subscriptions reject with `HomeAssistantUnavailableError` while adapter state is `unavailable` or `disconnected`.
- Adapter tracks remote unsubscribe handles so `destroy()` attempts each active remote unsubscribe exactly once; one rejection must not prevent remaining cleanup.
- `tests/helpers/fake-home-assistant-adapter.js` provides a reusable fake with deterministic connection state, state storage, call logs and configurable command results/errors for later provider tests.

### Task 3: Real HA-backed Action Registry providers

**Files:**
- Create: `custom_components/jamesui/frontend/ha/ha-action-providers.js`
- Create: `tests/jamesui-ha-actions.test.js`
- Use: `tests/helpers/fake-home-assistant-adapter.js`

**Interfaces:**
- Produces `registerHomeAssistantActionProviders({ actions, homeAssistant } = {})` → idempotent cleanup.
- Registers exactly these three Block-4 action types:
  - `entity.toggle`
  - `ha.service`
  - `scene.activate`
- `entity.toggle` action shape: `{ type: "entity.toggle", entity_id: "domain.object" }`; implementation calls `homeAssistant.callService("homeassistant", "toggle", {}, { entity_id })`.
- `ha.service` action shape: `{ type: "ha.service", domain, service, data?, target? }`; `data` and `target` must be plain objects when supplied.
- `scene.activate` action shape: `{ type: "scene.activate", entity_id: "scene.object", transition? }`; optional transition must be a finite number `>= 0`; implementation calls `scene.turn_on` with target `{ entity_id }` and transition data only when supplied.
- Malformed action inputs return provider result `{ status: "rejected" }` without invoking the adapter.
- `HomeAssistantUnavailableError` maps to `{ status: "unavailable" }`.
- Other adapter errors are re-thrown so the existing Action Registry normalizes them to `error` and reports `action:<type>` health.
- Do not change `navigate` or `url.open` behavior.

  7. shell destroy
