# JamesUI 1.0 – Block 8 `layout.home-hero-deck` Design Specification

_Date: 2026-10-03_
_Status: design written; awaiting user review_

## 1. Purpose

Block 8 introduces the first real page-layout module for the clean JamesUI 1.0 runtime: `layout.home-hero-deck`.

Its only responsibility is to provide the structural and visual arrangement for the future Start page. It defines stable mount targets for later widgets while remaining completely independent of Home Assistant data, capabilities, actions and domain logic.

The visible r11 Start screen remains the product-direction reference. Its implementation, selectors and patch CSS are not reused.

Primary acceptance target remains the OnePlus Pad 2 in portrait inside the JamesUI shell. The layout must nevertheless degrade predictably on narrower containers without device-specific JavaScript.

## 2. Scope

Block 8 delivers:

- one reusable module with ID `layout.home-hero-deck`;
- exactly four named slots:
  - `hero`
  - `widget-left`
  - `widget-right-main`
  - `widget-right-footer`
- one upper hero region;
- one intentional lower widget deck surface;
- stable slot DOM nodes across layout updates;
- responsive layout behavior expressed through CSS only;
- lifecycle behavior compatible with the existing Module Loader contract;
- architecture and regression tests for the new layout boundary.

Block 8 does **not** deliver:

- weather, calendar, house or dynamic-button widgets;
- Home Assistant access;
- capability consumption;
- action dispatch;
- Alpine scene/background selection;
- Start-page configuration loading;
- widget instance loading or mounting;
- a production bootstrap cutover;
- changes to the r11 production implementation.

Those concerns remain in later roadmap blocks.

## 3. Module location and identity

The module lives below a dedicated module namespace rather than Core:

```text
custom_components/jamesui/frontend/modules/layout.home-hero-deck/
  manifest.js
  index.js
  styles.js
```

The manifest is exported as ordinary JavaScript data so it can be validated by the existing Module Registry/manifest contract without introducing a second manifest format.

Canonical manifest values:

```js
{
  id: "layout.home-hero-deck",
  type: "layout",
  version: "1.0.0",
  core_api: "1.x",
  depends_on: [],
  requires_capabilities: [],
  provides_capabilities: [],
  config_schema: "layout.home-hero-deck/v1"
}
```

The layout has no concrete module dependencies and no capability dependencies.

## 4. Lifecycle contract

`index.js` exports the standard module factory:

```text
create(context, config)
  -> { mount(target), update(nextContext, nextConfig), destroy(), getSlot(name), listSlots() }
```

The layout must remain synchronous and side-effect-free outside its own target DOM.

### `create(context, config)`

- accepts the standard layout/widget module context already defined by Core;
- does not read Home Assistant, Config Service, capabilities or actions;
- validates only the small Block-8 layout configuration described in this spec;
- creates no persistent browser/global state.

### `mount(target)`

- creates exactly one layout root inside `target`;
- creates the four canonical slot nodes exactly once for that mount;
- applies the layout-owned root marker and class/data attributes;
- installs only layout-local styles needed by this module;
- returns or exposes no domain-specific content.

A repeated `mount()` after a previous mount must not leak the old DOM. The implementation may destroy/remount its own root when explicitly mounted again, but one mount must never result in duplicate roots or duplicate style elements.

### `update(nextContext, nextConfig)`

- validates and applies layout-only configuration;
- must **not replace the four slot nodes**;
- must not clear slot contents;
- must not remount future widgets indirectly;
- must not create subscriptions or timers.

Slot-node identity across `update()` is a required contract because later widget modules will be mounted into those nodes.

### `destroy()`

- removes the layout-owned root/style state;
- detaches only DOM owned by the layout;
- performs no action against child module lifecycle because Block 8 does not own/load widgets;
- is idempotent.

Later composition code is responsible for destroying any mounted child widgets before destroying/remounting the layout itself. Block 8 does not create an implicit child-module manager.

Widget lifecycle orchestration remains a later page/config composition concern.

## 5. Slot API

The layout exposes stable slot targets through an explicit lifecycle-local API rather than requiring callers to know CSS selectors.

The created layout instance provides:

```text
getSlot(name) -> Element | null
listSlots() -> readonly [
  "hero",
  "widget-left",
  "widget-right-main",
  "widget-right-footer"
]
```

`getSlot()` returns the current mounted slot element or `null` when the layout is not mounted/destroyed or when the name is unknown.

The slot names are permanent semantic contracts for the initial Start-page composition. Later widgets are assigned by page/configuration logic; the layout never hard-codes widget IDs.

Each slot node carries a stable DOM marker:

```text
data-jui-layout-slot="hero"
data-jui-layout-slot="widget-left"
data-jui-layout-slot="widget-right-main"
data-jui-layout-slot="widget-right-footer"
```

The layout root carries:

```text
data-jui-layout="home-hero-deck"
```

These markers are test/debug hooks, not a substitute for `getSlot()` in runtime orchestration.

## 6. Structural hierarchy

The DOM hierarchy is intentionally small:

```text
layout root
├─ hero region
│  └─ slot: hero
└─ deck surface
   ├─ left region
   │  └─ slot: widget-left
   └─ right region
      ├─ slot: widget-right-main
      └─ slot: widget-right-footer
```

The deck surface is one visual surface. `widget-left`, `widget-right-main` and `widget-right-footer` do not become independent card surfaces at layout level. Individual future widgets may choose their own internal presentation when their blocks are designed.

The old labels `Home`, `HEUTE & DANACH` and `ZUHAUSE` are not part of this layout.

## 7. Visual geometry

### Primary portrait composition

The layout fills the available page-region height rather than the physical viewport directly so the persistent shell/navigation remains the outer owner.

The composition has two vertical layers:

1. **Hero** – default ratio `0.42` of the available layout height.
2. **Deck** – starts with a restrained negative overlap into the hero and then occupies the remaining available height down to the page-region bottom.

The configurable hero range remains 35–50%; the 0.42 default represents the approved 40–45% portrait direction.

The exact geometry is token-/CSS-driven, not hard-coded to one OnePlus pixel resolution.

The layout root must support a minimum-height contract suitable for the shell page region and must not create its own viewport-fixed navigation assumptions.

### Deck appearance

The deck reflects the approved Start direction:

- one continuous dark/translucent surface;
- rounded upper corners;
- square lower corners;
- subtle warm highlight/shimmer at the upper edge;
- restrained blur/gradient treatment;
- no `!important`;
- no release-specific override layer;
- no copied r11 positional selectors.

All palette, spacing, radius, blur and motion values must come from Block-6 `--jui-*` tokens. If Block 8 genuinely needs one reusable layout token not expressible from the existing scale, it may be added centrally to `tokens.js`; raw duplicate palette values inside the module are forbidden.

The layout does not select or render an Alpine image. A future weather/background owner may place imagery behind or inside the hero without changing the slot contract.

## 8. Deck grid

On the primary portrait width, the deck uses a two-column CSS Grid:

```text
┌──────────────────────────────────┐
│ widget-left     │ widget-right-main   │
│                 │                     │
│                 ├─────────────────────┤
│                 │ widget-right-footer │
└──────────────────────────────────┘
```

Rules:

- left and right regions are intentionally balanced but not required to be exactly 50/50;
- the right side is a vertical grid/stack where `widget-right-main` receives the flexible main area and `widget-right-footer` remains content-sized or bounded;
- gaps consume the shared spacing scale;
- the deck may grow vertically if later widget content requires more than the initial viewport, allowing page-region scrolling rather than clipping or overlaying content.

Block 8 must not encode knowledge such as “calendar needs this width” or “four scene buttons need this height”. Those assumptions belong to the later widget/composition blocks.

## 9. Responsive behavior

Responsiveness is CSS-only. No `window.innerWidth`, resize listener, device sniffing or Home Assistant `narrow` flag is introduced.

The layout root establishes an inline-size CSS containment context. At the canonical local breakpoint:

```text
@container (max-width: 44rem)
```

the deck changes from two columns to one column in this exact semantic order:

1. `widget-left`
2. `widget-right-main`
3. `widget-right-footer`

The `hero` remains first and independent above the deck.

No slot is hidden at the narrow breakpoint.

The breakpoint is based on the layout container, not a named device or global viewport width. Its purpose is to prevent unusably narrow widget columns.

## 10. Configuration

Block 8 keeps layout configuration intentionally small.

Version-1 accepted configuration:

```js
{
  hero_ratio?: number
}
```

Rules:

- omitted `hero_ratio` uses exactly `0.42`;
- accepted range: `0.35` through `0.50` inclusive;
- invalid/non-finite values are rejected explicitly;
- the value changes only the hero/deck vertical geometry through a layout-owned CSS custom property;
- it must not change slot count, names, identity or semantic order.

No device-specific width, widget ID, entity ID, image, color, arbitrary CSS or pixel-position configuration is accepted in Block 8.

This small setting gives later page configuration a controlled geometry adjustment without turning the layout into a free-form CSS engine.

## 11. Styling ownership

`styles.js` owns only selectors scoped below:

```text
[data-jui-layout="home-hero-deck"]
```

It may style layout-owned structural descendants and slot containers but may not target future widget module IDs/classes.

Forbidden inside the Block-8 module:

- raw Home Assistant selectors;
- `.jamesui-home*` legacy selectors;
- `Panel.prototype` or legacy runtime hooks;
- `!important`;
- inline/data-URL SVG;
- external URLs;
- `fetch()` or runtime asset loading;
- domain terms such as weather entity IDs, calendar entities, lights, scenes or media players;
- global document/body selectors.

## 12. Core and Module Loader integration

Block 8 does not add Start-specific code to Core.

The existing Module Registry and Module Loader remain the module lifecycle owners. The Block-8 module is built so it can be registered/loaded through those contracts.

Block 8 does **not** yet make the Core shell automatically render the module on the `home` route. The current placeholder renderer may remain until a later composition step has enough real modules/configuration to build the new Start page coherently.

This prevents a temporary half-built Start page from becoming another production/reference branch inside Core.

Tests may load/mount the layout through a fake/real Module Registry + Loader to prove compatibility.

## 13. Error behavior

The layout contains no data provider and therefore has no unavailable-data state.

Errors are limited to:

- invalid configuration → `create()`/`update()` throws a clear `TypeError` or range error;
- invalid mount target → `mount()` throws a clear error;
- unknown slot name → `getSlot()` returns `null` rather than inventing a fallback;
- calls after `destroy()` behave predictably and do not retain stale slot nodes.

When loaded through the Module Loader, existing loader error isolation/health reporting remains responsible for catching lifecycle errors.

## 14. Testing strategy

Block-8 tests target contracts rather than a pixel-perfect screenshot.

Required tests:

### Manifest / loader compatibility

- manifest validates as type `layout`;
- no dependencies or capabilities are declared;
- the module can be loaded, mounted, updated, destroyed and reloaded by the existing Module Loader test harness.

### Slot contract

- exactly four slot names exist;
- exactly one DOM node is created per slot;
- `getSlot()` resolves the correct mounted node;
- unknown slots return `null`;
- slot identity remains unchanged across `update()`;
- slot children survive an `update()`;
- destroy invalidates slot lookups and removes layout-owned DOM;
- remount creates a fresh set with no leaked previous nodes.

### Configuration

- omitted configuration uses exactly `0.42`;
- valid boundary values `0.35` and `0.50` are accepted;
- NaN/infinite/string/out-of-range values are rejected;
- update changes the geometry property but not slot identity.

### CSS / architecture

- root-scoped layout CSS only;
- four slot selectors/markers exist;
- two-column deck + `44rem` container-query single-column semantic order is encoded;
- upper-corner-only deck rounding is preserved;
- no forbidden raw palette/legacy/HA/fetch/`!important` patterns;
- design tokens are consumed instead of redefining palette/spacing systems;
- no r11 production file or existing asset changes.

### Regression

The full `Validate JamesUI` suite remains green, including Blocks 0–7 and all retained r11 regressions.

## 15. Review focus before merge

Whole-branch review must explicitly verify:

1. **Slot identity:** `update()` cannot accidentally replace or clear a mounted widget target.
2. **Layout-only boundary:** no widget/domain/HA logic slipped into the layout.
3. **Responsive order:** narrow mode preserves all four semantic slots and deterministic order.
4. **Surface ownership:** deck is one intentional surface; Block 8 does not pre-design future widgets as cards.
5. **Core containment:** Start-specific markup is not introduced into Core or the production r11 bootstrap.

Critical/Important findings require RED → GREEN fixes before merge.

## 16. Exit criteria

Block 8 is complete only when:

- `layout.home-hero-deck` exists as a valid `layout` module;
- the four canonical slot IDs are stable and exposed through the instance API;
- slot DOM identity survives configuration updates;
- default `hero_ratio` is `0.42` with the bounded 0.35–0.50 contract;
- the hero/deck geometry follows the approved Start direction without fixed-device JS;
- the deck is one continuous visual surface with rounded top and square bottom;
- primary deck layout is two-column with the exact `44rem` container-query fallback order;
- all visual values use the shared design system;
- the layout has no HA/capability/action/domain/widget dependency;
- Module Loader lifecycle/error isolation remains compatible;
- no production route/bootstrap cutover occurs;
- r11 production/reference implementation remains unchanged;
- branch and merged-main CI are green.

## 17. Deferred work

Explicitly deferred:

- Block 9: weather provider/capabilities;
- Block 10: Weather Today hero widget + forecast overlay;
- Block 11: Calendar Agenda widget/provider;
- Block 12: House Quick widget/providers;
- Block 13: Dynamic Buttons;

Block 8 therefore establishes the spatial contract future Start modules depend on without creating any temporary business-logic shortcut.
