# JamesUI 1.0 – Block 14 Start Configuration Experience Design

_Date: 2026-10-09_  
_Status: approved conversational product design; technical implementation planning pending_

## 1. Scope and target

Deliver the first usable clean JamesUI 1.0 Start dashboard on OnePlus Pad 2 portrait via Fully, plus generic page/layout/widget instance orchestration and an on-page grid editor. Home Assistant remains authoritative, Fully merely the kiosk shell. r11 stays the production reference through the separately gated early cutover. Do not migrate Haus/Medien/Klima/Tür in Block 14.

Roadmap execution order approved: **14 → 19 → 20 → 21 → 15 → 16 → 17 → 18**. Block 14 prepares the Start-first release; Block 19 checks readiness, Block 20 switches production, Block 21 deletes legacy, secondary page migrations follow.

## 2. Page layouts and navigation

- Persistent bottom navigation is independent of page layout and always fixed.
- Layout types: a **hero + content** layout, and a **fullscreen content** layout with no hero. These are layout configurations, not route-specific hacks.
- The hero, when present, is a fixed structural layout region, not a draggable grid element. Default hero height **42%** of the available page region, configured per page within **35–50%**.
- The primary Start content layout is `fixed`: its normal view must fit the true available viewport above navigation and must not vertically scroll the page. A separate layout may choose `vertical` and own page scrolling; the Core must not assign scroll policy based on route.
- In hero layouts the lower deck is a visually continuous translucent surface: rounded upper corners, **no visible bottom border, bottom corner or floor**; it visually extends behind the fixed foreground navigation. The actual interactive content stays within the unobscured area above navigation.
- No hardcoded left/right content split. Existing Block-8 `layout.home-hero-deck` slots (`widget-left`, `widget-right-main`, `widget-right-footer`) must evolve into a generic free content region inside the existing layout architecture, not a parallel implementation. Preserve hero semantics and update the official layout contract/tests accordingly.

## 3. Shared logical grid

- Each configurable content region uses **12 logical columns**, not independent fixed left/right columns.
- Horizontal and vertical placement is grid-aligned; no arbitrary absolute pixel coordinates.
- Grid rows have a **fixed logical row height within one layout instance**. The numerical CSS-pixel value and gaps are **not yet approved**: derive a suitable readable/touch-safe design from actual OnePlus/Fully CSS viewport, design tokens and widget/button minimum sizes, then verify visually on the tablet.
- Element geometry persists as integer `column`, `row`, `column_span`, `row_span` (exact field names to be finalized in plan), with explicit bounds and collision validation.
- User-chosen gaps remain gaps; no automatic compaction or arbitrary reorder on render/load.
- Readability/touch targets have priority over maximum density: never shrink controls below effective usable minimums to force all items onto Start. Additional configured dashboard pages are the overflow strategy, not silently hidden or clipped widgets.
- Element internal content (e.g. Agenda rows and its internal scroll) remains independent of outer grid layout, and must measure the host allocation.
- Block 13's `compact | normal | wide` sizing classes and its CSS width minima (128/168/260 px) are implementation lower bounds, **not approved aesthetic targets**. Physical look/comfort must be assessed on the real tablet.

## 4. Dashboard elements

- Each widget is a single independently placed/resizable element. Widgets may use any internal layout, including their own lists/grids; they respect allocated outer bounds and support their contracted internal scrolling.
- Dynamic Buttons are independently placeable **first-class grid elements**, not required to be in one aggregate widget. Retain central `dynamic_buttons` definitions, normalized `control.states` feedback, generic Action Registry execution and Block-13 state machines. Reuse the existing runtime logic or carefully refactor its implementation boundary to support independent mounts; no duplicate control state machine, bypass actions, or permanent compatibility shim.
- `widget.dynamic-buttons` may remain a supported composition where appropriate, but is no longer the mandatory Start placement primitive. Central definition and per-occurrence presentation/state isolation survive.
- Agenda, House Quick, Weather Today and individual buttons must be configurable as instances, including multiple independent occurrences of the same widget module across pages.
- Future optional organizational elements: headings, dividers, groups/containers. The element model/registry must be extensible, but fully featured grouping need not be implemented in Block 14.
- The weather hero uses `widget.weather-today`; widget/calendar/tasks and House Quick must consume their completed providers and contracts, never raw `hass`.

## 5. In-place edit experience

- Long-press on a widget/button enters the page edit mode, and supports drag to reposition. Normal short-press remains the regular action only outside editing.
- Editing shows a subtle grid overlay and selected element frame. Resize handles allow changing both spans subject to minimum bounds.
- Position and resize previews update before release; write the committed new layout only upon completed action, not for each pointer move.
- Collision handling is **local push/reflow**: only directly affected neighbors move, while sizes, purposeful gaps, relative structure and later group integrity are preserved. Avoid chains that disrupt unrelated sections. Reject an impossible operation with a clear preview and leave persisted positions unchanged.
- Support **Undo** for the previous editing change (implementation may use an edit-session history).
- Editing element context menu includes configuration, duplication, removal.
- A `+ Hinzufügen` control opens an element catalog; selecting an available widget or single button enables per-instance setup and placement. Multiple instances are supported. New organizational element kinds can be registered later.
- An explicit `Fertig` completes editing. Navigation stays fixed throughout editing. Provide accessible non-drag affordances appropriate for tablet input; avoid conflict between long-press and provider widgets' short-press actions.

## 6. Configuration and runtime boundaries

- Persist in the existing HA-backed `jamesui.config` Config Store, schema v1 root sections `pages`, `layouts`, `widget_instances`, `dynamic_buttons`, `data_sources`, `module_settings`. Extend validated nested shape as needed; never create a separate unversioned persistence silo.
- Per page: layout ID/type, hero ratio where applicable, scroll policy, ordered element/instance refs. Per element: stable instance ID, module/button definition ID, grid geometry, local settings and bindings.
- Core continues to own Config Service, Module Registry/Loader, routing and shell; provider/widget contract receives only approved capability/action/event/overlay/module context. HA access remains behind HA Adapter.
- The current Module Loader caches module runtimes by module ID; Block 14 must evolve the **single canonical Loader** to support distinct instance IDs for one module definition. Verify lifecycle isolation, errors, update, unload/reload, subscriptions, and configuration changes without breaking existing provider/action semantics.
- Config loading, validation and saving must be atomic/consistent. Invalid input, unavailable providers, stale results or missing references must not crash the page or invent data. Disabled configuration dependencies must be understandable.
- Preserve no-monkey-patch/no-prototype-override/no-duplicated-architecture/no-long-lived-shim rules.

## 7. Visible default Start composition

Hero + content is the primary default Start layout: weather/date/time above, lower dark deck with independently placed Agenda, House Quick and configured Dynamic Buttons. No forced left/right split and no predetermined button count. Initial default geometry is only finalized after fitting actual widget minimums to measured tablet viewport and user review; do not hardcode speculative CSS positions. Bottom navigation follows the agreed `Start | Haus | Klima | Medien | Tür` visual language, but routes without migrated functionality must not falsely indicate readiness during the early 1.0 cutover.

## 8. Acceptance gates

1. New Start composition renders on actual **OnePlus Pad 2 portrait / Fully** viewport (record measured CSS viewport, nav occupancy, effective content size, screenshot/explicit user visual acceptance). Mockups and synthetic fake DOM tests do not substitute device acceptance.
2. Normal Start has no page-level vertical scroll; widgets do not clip or disappear behind the bottom navigation. Deck appears visually open at bottom.
3. Buttons look like comfortably usable house controls, not tiny mobile icons; labels and state feedback are readable.
4. Hero ratio and fullscreen variation work and share fixed navigation.
5. Generic loader supports true multiple instances of a widget with independent configuration, lifecycle and transient state.
6. Add, configure, drag, resize, duplicate, remove, undo, finish and reload/persist work. Collisions protect layout; deliberate empty cells remain empty.
7. Calendar/task, House Quick, Weather and Dynamic Button actions respect existing provider/action boundaries and correct truthful unavailable behavior.
8. Full unit/integration/architecture regression gates pass on unchanged implementation head; branch reviewed before merge and main CI checked afterwards.
9. No early production switch or r11 code modification in this block.

## 9. Explicit exclusions and future gates

- Block 14 does **not** implement complete Haus/Media/Climate/Door pages, production cutover, or legacy deletion.
- Early release cutover blocks 19–21 immediately follow Block 14; must confirm no fake/unusable route, documented rollback and successful real device acceptance before removing r11.
- Block 15–18 then build their pages on clean production JamesUI 1.0.
- Organizational groups and additional layout families can expand later through registered element/layout contracts rather than being implemented speculatively now.
