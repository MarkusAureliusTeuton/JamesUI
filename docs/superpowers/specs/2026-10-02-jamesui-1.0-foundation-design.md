# JamesUI 1.0 – Foundation Architecture

_Status: approved architecture direction (Variant B: clean foundation + controlled cutover)_
_Date: 2026-10-02_

## 1. Purpose

JamesUI is the permanent wall-tablet interface for the home. It runs on the OnePlus Pad 2, normally inside Fully, and should make important information visible at a glance while exposing frequently used KNX/Home Assistant functions immediately and deeper device controls when needed.

The application must remain easy to extend as more functions are added, including lighting, sockets, shutters, ventilation schedules, heating modes, appliance status and update actions, media control, door/camera functions and future energy functions.

The existing r11 UI is useful as a design reference, but the current frontend structure must not become the long-term architecture.

## 2. Decision

We will use **Variant B: build a clean modular JamesUI 1.0 foundation in parallel, port only the desired behavior, then perform one controlled cutover and delete the old implementation.**

The existing r11 code remains the visible/reference implementation until the replacement reaches the cutover gate. It is not the architectural basis for new functionality.

No new feature should be added to the old r11 architecture unless it is required as a critical bug fix before cutover.

## 3. Current debt that motivates the rebuild

The audit of `main` found several structural problems:

- `jamesui-panel.js` is a monolithic file that owns app shell, navigation, weather helpers, old Start markup, Haus, Klima demo content, Media logic, settings, overlays, display calibration and a large global CSS block.
- The old Start implementation still exists in `jamesui-panel.js`, while `jamesui-home.js` replaces `_homePage()` later at runtime.
- `jamesui-home-background.js` wraps existing panel methods and rewrites already-rendered HTML to apply background behavior.
- `jamesui-home-data.js` wraps `render()` and lifecycle methods to add calendar/scenes/runtime behavior.
- `jamesui-v11-polish.js` adds another CSS override layer with `!important`, data-URL SVGs and positional styling rules.
- The UI currently mixes Unicode icons, inline SVGs, data-URL SVGs and legacy weather SVG assets.
- The Python config API is a flat collection of unrelated keys and cannot scale cleanly to pages, layouts, widget instances, dynamic buttons and module-specific settings.
- Klima still contains hard-coded demo rooms and temperatures.
- Doorbell demo and other prototype behavior remain inside the production shell.
- Frontend revisioning is global, so any UI change invalidates the whole frontend bundle.

These patterns are acceptable during exploration but are not acceptable as the permanent platform.

## 4. Architectural principles

JamesUI 1.0 must follow these rules:

1. **One owner per responsibility.** A function is implemented in one module only.
2. **No runtime monkey-patching.** Modules may not overwrite `Panel.prototype`, wrap foreign render methods or regex-edit rendered HTML.
3. **Core is small.** Weather, Calendar, Media, Haus logic and device-specific behavior are not Core concerns.
4. **Pages are configuration.** A page selects a layout and assigns widgets to layout slots.
5. **Layouts do not know Home Assistant.** They only arrange slots.
6. **Widgets consume capabilities.** They do not directly discover unrelated entities or call arbitrary internal methods.
7. **Actions are providers.** Widgets request an action through a registered action type rather than hard-coding service execution.
8. **Data providers own subscriptions.** Rendering must not create hidden subscription side effects.
9. **Design is centralized.** Typography, colors, spacing, radii, shadows, motion and icon style come from one design system.
10. **Configuration is versioned.** Schema changes use explicit migrations; obsolete fields are removed after migration.
11. **Modules are independently versioned.** Frontend modules can be cache-busted/reloaded individually where technically possible.
12. **Git is the archive.** Old implementations are deleted after cutover; no `legacy`, `old`, `v9`, `v11-final` production copies remain.

## 6. Core responsibilities

The Core owns only cross-application infrastructure:

- Home Assistant connection handoff
- persistent application shell
- fixed bottom navigation
- route/page selection
- module registry and module loader
- capability registry
- action registry
- versioned configuration service
- overlay/dialog service
- shared event bus
- asset/icon registry
- shared design tokens and base components
- local device/display settings
- module health/error reporting

The Core must not contain:

- weather entity selection rules
- calendar subscriptions
- KNX domain-specific grouping
- Onkyo or Spotify rules
- climate room logic
- doorbell-specific logic
- page-specific visual markup

## 7. Module contract

Every module has a manifest with at least:

```json
{
  "id": "widget.weather-today",
  "type": "widget",
  "version": "1.0.0",
  "core_api": "1.x",
  "requires": ["weather.current", "weather.daily"],
  "provides": [],
  "config_schema": "weather-today.schema.json"
}
```

Module types initially supported:

- `layout`
- `widget`
- `provider`
- `action`
- `page-extension` only when a future use case proves necessary

Every frontend module follows a predictable lifecycle:

- `create(context, config)`
- `mount(target)`
- `update(nextContext, nextConfig)`
- `destroy()`

A module must clean up all event listeners, timers and subscriptions in `destroy()`.

## 8. Module registry and loader

The Module Registry stores the active manifest for every module and validates:

- unique module ID
- supported module type
- compatible Core API version
- dependency availability
- capability availability
- configuration schema compatibility

The loader imports modules by module-specific version token, for example:

```text
/jamesui_static/modules/weather-today/index.js?v=1.3.1
```

Changing one frontend widget should therefore not require changing the version token of unrelated modules.

A Core update still requires a full page reload. Python/backend integration changes may still require Home Assistant integration reload/restart depending on the Home Assistant lifecycle.

## 9. Capability registry

Data and control features are published as named capabilities instead of private panel methods.

Initial examples:

```text
weather.current
weather.daily
weather.hourly
calendar.events
house.lights
house.outlets
house.windows
house.doors
house.ventilation
climate.rooms
media.playback
```

A provider registers a capability implementation. Widgets declare capabilities they require.

When a capability is unavailable, the widget must receive an explicit unavailable/not-configured state rather than failing implicitly.

## 10. Action registry

Interactive UI elements use registered action types. Initial action types:

- `entity.toggle`
- `ha.service`
- `scene.activate`
- `navigate`
- `url.open`

An action is configured as data and executed through the Action Registry. Widgets do not directly call unrelated Home Assistant services.

Action execution returns a normalized result:

```text
success | unavailable | rejected | error
```

The Core handles common feedback and logging; a widget can optionally show contextual feedback.

## 11. Home Assistant adapter

All direct Home Assistant interaction is isolated behind a dedicated adapter.

It provides narrow services such as:

- state lookup/subscription
- registry access
- WebSocket command execution
- service calls
- entity/domain queries
- Home Assistant connection state

Providers may use the adapter. Layouts may not.

This boundary allows provider tests to use a fake adapter without a real Home Assistant runtime.

## 12. Configuration model

JamesUI configuration moves from a flat list of `config_entry.options` fields to a versioned structured store.

Top-level model:

```json
{
  "schema_version": 1,
  "pages": {},
  "layouts": {},
  "widget_instances": {},
  "dynamic_buttons": {},
  "data_sources": {},
  "module_settings": {}
}
```

Display-specific calibration that belongs to one physical browser/tablet remains local device storage and is not part of the shared home configuration.

Each schema version has an explicit migration to the next version. Migration code is tested. Once migration has completed, obsolete keys are not retained as permanent compatibility fields.

## 13. Page and layout model

The persistent bottom navigation initially remains:

```text
Start | Haus | Klima | Medien | Tür
```

Each page references one layout instance. A layout only defines visual slots.

The Start page uses a `layout.home-hero-deck` layout with slots such as:

```text
hero
widget-left
widget-right-main
widget-right-footer
```

Initial Start assignment:

```text
hero               → widget.weather-today
widget-left        → widget.calendar-agenda
widget-right-main  → widget.house-quick
widget-right-footer→ widget.dynamic-buttons
```

Future pages can use other layouts without rewriting the widgets.

## 14. Design system

JamesUI 1.0 has one shared token system for:

- background/surface colors
- champagne accent
- text/status colors
- type scale and weights
- spacing scale
- radii
- borders/highlights
- shadows
- blur
- motion durations/easing
- icon sizing

No version-specific CSS patch layers are allowed.

Widget-specific styles may exist inside the widget, but they must consume shared design tokens rather than redefining the application palette and typography.

## 16. Dynamic buttons

Dynamic buttons are a reusable widget/content model, not a special scene implementation.

A button stores visual presentation and one action definition, for example:

```json
{
  "id": "arrive",
  "label": "Ankommen",
  "icon": "home-arrive",
  "icon_color": "#e7c18d",
  "text_color": "#ffffff",
  "background": "arrive-warm",
  "action": {
    "type": "scene.activate",
    "target": "scene.ankommen"
  }
}
```

User-configurable fields:

- text
- icon
- icon color
- background from the local background library
- text color
- action type
- action target / URL / navigation destination / service data as appropriate

The initial preset library includes the visual templates:

- Ankommen
- Abend
- Kino
- Alles aus

Presets are presentation templates only. They do not pretend that a matching Home Assistant action exists until the user assigns one.

The Start dynamic-button widget receives four configured button IDs manually.

## 17. House quick controls

The house status area uses the same visual component language as dynamic buttons but with a status source plus an action.

Initial categories:

- Licht
- Steckdosen
- Fenster
- Türen/Tore
- Lüftung
- Klima
- Medien

Examples:

```text
Licht        2 an       → navigate Haus/Licht or configured quick action
Fenster      Alle zu    → navigate Haus/Fenster
Lüftung      Auto       → navigate detail or configured action
```

Status aggregation belongs to house capability providers, not the Start widget.

## 18. Calendar

Calendar is split into:

- `provider.calendar` – owns Home Assistant calendar discovery/subscriptions/normalization
- `widget.calendar-agenda` – displays the configured subset

Widget settings include:

- selected calendars
- visible item count
- date range
- include/exclude all-day events
- optional calendar-color presentation

The current event normalization logic may be ported if it still fits the provider contract.

## 19. Weather and Start hero

The visible r11 hero is the design reference, not the code reference.

Required information on Start:

- weekday/date
- large current time
- current outdoor temperature
- current condition
- daily maximum
- nightly/daily minimum
- rain probability and, when supported by real granular data, expected first rain time
- strong wind/storm relevance
- snow relevance
- sunrise
- sunset
- moon phase / illumination
- Alpine background selected by weather + sun period

The normal Start layout has no visible 3-day-forecast row. Tapping the large current temperature opens the forecast overlay without moving or expanding the page layout.

## 20. Start widget deck

The lower Start region becomes one intentional surface:

- begins at the current approved visual overlap position below the hero
- extends vertically to the persistent bottom navigation
- rounded upper corners
- square lower corners
- subtle translucent/dark gradient inspired by the approved mockup
- fine warm shimmer/highlight along the upper edge
- Alpine image can continue subtly behind the surface near the transition

The labels `Home`, `HEUTE & DANACH` and `ZUHAUSE` are removed.

## 21. Error isolation

A failing module must not crash the whole application.

The loader catches initialization errors and replaces the affected slot with a small module-error state containing:

- module ID
- readable status
- optional retry action

The Module Registry records module health for diagnostics.

Provider failure marks the corresponding capability unavailable; consumers update accordingly.

## 22. Testing strategy

Tests target contracts and behavior rather than release-specific CSS patches.

Required layers:

### Core tests
- registry validation
- module dependency resolution
- module lifecycle cleanup
- routing
- action dispatch
- capability availability
- config schema/migrations

### Provider tests
- Home Assistant adapter fakes
- subscription cleanup
- normalization behavior
- unavailable/error handling

### Widget tests
- mount/update/destroy
- rendering for available/unavailable/empty states
- configured actions

### Architecture checks
CI must reject:

- production `Panel.prototype` monkey-patches outside the legacy implementation before cutover and anywhere after cutover
- release-version names such as `v9`, `v10`, `v11` in new production module paths
- demo device/temperature data in production code
- layout modules calling Home Assistant services directly
- modules missing manifests or version metadata
- stale/unreferenced production assets after cutover

### Visual/runtime tests
- OnePlus Pad 2 portrait remains the primary acceptance viewport
- Fully/browser screenshot verification is required at major UI milestones

## 23. Migration and cutover strategy

We do not rewrite all features at once.

1. Build the new Core and module infrastructure in parallel.
2. Build the new Start page on that infrastructure.
3. Build new configuration UI for Start and dynamic buttons.
4. Port required Haus functions.
5. Port useful Media logic.
6. Replace Klima demo with real climate behavior.
7. Replace Tür demo with real integrations when available.
8. Pass the cutover gate.
9. Switch the Home Assistant panel bootstrap to the new Core.
10. Delete the old implementation and old patch-specific tests/assets in the same migration phase.

The repository history remains available through Git; no legacy source copy remains in production directories.

## 24. Code to retain conceptually vs delete

### Reuse/port when appropriate
- guarded Home Assistant bootstrap/Shadow-DOM property handling
- Alpine WebP asset family
- good weather normalization/calculation logic
- useful calendar normalization logic
- proven entity classification rules
- display calibration concept as a separate device-settings module
- WebP integrity tests
- useful Media integration knowledge

### Delete at cutover
- monolithic old `jamesui-panel.js`
- old `_homePage()` implementation
- `jamesui-home-entry.js`
- `jamesui-home.js`
- `jamesui-home-data.js`
- `jamesui-home-background.js`
- `jamesui-v11-polish.js`
- legacy weather SVG family no longer used by the new architecture
- Klima demo rooms/temperatures
- doorbell UI demo
- version-patch-specific tests superseded by contract tests

## 25. Cutover acceptance criteria

The old frontend may be removed only when:

1. the new Core loads reliably through Home Assistant and Fully/browser,
2. persistent bottom navigation is stable,
3. Start hero provides the agreed weather information,
4. forecast opens from the temperature without layout shift,
5. Calendar works through its provider,
6. House Quick uses real capabilities,
7. Dynamic Buttons can be created/configured/assigned and execute real actions,
8. design tokens and new icon library are active,
9. configuration store and migrations are tested,
10. module errors are isolated,
11. primary OnePlus portrait layout is visually accepted,
12. CI architecture gates are green.

After cutover there must be exactly one production implementation for each of these concerns.

## 26. Non-goals for the Foundation phase

The Foundation rebuild does not need to complete every future home feature before the new architecture is considered valid.

The first goal is a clean platform plus the complete Start experience. Detailed WC fan schedules, full heating programming, appliance update flows and advanced shutter automation are later modules built on the same interfaces.

## 27. Execution model

Implementation is performed in numbered blocks. Each block has its own detailed implementation plan, branch, tests and exit criteria. A block is completed and merged before beginning the next dependent block unless the roadmap explicitly permits safe parallel work.
