# JamesUI 1.0 – Block 13 Dynamic Buttons Design

_Date: 2026-10-09_  
_Status: approved conversational design; written specification_

## 1. Purpose

Block 13 introduces a reusable `widget.dynamic-buttons` module for configurable household actions on the clean JamesUI 1.0 architecture.

Dynamic Buttons are not part of House Quick. They are a separate widget family for actions such as scenes, switches, garage-door commands, one-shot commands, navigation and future registered actions.

The module must support both:

- **stateful toggles** with an independent real feedback signal; and
- **stateless triggers** with short execution feedback only.

The actual automation logic remains outside JamesUI. A scene, garage door or other function may be controlled by Home Assistant, KNX, a SmartVisu/JUNG server or another system. JamesUI sends a configured action and, where applicable, consumes one externally prepared feedback signal that represents the real state.

Success means:

- user commands run only through the Action Registry;
- a successful action call is never treated as proof of the real device/scene state;
- stateful buttons follow an independent normalized feedback source;
- multiple widget instances can reuse the same central button definitions while keeping local interaction feedback isolated;
- the widget is ready for later grid placement/editing without implementing the Block-14 editor or final Start composition.

## 2. Binding project constraints

The existing JamesUI 1.0 architecture remains binding:

- Variant B remains in force; r11 stays production/reference until controlled cutover.
- No normal feature work is added to r11.
- Modules use `create(context, config)`, `mount(target)`, `update(nextContext, nextConfig)`, `destroy()`.
- Widgets consume capabilities/actions only and receive no raw Home Assistant access.
- Providers may use the Home Assistant Adapter.
- Interactive commands go through the Action Registry.
- No monkey-patches, Prototype overrides, release-polish layers, duplicate architectures or permanent compatibility shims.
- No invented/demo backend data.
- The structured configuration sections remain `pages`, `layouts`, `widget_instances`, `dynamic_buttons`, `data_sources`, `module_settings`.
- Final Start grid/composition, generic page/widget instance orchestration, drag/drop placement and resize behavior remain Block 14.
- Later House/Climate/Media/Door migrations and production cutover remain out of scope.

## 3. Product model

### 3.1 Two interaction modes

Dynamic Buttons support exactly two interaction modes in Block 13:

1. `toggle`
2. `trigger`

The interaction mode must be visually recognizable in the resting UI through a small permanent interaction-mode indicator. Toggle and trigger remain one visual button family; they do not use unrelated button shapes or color systems.

### 3.2 Toggle

A toggle represents a real externally reported binary end state with optional intermediate states.

A valid toggle requires:

- `activate_action`
- `deactivate_action`
- `state_source_id`

The two actions may be technically different or may intentionally contain the same registered action payload when the external system itself performs toggle semantics.

A scene is modeled as a toggle when the external scene controller provides a real activated/deactivated feedback signal. JamesUI does not determine scene membership and does not infer whether the scene is active from individual lights/devices.

### 3.3 Trigger

A trigger represents a stateless one-shot action.

A valid trigger requires:

- one `action`

It has no persistent active/inactive state. On successful completion it shows a short positive confirmation and returns to neutral.

Examples include one-shot service commands, navigation, URL opening or commands whose external interface exposes no meaningful persistent state.

## 4. Command boundary

Dynamic Buttons may execute **any Action Registry action**.

The widget validates only the generic action envelope:

- action is a plain object;
- `type` is a non-empty string;
- the payload is immutable/detached from mutable configuration state.

Type-specific validation remains the responsibility of the registered action provider.

This deliberately avoids hard-coding Block 13 to the action types currently present on `main`:

- `entity.toggle`
- `ha.service`
- `scene.activate`
- `navigate`
- `url.open`
- `task.update`

Future action providers must be usable without changing `widget.dynamic-buttons`.

## 5. Real-state boundary

### 5.1 Generic capability

Block 13 introduces one normalized status capability:

`control.states`

The first provider module is conceptually `provider.control-state`. It is Home-Assistant-backed through the existing Home Assistant Adapter, but its **consumer contract is generic**. The widget never knows whether the raw signal originated from HA, KNX bridged into HA, SmartVisu bridged into HA or another upstream controller.

Direct new KNX/SmartVisu protocol clients are explicitly out of Block 13.

### 5.2 Query/subscription service

`control.states` is a provider-owned subscribable service. Conceptually:

```text
version: 1
configured_sources: [{ id }]

subscribe({ source_ids }, listener) -> unsubscribe
```

A consumer requests only the source IDs it needs. Multiple consumers may subscribe to the same source. The provider may share/ref-count underlying Home Assistant subscriptions.

The service object is generation-bound. A service obtained before provider update/rebind/destroy becomes stale and must reject new use. Late callbacks from stale generations must not affect current consumers.

### 5.3 Normalized state record

Each requested source yields a normalized immutable record:

```text
source_id
status: active | inactive | intermediate | unavailable
detail: string | null
revision: non-negative integer
reason: string | null
```

Rules:

- `active` and `inactive` are terminal/end states.
- `intermediate` carries a configured semantic `detail` such as `opening`, `closing` or `moving`.
- `unavailable` means the bound signal cannot currently be interpreted reliably.
- unknown/unmapped raw values are `unavailable`; JamesUI never guesses.
- `revision` advances only when the bound signal's relevant interpreted value/availability changes, not merely because an unrelated HA state object/attribute changed.

The revision rule is critical for command acknowledgement: the already-known pre-command state may not be mistaken for a new response.

## 6. Status-source configuration

### 6.1 Canonical ownership

Technical feedback-source definitions belong under:

`data_sources.control_states`

Button definitions belong under:

`dynamic_buttons`

This keeps technical data-source ownership separate from interaction/presentation configuration.

The existing schema-v1 top-level structure already supports both sections; Block 13 does not require a new top-level config section.

### 6.2 One signal per source

Each `state_source_id` represents exactly one explicitly configured external feedback signal.

Block 13 does **not** combine multiple sensors/entities into a derived scene/device state. Such logic belongs in the upstream automation/controller.

### 6.3 HA-backed source shape

The HA-backed provider supports:

- one configured `entity_id`;
- optional one `attribute`; when absent, use the entity state;
- explicit `active_values`;
- explicit `inactive_values`;
- optional intermediate mappings, each with a stable semantic detail ID and explicit raw values.

Conceptually:

```yaml
data_sources:
  control_states:
    garage:
      entity_id: cover.garage_feedback
      attribute: state
      active_values: [open]
      inactive_values: [closed]
      intermediate:
        - id: opening
          values: [opening]
        - id: closing
          values: [closing]
```

A source without `attribute` evaluates the HA entity's main state.

Mappings must be deterministic and non-overlapping. A raw value may not belong to more than one terminal/intermediate mapping.

## 7. Central Dynamic Button definitions

`dynamic_buttons` is a reusable central library keyed by stable button ID.

Every definition has:

- stable ID from the map key;
- required non-empty `name`;
- `mode: "toggle" | "trigger"`;
- optional base semantic icon;
- optional `timeout_ms`, default **5000 ms**.

### 7.1 Toggle definition

Conceptually:

```yaml
dynamic_buttons:
  scene_evening:
    name: Abend
    mode: toggle
    icon: home.scene
    state_source_id: scene_evening_state
    activate_action:
      type: ha.service
      ...
    deactivate_action:
      type: ha.service
      ...
    timeout_ms: 5000
    presentation:
      active:
        text: Aktiv
        icon: optional.semantic.icon
      inactive:
        text: optional
        icon: optional.semantic.icon
      intermediate:
        opening:
          text: Öffnet
          icon: optional.semantic.icon
```

State-specific text/icon entries are optional. Missing state text does not remove the fixed button name. Missing state icon falls back to the base icon.

If an intermediate detail exists but has no button-specific presentation entry, the widget uses a generic in-progress presentation rather than exposing a technical raw/detail identifier as user-facing copy.

### 7.2 Trigger definition

Conceptually:

```yaml
dynamic_buttons:
  all_shutters_close:
    name: Rollläden
    mode: trigger
    icon: optional.semantic.icon
    description: Alle schließen
    action:
      type: ha.service
      ...
    timeout_ms: 5000
```

`description` is optional and is presentation text only, never a status signal.

## 8. Per-widget instance content

A `widget.dynamic-buttons` instance selects central button definitions by ID.

Each use owns its own presentation sizing class:

- `compact`
- `normal`
- `wide`

The sizing class belongs to the **use/instance**, not the central button definition. The same central Dynamic Button may therefore be `normal` in one widget instance and `wide` in another.

Block 13 keeps instance content deterministic and independently configurable. Generic page/Loader multi-instance orchestration remains Block 14.

The widget has **no built-in title/header**.

## 9. Toggle execution state machine

### 9.1 Starting a command

A toggle is actionable only when its current normalized status is exactly `active` or `inactive`.

- From `inactive`: execute `activate_action`, expect `active`.
- From `active`: execute `deactivate_action`, expect `inactive`.
- From `intermediate`: disabled until a terminal state arrives.
- From `unavailable`: disabled until a valid terminal state arrives.

On accepted user tap:

1. capture current source revision;
2. choose target terminal state;
3. enter local `pending`;
4. start the configured timeout;
5. execute the selected action through `context.actions.execute(...)`.

While `pending`, further taps on that local button instance are ignored/disabled.

### 9.2 Action result versus real feedback

Action Registry `success` means only that the command path accepted/completed the action. It is **not proof of the external target state**.

For a toggle:

- Action `success` leaves the button pending until real feedback reaches the target.
- Action `rejected`, `unavailable` or `error` ends the operation immediately as a transient command failure.
- If the expected target feedback arrives before the action Promise resolves, the real feedback wins: pending ends successfully and a later action result for that completed operation is ignored.
- Late callbacks from older operations/generations are ignored.

### 9.3 Feedback evaluation

Only a source revision newer than the revision captured at command start participates in command acknowledgement.

For a newer feedback revision:

- expected terminal state -> success, end `pending`;
- configured `intermediate` -> remain `pending`, show the intermediate presentation;
- opposite/unexpected terminal state -> fail immediately;
- `unavailable` -> fail the operation because the target can no longer be verified.

If the signal never changes from the pre-command state, the operation remains pending until timeout.

### 9.4 Timeout

Each button uses one common `timeout_ms` for both toggle directions.

Default: **5000 ms**.

Timeout behavior:

- end `pending`;
- show transient error feedback;
- return to rendering the latest real status;
- no automatic retry;
- no second command;
- no persistent error/escalation history.

Long-running functions such as garage doors may configure a longer timeout such as 30–45 seconds.

## 10. Trigger execution state machine

On tap:

1. enter local `pending`;
2. block further taps;
3. execute the configured action;
4. bound the operation by `timeout_ms`.

Results:

- `success` -> short positive confirmation for approximately **650 ms**, then neutral;
- `rejected`, `unavailable`, `error` or timeout -> short red multi-pulse feedback, then neutral.

Trigger feedback is never persisted as a real active state.

## 11. Local interaction feedback versus shared real state

Real source state is shared through `control.states`. If the same central button appears in two widget instances, both reflect external `active/inactive/intermediate/unavailable` updates.

Transient interaction state is local to the instance where the user acted:

- `pending`;
- positive trigger confirmation;
- transient error animation.

Pressing a button in one widget instance must not put a second instance into `pending`.

## 12. Visual contract

### 12.1 Stable content

Every Dynamic Button shows:

- required fixed name;
- optional icon;
- at most one secondary/status line;
- permanent small interaction-mode indicator distinguishing toggle from trigger.

The fixed name remains visible through state changes.

### 12.2 Toggle appearance

- `inactive`: normal/neutral JamesUI button treatment.
- `active`: the standard JamesUI active treatment, matching the visual language of an enabled light/control; no scene-specific color.
- `intermediate`: configured status text/icon when available, otherwise generic in-progress treatment.
- `unavailable`: persistent subdued/unavailable treatment plus compact `Nicht verfügbar` feedback.

A toggle may preserve its underlying real-state styling while also showing a local pending affordance. Pending must not fabricate a target state.

### 12.3 Trigger appearance

A trigger has a neutral resting treatment and may show its optional description in the one secondary line.

During execution the secondary line/feedback affordance may temporarily represent progress. Success produces the short positive confirmation; failures produce the transient red multi-pulse feedback.

### 12.4 Failure semantics

Command/timeout failures are transient UI feedback only.

Repeated failures do not create a new persistent product state. Each failure simply replays the short error feedback and returns to the actual real-state or neutral presentation.

Persistent `unavailable` is different: it reflects the real inability to read the configured feedback source and remains visible until valid feedback returns.

### 12.5 Design System

Styles use JamesUI design tokens and semantic icons only. No copied r11 selectors, palette constants, Unicode-icon system, inline SVG strings, data-image hacks or `!important` patching.

## 13. Tap, long-press and future editing

Block 13 implements the normal primary tap/click action only.

Long-press is reserved for the later layout editor:

- long-press starts edit/drag directly on the touched element;
- it must suppress normal button activation;
- there is no separate prerequisite global edit switch;
- drag/resize mechanics themselves are not implemented in Block 13.

The Dynamic Button implementation must not install gesture behavior that prevents the future host/editor from intercepting long-press/drag. It must expose stable item identity in its DOM so Block 14 can address placements safely.

## 14. Grid/minimum-size contract

Block 13 does not decide that Start shows exactly 3, 4 or 5 buttons per row.

Dynamic Buttons expose the three usage sizing classes `compact`, `normal`, `wide` and must maintain a truthful minimum readable presentation. The widget/layout must never squeeze a button below its supported minimum merely to fit another column.

Block 14 will:

- define the final logical grid/raster;
- map sizing classes to actual minimum spans;
- decide how many buttons fit beside each other at the OnePlus Pad 2 portrait target;
- own grid coordinates/placement;
- own drag/drop and resize;
- own collision handling and automatic reflow/repacking.

The intended editing behavior is Android/iOS-like: elements move freely **on the logical grid**, not by arbitrary pixel coordinates. Dropping onto occupied space may reflow other elements when a valid arrangement exists.

## 15. r11 behavior retained only as evidence

The retained r11 Start implementation demonstrates:

- manually favored scene buttons;
- immediate tap feedback;
- scene actions initiated from the Start UI;
- a short roughly 650 ms visual activation reaction.

Block 13 does **not** retain:

- automatic scene discovery/fill;
- direct raw `hass.callService` from the UI;
- prototype wrapping;
- r11 selectors/CSS;
- Unicode scene icons;
- the assumption that action success itself proves scene state.

The new toggle model supersedes the old scene-only behavior whenever an external activated/deactivated feedback signal exists.

## 16. Planned module boundaries

Expected Block-13 production boundaries:

```text
custom_components/jamesui/frontend/modules/provider.control-state/
  manifest.js
  config.js
  normalize.js
  provider.js
  index.js

custom_components/jamesui/frontend/modules/widget.dynamic-buttons/
  manifest.js
  config.js
  model.js
  styles.js
  widget.js
  index.js
```

A small shared pure helper may be introduced only if both modules genuinely need the same generic JSON/action/source validation. It must not become a second service layer.

No r11 production file is modified.

## 17. Provider lifecycle requirements

`provider.control-state` must:

- explicitly validate configured unique source IDs;
- reject overlapping raw-value mappings;
- subscribe only through the Home Assistant Adapter;
- isolate consumers/listeners;
- publish `not_configured` when no control-state sources exist;
- publish top-level `unavailable` when Home Assistant is disconnected;
- provide an immutable generation-bound service while connected;
- share/ref-count underlying source/entity subscriptions where practical;
- ignore late callbacks from stale provider generations;
- clean up subscriptions on update/destroy;
- restore the previous valid runtime if a mounted rebind fails, matching the atomic lifecycle standard established in prior blocks.

## 18. Widget lifecycle requirements

`widget.dynamic-buttons` must:

- consume `control.states` only for real state;
- consume `context.actions` only for commands;
- never access raw Home Assistant;
- resolve/use central button definitions without owning the Config Service;
- support independent direct multiple instances;
- release and rebind status subscriptions on capability replacement/update;
- cancel timers and invalidate pending operations on update/destroy;
- treat status-service replacement during a pending toggle as loss of acknowledgement continuity and fail/clear that local operation safely;
- ignore stale action Promise completions and stale timer callbacks;
- keep healthy sibling buttons usable if one configured state source is unavailable.

## 19. Configuration/composition boundary

Block 13 defines and validates the reusable subcontracts for:

- `data_sources.control_states`;
- `dynamic_buttons`;
- per-`widget.dynamic-buttons` selected uses/sizing.

The widget itself does not receive the global Config Service. A pure resolver may combine a central definition library with one instance's button references into immutable runtime config for tests and later orchestration.

Block 14 owns the generic runtime composition that reads the structured store, creates arbitrary widget instances, resolves global definitions into instance runtime config, and applies placement/grid metadata.

This preserves the foundation rule that normal widgets do not become config-store clients.

## 20. Explicit non-goals

Block 13 does not implement:

- final Start composition or exact number of buttons per row;
- generic page/widget placement orchestration;
- drag/drop or resize editor mechanics;
- arbitrary pixel placement;
- multiple-signal state derivation;
- direct KNX/SmartVisu protocol clients;
- scene membership/grouping logic;
- House Quick changes;
- detail pages;
- long-press action bindings;
- persistent command-error history/escalation;
- automatic retries;
- production cutover.

## 21. Acceptance gate

Block 13 is complete only when all of the following are true:

- central reusable Dynamic Button definitions are validated independently from per-instance use/size;
- control-state sources live under the `data_sources` contract and are explicitly mapped;
- `provider.control-state` exposes `control.states` without leaking raw HA state to widgets;
- state revisions protect against treating the pre-command state as fresh acknowledgement;
- `widget.dynamic-buttons` supports both `toggle` and `trigger`;
- toggle actions remain pending until the expected new real target state arrives;
- intermediate feedback keeps a toggle pending and is displayable;
- wrong terminal feedback, unavailable feedback, Action Registry failure and timeout terminate the operation safely;
- real target feedback wins races against late Action Registry completion;
- triggers use pending + approximately 650 ms success feedback or transient error feedback only;
- both modes suppress repeat taps while pending;
- unavailable/intermediate toggles are not actionable;
- real status is shared across instances while pending/success/error feedback is local;
- fixed name, optional icon, one secondary line and permanent toggle/trigger indicator are enforced;
- active uses normal JamesUI active styling;
- `compact | normal | wide` usage sizing exists without hard-coding final grid spans;
- no header is built into the widget;
- no raw HA access, legacy patching or r11 changes are introduced;
- Block 14 responsibilities remain deferred;
- targeted tests, architecture guards, whole-branch review, unchanged feature-head CI and merged-main CI all pass before completion is claimed.
