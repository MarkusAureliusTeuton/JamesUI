# JamesUI 1.0 – Block 10 Weather Today + Forecast Overlay Design

_Date: 2026-10-04_
_Status: conversational design approved; written spec pending user review_

## 1. Purpose

Block 10 builds the first visible JamesUI 1.0 Start hero on top of the completed platform. It introduces one coherent widget, `widget.weather-today`, which renders the Alpine/weather hero into the Block-8 `hero` slot and opens a modal forecast overlay when the large current temperature is activated.

The block must preserve the accepted Start direction without copying r11 markup, CSS, selectors, direct Home Assistant access or patch layers.

Success means:
- the OnePlus Pad 2 portrait-oriented hero has the accepted Alpine-Chic visual hierarchy;
- all weather content comes only from Block-9 capabilities;
- missing backend data stays explicit rather than fabricated;
- forecast opens above the page without moving or expanding the hero/layout;
- the Core gains only a weather-neutral DOM-overlay hosting capability;
- Block 10 does not compose the final Start page or switch production away from r11.

## 2. Scope

### In scope

- new widget module `widget.weather-today`;
- current device-local date and `HH:MM` clock;
- Alpine background selected from the retained local asset family;
- current condition, temperature and semantic weather icon;
- today's high/low when a real current-day Daily item exists;
- precipitation information, including a concrete start time only when Block 9 supplied one from genuine Hourly data;
- wind/gust, sunrise, sunset and moon phase/illumination facts;
- modal Hourly/Daily forecast overlay;
- live capability updates while the hero and/or overlay are mounted;
- generic Core shell support for mounting DOM content supplied by any overlay descriptor;
- a narrow additive Block-9 timezone metadata amendment needed for truthful UI formatting;
- loader/lifecycle/architecture tests.

### Out of scope

- Calendar, House Quick or Dynamic Buttons;
- final Start page composition/configuration (Block 14);
- settings UI for background/manual scene selection;
- charts, radar, animated weather, external weather APIs or remote assets;
- new weather forecasting/provider heuristics;
- Home Assistant calls from the widget;
- production bootstrap/cutover;
- deletion of r11 or legacy weather assets.

## 3. Architectural choice

Use one widget module rather than separate clock/weather/forecast modules.

`widget.weather-today` owns the coherent hero experience and its forecast dialog. The widget consumes capabilities and shared visual infrastructure, but has no Home Assistant dependency.

The forecast overlay remains transient UI state. The existing Overlay Service stays the owner of which overlay is current. The Core shell is extended only so an overlay descriptor may contain a DOM element; the Core does not learn any weather vocabulary or forecast behavior.

## 4. Module contract

Manifest:

```text
id: widget.weather-today
type: widget
version: 1.0.0
core_api: 1.x
depends_on: []
requires_capabilities:
  - weather.current
  - weather.daily
  - weather.hourly
  - weather.sun
  - weather.moon
  - weather.atmosphere
provides_capabilities: []
config_schema: widget.weather-today/v1
```

All six capabilities are declared because the widget understands them. Runtime `unavailable` or `not_configured` snapshots remain normal states and must not prevent the widget from mounting.

V1 widget config is intentionally empty. Any unknown key is rejected. Existing migrated background settings remain stored but are not wired into this widget until the Start configuration block; automatic atmosphere-driven backgrounds are the only Block-10 behavior.

Lifecycle remains:

```text
create(context, config)
mount(target)
update(nextContext, nextConfig)
destroy()
```

The widget uses only the normal widget context:
- `events`
- `overlays`
- `capabilities`
- `actions`
- `module`

It receives no raw `hass`, Home Assistant Adapter, Config Service, Router, Health Service, Design System object, Module Registry or Module Loader.

## 5. Narrow Block-9 timezone metadata amendment

Block 9 deliberately keeps calendar/day semantics in the Home Assistant timezone. Block 10 must not undo that by formatting forecast or sun instants in the browser timezone.

Therefore Block 10 includes an additive metadata extension to existing Block-9 values:

- available `weather.current` value carries `time_zone`;
- available `weather.daily` value carries `time_zone`;
- available `weather.hourly` value carries `time_zone`;
- available `weather.sun` value carries `time_zone`.

`time_zone` is either the validated Home Assistant IANA timezone or `null` where the existing capability may truthfully remain available without one. No seventh capability is introduced and no forecast-selection behavior changes.

Rules:
- Daily remains unavailable with `timezone_unavailable` under the existing Block-9 contract when no valid HA timezone exists.
- Hourly may remain available with `time_zone: null`; Block 10 then does not pretend to know the user's local clock time for those forecast entries.
- Current weather may remain available with `time_zone: null`; `next_precipitation_at` is already null in that state.
- Sun may remain available with `time_zone: null`; sunrise/sunset clock labels then render unavailable rather than using browser-local conversion.

All weather/sun instant formatting uses the capability-provided timezone via `Intl.DateTimeFormat`. The only intentionally browser/device-local time is the large wall clock/date.

## 6. Hero structure

The widget mounts one stable hero root into the supplied target. It creates DOM through `target.ownerDocument` only.

Semantic structure:

```text
weather-today root
├─ decorative Alpine image layer
├─ readability/atmosphere shading layer
└─ content layer
   ├─ date + large clock
   ├─ current-weather row
   │  ├─ semantic weather icon
   │  └─ forecast trigger containing current temperature + condition
   └─ weather facts
      ├─ maximum
      ├─ minimum
      ├─ precipitation
      ├─ wind/gust
      ├─ sunrise
      ├─ sunset
      └─ moon
```

No `Home`, `HEUTE & DANACH` or `ZUHAUSE` labels are rendered.

The widget root and important child nodes remain stable across capability updates. Updates mutate text, attributes, icons and asset source rather than replacing the whole hero.

## 7. Device clock/date

The hero clock is UI/device state, not weather domain data.

- locale: `de-DE`;
- time: 24-hour `HH:MM`, no seconds;
- date: weekday + day + month, no year in the main hero;
- device/browser timezone is intentional for this clock only;
- render immediately on mount;
- use one self-rescheduling timeout aligned to the next minute boundary;
- reschedule after every tick so long-running kiosk drift is bounded;
- date naturally updates at local midnight;
- `destroy()` clears the active timeout.

Production `index.js` may adapt `Date`, `setTimeout` and `clearTimeout` into an injectable runtime so tests can be deterministic.

## 8. Current-weather presentation

### Condition icon

Map known Home Assistant conditions only to the semantic local icon library:

- `sunny` → `weather.sunny`
- `partlycloudy` → `weather.partly-cloudy`
- `cloudy`, `exceptional` → `weather.cloudy`
- `rainy` → `weather.rain`
- `pouring` → `weather.heavy-rain`
- `snowy` → `weather.snow`
- `lightning`, `lightning-rainy`, `hail` → `weather.storm`
- `windy`, `windy-variant` → `weather.wind`
- `fog` → `weather.fog`
- `snowy-rainy` → `weather.rain`
- `clear-night` → current `weather.moon` phase icon when available; otherwise no fabricated weather icon.

Unknown conditions get no invented icon.

Known conditions receive concise German display labels. Unknown/non-empty conditions render a neutral `Wetterlage unbekannt` label rather than exposing an English/internal state as polished copy.

### Temperature trigger

The large temperature is the only normal hero forecast trigger.

- It is implemented as a real `<button type="button">` for keyboard/touch accessibility.
- It is visually styled as part of the hero rather than as a generic control surface.
- Accessible label is dynamically meaningful, e.g. `Wetterprognose öffnen, aktuell 18 Grad Celsius` when the data supports it.
- It remains operable even when current temperature is unavailable, because a Daily/Hourly forecast may still be available; in that case its visible value is `—` and its label remains `Wetterprognose öffnen`.
- Opening the forecast never changes hero/layout geometry.

Numeric weather values use `de-DE` formatting and preserve provider-supplied units. Missing values render `—`, never `0`.

## 9. Today's high/low

The hero uses only a Daily item whose `date` equals today's calendar date in `weather.daily.time_zone`.

- If such an item exists, use its real `temperature_high` / `temperature_low` independently.
- If today's item does not exist, do not silently use tomorrow's forecast.
- Missing high or low renders `—` independently.

This prevents a next-day forecast from being mislabeled as today's high/low.

## 10. Weather facts

Primary order is fixed:

1. maximum
2. minimum
3. precipitation
4. wind/gust
5. sunrise
6. sunset
7. moon

On the primary tablet portrait width they form one restrained row. Narrow container layouts may wrap deterministically; semantic order does not change.

### Precipitation

- If `weather.current.next_precipitation_at` is present, show its clock time formatted in `weather.current.time_zone` plus probability when present.
- Otherwise today's Daily precipitation probability may be shown if real.
- If the current weather condition is snow-related, the accessible/semantic fact label becomes `Schnee`; no fabricated accumulation value is added.
- No concrete rain/snow start time is derived by the widget.

### Wind/gust

- Show real wind speed and provider unit when present.
- Add gust value when present.
- `windy`, `windy-variant`, lightning/storm-like conditions may receive stronger visual emphasis through semantic CSS state.
- Block 10 introduces no new numeric storm/wind threshold.

### Sunrise/sunset

- Use only `weather.sun.next_rising` / `next_setting` and `weather.sun.time_zone`.
- If the instant or timezone is unavailable, render `—`.
- Never format Sun data using browser timezone as a fallback.

### Moon

- Map the eight Block-9 canonical phase IDs to existing `moon.*` icons.
- Show illumination percentage when finite.
- The widget does not calculate moon data.

## 11. Alpine background contract

Only the approved local Alpine family is usable in Block 10.

Allowlist:

```text
clear-day   -> /jamesui_static/assets/alpine/clear-day.webp
cloudy-day  -> /jamesui_static/assets/alpine/cloudy-day.webp
rain-day    -> /jamesui_static/assets/alpine/rain-day.webp
snow-day    -> /jamesui_static/assets/alpine/snow-day.webp
fog         -> /jamesui_static/assets/alpine/fog.webp
dusk        -> /jamesui_static/assets/alpine/dusk.webp
clear-night -> /jamesui_static/assets/alpine/clear-night.webp
cloudy-night-> /jamesui_static/assets/alpine/cloudy-night.webp
```

The selected key comes only from available `weather.atmosphere.scene_key`.

Unknown/missing keys:
- hide/remove the decorative image source;
- keep a neutral dark token-driven gradient/fallback;
- do not guess `cloudy`, `day` or another weather scene.

The Alpine image is decorative (`alt=""`, hidden from accessibility semantics). A fixed token-driven shading layer protects text contrast without mutating the image asset.

No remote image, dynamic URL, old `assets/weather/*.svg` or data URI is allowed.

## 12. Styling

Widget styles are root-scoped under a unique Block-10 data attribute and consume existing Block-6 tokens for palette, typography, spacing, radii, shadows and motion.

Visual hierarchy on the primary target:
- date quiet and compact;
- clock dominant but lighter than the temperature interaction area;
- current temperature prominent;
- condition secondary;
- facts compact with warm/champagne icon accents;
- background photography visible but subordinate to legibility;
- no glowing borders and no generic Lovelace/card appearance.

Responsive behavior is CSS/container-driven, not JS/device detection. The widget establishes/uses an inline-size container and at a narrow threshold may wrap facts while preserving order and target accessibility.

No r11 selector, pixel-polish layer, `!important`, raw palette duplication or global CSS mutation is permitted.

## 13. Generic DOM overlay-host extension

The existing Overlay Service contract remains valid and keeps stale-close protection.

A descriptor may additionally carry:

```text
content: <DOM element>
```

Core shell behavior:
- if no overlay is current: hide root and clear children;
- if `descriptor.content` is a DOM element owned by the shell document: mount that element into `overlayRoot` with `replaceChildren()`;
- otherwise preserve the existing backward-compatible text fallback using `descriptor.title ?? descriptor.id`;
- Core does not create weather dialogs, inspect weather capability names or import the weather widget.

The content element is owned by the caller/widget. Replacing/closing the overlay detaches it from the shell host; widget listeners remain the widget's cleanup responsibility.

No new persistent Core state is introduced.

## 14. Forecast overlay

Overlay ID is stable and module-scoped:

```text
widget.weather-today:forecast
```

The widget builds overlay DOM with the shared visual primitives:
- `createOverlayFrame()`
- `createDialog({ title: "Wetterprognose" })`
- `createButton()` for close
- `createIcon(..., "shell.close")`

The dialog has an explicit close button with `aria-label="Prognose schließen"`. Backdrop activation may close only when the event target is the backdrop itself; interacting inside the dialog must not close it.

A full keyboard focus-trap subsystem is not introduced in Block 10. Existing semantic dialog/aria-modal primitives are retained and the close button remains keyboard reachable.

### Hourly section

Heading: `Nächste Stunden`.

- Use only available `weather.hourly`.
- Require a valid `weather.hourly.time_zone` before presenting clock labels.
- Filter to valid items whose instant is at or after `runtime.now()`.
- Show at most the next 12 items.
- Each row/item may show local time, condition icon/label, temperature and precipitation probability.
- Do not interpolate missing hours or manufacture values.
- If Hourly exists but has no trustworthy timezone, show a concise `Zeitbasis nicht verfügbar` state rather than browser-local times.

### Daily section

Heading: `Nächste Tage`.

- Use only available `weather.daily`.
- Filter from today's date in `weather.daily.time_zone` forward.
- Show at most 7 items.
- Day label is `Heute`, `Morgen`, otherwise localized weekday.
- Show condition, high/low and precipitation probability where real.
- No charting or synthetic trend values.

### Empty forecast

The overlay still opens when no usable Hourly or Daily data exists and renders:

`Prognose aktuell nicht verfügbar`

This state is preferable to making the temperature control inert or silently closing the dialog.

## 15. Live updates and overlay ownership

The widget subscribes once to each declared capability through `context.capabilities.subscribe(..., { emitCurrent: true })`.

It maintains the latest six snapshots and derives a view model from them.

Capability updates:
- update existing hero nodes in place;
- update an open forecast dialog in place;
- never reopen the overlay solely because data changed;
- never replace the Block-8 hero slot node or layout root.

The widget may subscribe to Overlay Service changes only to detect when another overlay replaced its forecast. If current overlay ID no longer equals `widget.weather-today:forecast`, it drops its local forecast-overlay references without closing the new overlay.

The close callback returned by `overlays.open()` is retained while its own forecast is current. On `destroy()` the widget invokes that callback; stale-close protection guarantees this cannot close a newer unrelated overlay.

## 16. Update and destroy semantics

### `update(nextContext, nextConfig)`

- validate the full next context/config before mutation;
- V1 config remains empty/strict;
- preserve hero root identity when mounted;
- if Capability Registry identity changed, unsubscribe old capability listeners and subscribe to the new registry;
- if Overlay Service identity changed while this widget owns an open overlay, close only the old-service overlay before switching;
- keep one clock timeout only.

### `destroy()`

Must:
- unsubscribe all capability subscriptions;
- unsubscribe any overlay observer;
- clear the clock timeout;
- close only the widget's own forecast through its stale-safe close callback;
- remove widget-owned DOM/style nodes from its mount target;
- remove all widget-created listeners;
- be idempotent.

## 17. Error/unavailable behavior

Capability statuses are handled independently.

Examples:
- current unavailable + Daily available: show unavailable current temp/condition, keep today's high/low and forecast overlay functional;
- atmosphere unavailable: use neutral dark fallback, not guessed imagery;
- sun unavailable: sunrise/sunset are `—`, moon/weather remain unaffected;
- moon unavailable: moon fact is `—`, no local widget calculation;
- Hourly unavailable: hide/empty only Hourly section; Daily remains;
- Daily unavailable: high/low are `—`, Hourly may still populate overlay;
- both forecasts unavailable: overlay opens with explicit unavailable message.

The widget never converts `unavailable`/`not_configured` into plausible fake weather values.

## 18. Proposed implementation boundary

Expected new module directory:

```text
custom_components/jamesui/frontend/modules/widget.weather-today/
```

Likely focused files:
- `manifest.js` – module contract;
- `config.js` – strict V1 empty config;
- `model.js` – condition/icon/label/fact/view-model derivation;
- `format.js` – `de-DE`, HA-timezone and device-clock formatting;
- `assets.js` – immutable Alpine scene allowlist;
- `overlay.js` – forecast dialog DOM/update behavior;
- `styles.js` – root-scoped token CSS;
- `widget.js` – lifecycle/subscriptions/hero DOM ownership;
- `index.js` – production runtime adapter + `create()`.

Exact file splitting may be reduced during planning if two helpers are too small, but responsibilities must remain isolated and testable.

Existing files intentionally touched by Block 10 are limited to:
- Block-9 provider/normalizers for additive `time_zone` metadata;
- Core `shell.js` for generic overlay DOM content hosting;
- tests and CI/architecture gates.

`overlay-service.js` should not need weather-specific or content-specific logic changes.

## 19. Testing contract

Implementation must be test-driven and cover at minimum:

### Manifest/config
- widget manifest/type/version/capability declarations;
- strict empty V1 config;
- no provided capabilities.

### Timezone amendment
- current/daily/hourly/sun expose validated HA timezone metadata as specified;
- invalid/missing timezone never causes browser fallback;
- existing Block-9 behavior remains green.

### Pure view model/formatting
- known condition → exact semantic icon + German label;
- unknown condition → no fabricated icon/label;
- today high/low never borrow tomorrow;
- precipitation start time only consumes provider field;
- unit preservation;
- sunrise/sunset/hourly formatting uses supplied HA timezone;
- missing timezone produces explicit unavailable display;
- moon phase → exact `moon.*` ID;
- exact Alpine allowlist and neutral unknown fallback.

### Hero lifecycle
- mount creates stable semantic DOM;
- six capability subscriptions with current snapshot emission;
- capability updates mutate hero without replacing root;
- one minute-aligned clock timeout at a time;
- temperature button opens overlay without changing hero target geometry/identity;
- update rebinds context safely;
- destroy removes subscriptions/timer/listeners/DOM and is idempotent.

### Overlay host
- legacy title-only descriptor still renders text;
- valid same-document DOM content is mounted;
- closing clears content;
- unrelated/newer overlay is protected from stale widget close.

### Forecast dialog
- next 12 future Hourly only;
- up to 7 current/future Daily entries;
- `Heute`/`Morgen` semantics from HA timezone;
- live capability update refreshes an open dialog in place;
- no-timezone Hourly state is truthful;
- empty forecast message;
- explicit close and backdrop-only close behavior.

### Architecture gates
- no raw `hass` or HA Adapter import in widget;
- no Config Service/Router/Health/Registry/Loader import;
- no r11/legacy Start import;
- no remote fetch/XHR/CDN assets;
- no old weather SVG dependency;
- Alpine assets restricted to exact allowlist;
- Core shell contains no `weather.*`, forecast condition mapping or widget ID-specific rendering branch;
- production `jamesui-entry.js` remains on r11.

### Loader integration
- real Module Registry/Loader load/mount/update/reload/destroy compatibility using the new widget manifest.

## 20. Visual acceptance for this block

Block 10 is a visible module milestone, but it is not yet the composed Start page. Acceptance in this block proves the hero/widget and overlay independently at the primary portrait geometry. Final OnePlus/Fully full-page screenshot acceptance remains mandatory again at the composed Start milestone (Block 14 / pre-cutover).

Block-10 visual review must verify:
- Alpine background remains recognisable;
- date/time hierarchy is calm and premium;
- temperature/condition is readable over every approved scene family;
- facts remain legible without becoming seven card tiles;
- forecast is clearly modal and causes no hero/layout shift;
- narrow fallback remains usable;
- no generic Lovelace/card styling or glow-heavy treatment appears.

If a deterministic browser screenshot harness is available during implementation, use it for the primary portrait review; do not introduce a permanent browser/runtime dependency solely to create that screenshot.

## 21. Explicit non-goals / permanent guards

Block 10 must not:
- query Home Assistant directly;
- calculate weather, rain time or moon phase;
- invent missing values;
- import/use r11 render functions or CSS;
- introduce a second overlay system;
- add weather logic to Core;
- wire the final Start route/page;
- consume Calendar/House/Dynamic Button capabilities;
- modify production bootstrap;
- create `v12`, polish, legacy-copy or compatibility-layer files.

## 22. Acceptance criteria

Block 10 is complete only when:
1. `widget.weather-today` satisfies the lifecycle and manifest contracts;
2. the Hero renders solely from capabilities + device clock;
3. the retained Alpine assets are selected only through the exact atmosphere allowlist;
4. current/today/sun/moon facts remain truthful under partial data;
5. temperature opens a live Hourly/Daily forecast overlay with no page-layout shift;
6. weather/sun timestamps are formatted using capability-provided HA timezone metadata, never implicit browser fallback;
7. the Core overlay-host extension is generic and backward compatible;
8. all lifecycle cleanup and stale-overlay behavior are tested;
9. real Module Loader compatibility is proven;
10. architecture gates prove no HA/config/r11/remote-asset/Core-weather coupling;
11. full branch CI and whole-branch review are green with no open Critical/Important findings;
12. after merge, `main` CI is green;
13. r11 remains the running production/reference runtime.
