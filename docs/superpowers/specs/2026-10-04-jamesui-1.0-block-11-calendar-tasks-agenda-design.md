# JamesUI 1.0 – Block 11 Calendar, Tasks and Agenda Design

_Date: 2026-10-04_
_Status: conversational design approved; written spec pending user review_

## 1. Purpose

Block 11 builds the real household Agenda domain on the clean JamesUI 1.0 architecture. It introduces:

- `provider.calendar` for explicitly configured Home Assistant `calendar.*` sources;
- `provider.tasks` for explicitly configured Home Assistant `todo.*` sources;
- `action.task-update`, registering the semantic action `task.update`;
- `widget.calendar-agenda` as the reusable presentation and interaction layer.

The widget must work as calendar-only, task-only or combined Agenda, support multiple independent widget instances, respect host-layout bounds, and never access raw Home Assistant APIs directly.

Success means:

- configured calendar events and tasks are displayed truthfully in the Home Assistant timezone;
- running, upcoming, historical, all-day and multi-day events behave consistently;
- tasks can be completed, undone for five seconds and edited in Block 11;
- overdue tasks are carried into Today without rewriting their true due value;
- JamesUI-owned advance notices are available without pretending that source reminders exist;
- one unavailable source does not break healthy sibling sources;
- no stale backend data is silently presented as current;
- no final Start composition, generic loader-wide instance orchestration or production cutover occurs in this block.

## 2. Binding project constraints

Foundation rules remain binding:

- modules use `create(context, config)`, `mount(target)`, `update(nextContext, nextConfig)`, `destroy()`;
- widgets consume capabilities and actions only;
- providers/actions may use the Home Assistant Adapter;
- user/control commands go through the Action Registry;
- providers own Home Assistant data subscriptions;
- the Event Bus is not a second domain-state layer;
- the Agenda widget receives no raw `hass`, Home Assistant Adapter, Config Service, Router, Health Service, Design System object, Module Registry or Module Loader;
- no monkey-patches, Prototype overrides, version-polish layers, duplicate implementations or permanent compatibility shims;
- r11 remains production/reference until the later controlled cutover;
- OnePlus Pad 2 portrait remains the primary visual target;
- page scrolling belongs to the host layout, not the Agenda widget.

Cross-page sizing/scroll rules remain in `docs/JAMESUI_1_0_LAYOUT_PLANNING_NOTES.md`.

## 4. Architectural choice

Three approaches were considered:

1. **Range-based calendar capability + live task snapshot + dedicated semantic task action** — selected.
2. One large shared 1–365-day calendar snapshot for all configured calendars — rejected because it over-fetches and over-updates unrelated consumers.
3. Provider derives one union range from every widget-instance config — rejected because it couples providers to page/widget configuration orchestration.

The selected design keeps calendar reads range-based because each Agenda instance can need a different historical/future window. Tasks fit a live source snapshot because Home Assistant exposes each complete `todo.*` list as a subscription stream. Mutations remain semantic actions rather than leaking `todo.update_item` service syntax into the widget.

## 5. Home Assistant contracts used by Block 11

### Calendar

Current Home Assistant developer documentation defines `calendar/event/subscribe` with `entity_id`, `start` and `end`. The subscription immediately returns the current event list for that range and pushes updates when the calendar entity changes. If event retrieval fails, the subscription payload uses `events: null`.

Important limitation: although Home Assistant's internal `CalendarEvent` model can contain `uid`, `recurrence_id`, `rrule` and status, the documented `calendar/event/subscribe` payload exposes only fields that have values among:

- `start`
- `end`
- `summary`
- `description`
- `location`

Block 11 therefore must not depend on source calendar UID, recurrence metadata or reminder metadata for display identity, deduplication or dismissal persistence.

Reference:
`https://developers.home-assistant.io/docs/core/entity/calendar/`

### Todo

Current Home Assistant exposes `todo/item/subscribe` for one `todo.*` entity. It sends an initial `{items: [...]}` update and then pushes later list updates. Todo items contain:

- `uid`
- `summary`
- `status`
- `due`
- `description`
- `completed`

The Todo entity exposes supported-feature flags for update, due date, due datetime and description support.

References:
- `https://developers.home-assistant.io/docs/core/entity/todo/`
- `https://github.com/home-assistant/core/blob/dev/homeassistant/components/todo/__init__.py`

### Todo update

Home Assistant `todo.update_item` can update an existing task using its UID. Supported updates include rename, `needs_action | completed`, due date, due date/time and description. Current Home Assistant service validation permits `null` for due/description fields, allowing supported extended fields to be cleared explicitly.

References:
- `https://www.home-assistant.io/actions/todo.update_item/`
- `https://github.com/home-assistant/core/blob/dev/homeassistant/components/todo/__init__.py`

## 6. Shared timezone rule

All Agenda domain date/time semantics use the validated Home Assistant IANA timezone from `homeAssistant.timeZone()`:

- Today/Morgen/day grouping;
- lookback/lookahead boundaries;
- all-day projections;
- multi-day timed projections;
- task due-date grouping;
- event/task clock formatting;
- advance-notice thresholds;
- HA-local midnight refresh.

Neither provider nor widget may silently fall back to browser timezone for Agenda domain data.

If Home Assistant is connected but its timezone is missing/invalid:

- `calendar.events` is `unavailable` with reason `timezone_unavailable`;
- `tasks.items` is `unavailable` with reason `timezone_unavailable`.

## 8. `calendar.events` capability

`calendar.events` is a read-only range service published through the Capability Registry. It is not a user command and therefore does not belong in the Action Registry.

Available value:

```text
{
  version: 1,
  time_zone: <validated HA IANA timezone>,
  configured_sources: [
    { entity_id, name }
  ],
  subscribe_ranges(request, listener) -> unsubscribe
}
```

Source `name` uses Home Assistant `friendly_name` when present, otherwise the truthful entity ID.

A request contains one or more source ranges:

```text
{
  ranges: [
    {
      entity_id: "calendar.family",
      start_date: "2026-09-27",
      end_date: "2026-11-04"
    }
  ]
}
```

`start_date` is inclusive and `end_date` exclusive, expressed as Home-Assistant-local `YYYY-MM-DD` dates. The provider converts them to the timezone-aware instants required by `calendar/event/subscribe`.

Listener snapshot:

```text
{
  time_zone,
  sources: {
    "calendar.family": {
      status: "available" | "unavailable",
      reason: null | <stable reason>,
      events: [...]
    }
  }
}
```

Rules:

- requests may use only configured `calendar.*` sources;
- invalid/unconfigured source IDs are rejected rather than silently discovered;
- identical `(entity_id, start_date, end_date)` remote subscriptions may be shared with reference counting;
- provider also observes configured calendar entity state locally so source existence/name/unavailable changes invalidate previously successful data immediately;
- payload `events: null` becomes source-specific `unavailable`, not a successful empty calendar;
- one failed source does not make healthy siblings unavailable;
- full HA disconnection makes the top-level capability unavailable and clears current remote values;
- reconnect republishes an available range service and consumers re-establish their current requests;
- stale callbacks from prior generation/range are ignored;
- `destroy()` unsubscribes all local and remote subscriptions.

Stable source-level reasons are limited to values such as:

```text
source_missing
source_unavailable
subscription_failed
fetch_failed
home_assistant_disconnected
timezone_unavailable
```

### Normalized calendar event

```text
{
  occurrence_id,
  source_entity_id,
  title,
  description,
  location,
  all_day,
  start_date,
  end_date,
  start_at,
  end_at
}
```

Exactly one time representation is used:

- all-day: `start_date`/`end_date`, with exclusive `end_date`;
- timed: `start_at`/`end_at` as validated ISO instants.

Provider `occurrence_id` is source-specific and derived from:

```text
source_entity_id + normalized title + normalized start + normalized end + all_day
```

It is a JamesUI occurrence key, never presented as a source UID.

Malformed events are rejected instead of guessed, including:

- missing/blank title;
- invalid start/end;
- end not after start;
- mixed date/date-time representations.

## 9. `tasks.items` capability

`provider.tasks` owns one `todo/item/subscribe` stream per configured `todo.*` source while mounted and observes each configured Todo entity state locally for availability/name/supported-feature changes.

Available value:

```text
{
  version: 1,
  time_zone,
  sources: {
    "todo.household": {
      status,
      reason,
      name,
      supported_features,
      capabilities: {
        can_update,
        can_set_due_date,
        can_set_due_datetime,
        can_set_description
      },
      items: [...]
    }
  }
}
```

Normalized task:

```text
{
  source_entity_id,
  uid,
  title,
  status,
  due: {
    kind: "none" | "date" | "datetime",
    value: null | <ISO date/instant>
  },
  description,
  completed_at
}
```

Rules:

- usable non-empty UID and title are required; malformed items lacking stable identity/title are excluded rather than shown as broken read-only rows;
- only `needs_action` and `completed` are accepted;
- date and datetime due values remain distinct;
- datetime due values must be timezone-aware valid instants;
- description/completed timestamp are nullable;
- feature capabilities come from the real Todo entity `supported_features` mask;
- identical semantic snapshots are not republished merely because a callback object changed;
- one unavailable list remains source-specific while healthy sibling lists continue;
- full HA disconnection makes the capability unavailable and clears current list values instead of presenting stale items as current;
- reconnect rebuilds configured subscriptions;
- stale callbacks from old generation/source are ignored;
- `destroy()` cleans local and remote subscriptions.

## 10. `task.update` action contract

Request:

```text
{
  type: "task.update",
  source_entity_id: "todo.household",
  uid: "<stable source uid>",
  patch: {
    title?: "New title",
    status?: "needs_action" | "completed",
    due?:
      { kind: "date", value: "YYYY-MM-DD" }
      | { kind: "datetime", value: "<ISO instant>" }
      | { kind: "none", value: null },
    description?: "text" | null
  }
}
```

Rules:

- patch must contain at least one supported field;
- title must be non-empty after trim;
- due date/datetime formats are validated strictly;
- `kind: none` means explicit due clearing;
- `description: null` means explicit description clearing;
- unknown fields are rejected;
- raw Home Assistant service data is never accepted from the widget.

Execution:

1. validate source/UID/patch;
2. require connected Home Assistant;
3. read the current Todo entity state and feature mask;
4. require `UPDATE_TODO_ITEM`;
5. require the appropriate due/description feature for extended fields;
6. translate title → `rename`, status → `status`, due → `due_date|due_datetime`, description → `description`;
7. always pass task UID as Home Assistant `item` selector;
8. return `success | unavailable | rejected | error` through the normal Action Registry contract.

For due clearing:

- when the current task due kind is known, clear using the corresponding supported due field;
- if there is no current due value, clearing is a successful no-op at widget patch-generation level and no action is sent;
- if the required due feature is absent, reject before service execution.

The widget never uses generic `ha.service` for Todo updates.

Defaults:

```text
presentation_mode = grouped
calendar_enabled = true
tasks_enabled = true
visible_items_mode = auto
max_visible_items = 5
lookahead_days = 30
lookback_days = 7
show_all_day = true

```

Invalid configurations:

- both domains disabled;
- calendar enabled with zero selected calendars;
- tasks enabled with zero selected todo lists;
- duplicate selected source IDs;
- selected source with wrong domain;
- lookahead outside `1..365`;
- lookback outside `0..365`;
- fixed visible count outside `3..8`;
- invalid icon ID or accent format;
- invalid event-rule operator/order/config.

Per-calendar and per-task-list accent values are optional `#RRGGBB` values. `null` means neutral JamesUI fallback. Icon IDs must exist in the local semantic registry.

Irrelevant child settings remain understandable but disabled/greyed in the later configuration UI.

## 12. Widget-instance independence

The same `widget.calendar-agenda` implementation must support multiple simultaneous independent `create()` instances.

Each instance owns independent:

- selected calendar/list IDs and order;
- domain enablement;
- mode;
- lookahead/lookback;
- row capacity settings;
- task ordering;
- all-day/location options;
- calendar/task-list presentation;
- advance-notice config;
- current day selection;
- scroll/gesture state;
- pending task mutations/Undo entries;
- dismissed notice state scope.

Changing one instance must not mutate another.

Block 11 does **not** redesign the generic Module Loader, which currently manages runtime modules by module ID. Block 11 proves instance safety through direct parallel lifecycle tests. Generic orchestration of multiple configured widget instances remains Block 14.

## 13. Future display horizon and provider ranges

`lookahead_days = N` means Today plus the next **N local calendar days** are inside the normal future display window. Therefore a default of `30` includes Today through Today+30; the exclusive normal end date is Today+31.

Each selected calendar inherits the widget default unless a per-calendar lookahead override is enabled.

For normal Agenda presentation, overall future day navigation/group horizon is the maximum normal lookahead among enabled selected calendars; in task-only mode it uses the widget-level `lookahead_days`.

Task provider data itself is not range-limited (`task lookahead = 0` means unrestricted/not applicable), but dated future tasks are presented only inside the widget's current normal future display horizon. Untimed incomplete tasks are always assigned to Today.

Advance-notice retrieval may extend a calendar provider range beyond the normal display horizon, but those extra events are **notice candidates only** until they enter the normal lookahead window; they must not leak into ordinary grouped/timeline/day event rows early.

### Day-mode historical range

`lookback_days = N` means Today and the previous N local calendar days are reachable in `day` mode. `0` means Today is the earliest day.

Calendar range start in `day` mode therefore includes `Today - lookback_days`; grouped/timeline normal range starts at Today.

## 14. Presentation modes

### `grouped`

- starts at Today;
- groups by local day;
- headings use `Heute`, `Morgen`, then localized date;
- calendar events/tasks combine under the ordering rules;
- no automatic past-day display.

### `timeline`

- starts at Today;
- chronological future presentation through the normal display horizon;
- no automatic past-day display;
- approved point/vertical-line language.

### `day`

- one selected local day;
- horizontal swipe moves exactly one calendar day;
- vertical scrolling handles entries inside the selected day;
- empty days are not skipped;
- Today header: `Heute · So, 4. Oktober`;
- other header: `Mo, 5. Oktober`;
- quiet empty state: `Keine Termine oder Aufgaben`;
- small accessible previous/next controls supplement swipe;
- backwards navigation stops at the lookback boundary;
- forward navigation stops at the current normal future display horizon.

Gesture direction locks after the initial movement: clearly horizontal means day navigation, clearly vertical means content scrolling. Exact threshold constants are implementation details tested on the primary tablet and are not user settings.

## 15. Current, ended and historical event visibility

For Today in all modes:

- running timed event: `start_at <= now < end_at` → visible;
- upcoming timed event: `start_at > now` → visible;
- ended timed event: `end_at <= now` → hidden from normal Today.

When `day` shows a past date inside lookback, all valid calendar-event projections for that historical day are shown regardless of current clock time.

All-day event is active on local date `D` when:

```text
start_date <= D < end_date
```

Thus an all-day event covering Today remains visible for the whole local day.

## 16. All-day and multi-day projections

### All-day

`show_all_day = true` by default.

If enabled:

- one display projection per covered local day;
- time label `Ganztägig`;
- never invent `00:00`;
- all-day calendar events sort before timed calendar events inside the calendar-event portion of a day;
- detail overlay preserves truthful original start/end dates.

`show_all_day = false` hides all all-day projections for that instance.

### Timed events crossing local midnight

One projection is created for every HA-local calendar day overlapped by the timed interval.

- start day → real start time, e.g. `18:00`;
- full intermediate day → `laufend`;
- end day → `bis <end time>`, e.g. `bis 10:00`.

For a two-day event: `22:00` then `bis 01:30`.

The underlying event remains one timed source event and the detail overlay always shows the full original interval.

## 17. Recurring events

Home Assistant calendar integrations expand recurring events into concrete occurrences for range results. JamesUI treats each returned occurrence independently.

No inferred series identity is used for collapse across different dates and no recurrence editing is introduced in Block 11.

## 18. Duplicate calendar events and source precedence

Cross-calendar logical duplicate key:

```text
normalized title + normalized start + normalized end + all_day
```

Normalization:

- trim/collapse whitespace;
- case-fold title using `de-DE` semantics;
- normalize timed instants to canonical ISO representation;
- all-day values remain canonical `YYYY-MM-DD` dates.

Location/description differences do not prevent collapse.

All contributing source IDs are retained as provenance.

If multiple selected calendars collapse into one logical event:

- the first calendar in the widget's configured calendar order is the **presentation owner**;
- its calendar default/rules determine icon, accent and advance-notice behavior;
- its location/description are primary when present;
- detail overlay lists the contributing source names when more than one source participated;
- conflicting optional values from secondary sources are not silently merged into invented text.

The cross-source logical key is also the base identity for device-local notice dismissal. Provider `occurrence_id` remains source-specific.

## 19. Task day assignment and visibility

Completed tasks are hidden from the normal Agenda in all modes, including historical day browsing.

Incomplete tasks:

- `due.kind = date` → assigned to that HA-local due date;
- `due.kind = datetime` → assigned to the HA-local calendar date/time represented by the instant;
- `due.kind = none` → assigned to Today only.

Future dated tasks are shown only while their due day is inside the widget's normal future display horizon. The provider remains unbounded; this filtering is widget presentation logic.

## 20. Task ordering

Per instance:

```text
task_order_mode = chronological | tasks_before | tasks_after
```

For `chronological` only:

```text
untimed_task_position = before | after
```

Default: `after`.

Rules:

- `tasks_before`: all tasks of the day before all calendar events;
- `tasks_after`: all tasks of the day after all calendar events;
- `chronological`: all-day calendar events form the all-day calendar bucket, timed tasks/calendar events then sort by local time;
- chronological + `untimed_task_position=before`: untimed Today tasks appear before the all-day/timed content;
- chronological + `untimed_task_position=after`: untimed Today tasks appear after all-day/timed content;
- within the calendar portion, all-day events remain before timed calendar events;
- ties sort deterministically by configured source order, then localized title.

If tasks are disabled, task-order settings are irrelevant/disabled.

## 21. Overdue carry-forward

Incomplete task whose due date/time is before Today/current time:

- remains on its original due day when that past day is viewed in `day` mode;
- is additionally projected into Today until completed;
- is not projected onto every intervening day;
- keeps its original provider due value;
- receives no warning color, badge or `seit X Tagen` label.

Carry-forward is presentation logic only.

## 22. Task completion and five-second Undo

Use exact UI duration:

```text
UNDO_DURATION_MS = 5000
```

Completion flow:

1. completion control executes `task.update` with `status: completed`;
2. while request is in flight, the same task's completion control is disabled;
3. on `success`, hide task immediately with instance-local optimistic mutation state;
4. add an independent Undo entry keyed by `(source_entity_id, uid)` for 5000 ms;
5. Todo stream remains authoritative and reconciles final state;
6. on action failure, optimistic state is removed and task remains/returns.

Undo:

- executes only `status: needs_action` for original source+UID;
- never rewrites title, due or description;
- on success, task is restored optimistically while stream confirmation arrives;
- failure leaves the backend-confirmed state and shows restrained feedback.

Multiple quick completions may have multiple active Undo entries; no single global undo target.

## 23. Task detail and editing

Activating the non-completion part of a task row opens a shared Overlay Service dialog.

Editable in Block 11 when the real source supports it:

- title;
- due date;
- due date/time;
- clear due;
- description;
- clear description.

Status remains controlled through completion/Undo.

Unsupported fields are read-only/disabled rather than pretending to be editable.

Save:

1. compute minimal patch containing only changed fields;
2. if patch is empty, close without action;
3. execute one `task.update`;
4. on success, close the overlay and let the stream reconcile the refreshed task;
5. on failure/rejection/unavailable, keep overlay open, preserve input and show concise user-readable feedback;
6. never expose raw HA service error text in normal UI.

No create/delete/move/reorder controls are present.

## 24. Calendar event detail overlay

Event row activation opens the shared Overlay Service with only real available fields:

- title;
- date/time or all-day range;
- location when present;
- description when present;
- contributing source names when duplicate collapse combined sources.

No fake placeholder such as `Kein Ort`.

Calendar event editing is out of scope.

## 25. Row geometry and optional location

Fixed row geometry:

- equal row height;
- stable time/date area;
- stable icon area;
- stable task-completion area where applicable;
- title gets remaining width with `minmax(0,1fr)` behavior;
- long titles ellipsize;
- font size does not shrink;
- icon/accent choice never changes geometry.

`show_location = false` default.

If enabled:

- reserve a stable second-line area for applicable rows;
- render actual location only when present;
- no fake location placeholder.

## 26. Timeline continuation and internal scrolling

The approved vertical point-and-line language is used.

For current rendered day/segment:

- hidden earlier rows → short dashed continuation upward;
- hidden later rows → short dashed continuation downward;
- no hidden content in direction → normal line termination;
- no permanent up/down arrow controls;
- dashed continuation never changes row height/alignment.

In `day` mode continuation refers only to hidden entries of the selected day.

Dash length/gap are visual implementation constants constrained by the existing Design System, not user config.

## 27. Visible-row modes and host sizing

```text
visible_items_mode = fixed | auto
```

Default: `auto`.

### Fixed

```text
max_visible_items default = 5
allowed = 3..8
```

Events/tasks count together. Day headings, source-status notices and advance notices do not count as item rows, but they consume real widget height.

If host height cannot display the configured item count simultaneously, rows remain full height and the content area scrolls internally; no partial row is shown.

### Auto

Compute the maximum count of complete fixed-height item rows that fits below the currently rendered header/controls/status/advance-notice regions inside the actual host allocation.

Rules:

- never compress row height;
- never show a partial row;
- recalc on real host allocation change;
- `max_visible_items` remains visible but disabled/greyed in config;
- extra content remains internally scrollable;
- widget never enlarges parent merely to reveal more rows;
- if required widget chrome plus one complete row cannot fit, render a restrained `too_small` state instead of clipping.

Minimum usable height is therefore derived from current chrome + one complete row, not a hard-coded product pixel value.

Block 14 later expresses Start widget spans through the host layout's logical grid.

## 28. Calendar presentation and event rules

Per selected calendar, per widget instance:

- default semantic icon;
- optional `#RRGGBB` accent.

Ordered event rules may override icon, accent and/or advance-notice days.

Supported operators:

- exact (`ist genau`);
- contains (`enthält`);
- starts with (`beginnt mit`).

Matching:

- case-insensitive `de-DE` text comparison after trim/collapse whitespace;
- title is always included;
- description/location may each be enabled as additional fields;
- a rule matches when its operator matches any enabled field;
- first matching rule wins;
- no regex in normal UI;
- rules are reorderable.

Presentation priority:

1. first matching rule;
2. presentation-owner calendar default;
3. neutral JamesUI fallback.

Color is marker/icon/fine accent only, never a bright full-row/card background.

Waste examples: `Gelber Sack`, `Biotonne`, `Restmüll`, `Papier`.

## 29. Task-list presentation

Each selected `todo.*` list may define per-widget-instance:

- default semantic icon;
- optional `#RRGGBB` accent.

No task keyword/title rule engine in Block 11.

## 30. JamesUI advance notices

The consumed Home Assistant Calendar subscription does not expose reminder/alarm metadata. JamesUI therefore never claims to show source reminders.

Block 11 instead provides an explicit JamesUI-owned **Vorlaufhinweis**.

### Configuration

Per calendar:

```text
advance_notice_days = 0..365
```

Default `0` = off.

An event rule may optionally specify its own `advance_notice_days = 0..365`:

- field omitted → inherit calendar default;
- `0` → explicitly disable for matched events;
- positive value → override calendar default.

First matching rule/presentation-owner precedence applies after duplicate collapse.

Examples:

```text
calendar default = 0
Zahnarzt = 7
Gelber Sack = 1
```

### Threshold semantics

Lead time uses HA-local calendar arithmetic, not fixed 24-hour milliseconds:

- timed event: subtract N local calendar days while preserving its local wall-clock start time;
- all-day event: subtract N local calendar days from its start date, threshold at local day start.

This avoids DST distortion.

### Provider range

For each selected calendar, provider retrieval end covers at least the maximum of:

- normal effective calendar lookahead;
- calendar default advance days;
- every configured rule advance days.

Events fetched only because of advance notice remain excluded from normal Agenda rows until they enter normal display horizon.

### Lifecycle and order

Eligible notice:

- threshold reached;
- event has not started;
- not dismissed for this widget instance/device.

Notices sort by event start ascending, then localized title.

At event start:

- notice disappears from notice region;
- event continues normally as a running Agenda event.

### Display

- normal compact state shows at most 2 notices;
- additional notices → `+N weitere Hinweise`;
- activating it expands remaining notices inside widget;
- notices do not count toward `max_visible_items`;
- notices consume real widget height;
- expanded notice area never grows host layout and may scroll internally.

### Dismissal persistence

Device-local storage key:

```text
jamesui-agenda-notice-dismissals-v1
```

Record is scoped by widget instance ID and logical occurrence key.

Dismissed occurrence does not reappear on that device after reload. If title/start/end/all-day identity changes, it is a different occurrence and may appear again.

Expired records are pruned at load and at HA-local day/event-boundary refresh so storage remains bounded.

## 31. Source errors, empty states and stale-data policy

Enabled source-specific failure renders a quiet notice, e.g.:

```text
Familienkalender derzeit nicht verfügbar
Einkaufsliste derzeit nicht verfügbar
```

Healthy siblings continue.

Disabled domain never emits its source/capability errors into that widget instance.

If every enabled domain is unavailable because HA is disconnected/timezone invalid, render overall state:

```text
Agenda derzeit nicht verfügbar
```

No cached remote event/task values are silently shown as current.

Healthy empty states remain distinct:

```text
Keine Termine oder Aufgaben
Keine Termine
Keine Aufgaben
```

Source-status notices do not count toward the configured item-row count but consume real height and therefore affect auto capacity.

## 32. Refresh and reconnect strategy

No periodic Home Assistant polling.

### Calendar provider

- remote `calendar/event/subscribe` only for currently requested ranges;
- identical range keys may be shared/ref-counted;
- local entity subscriptions track source existence/name/availability;
- generation/source guards block stale callbacks;
- reconnect/config change rebuilds only needed current subscriptions.

### Task provider

- one remote `todo/item/subscribe` per configured list;
- local entity subscription tracks feature/name/availability changes;
- semantic snapshot equality suppresses redundant capability publishes;
- generation/source guards block stale callbacks;
- reconnect rebuilds configured subscriptions.

### Widget time scheduler

Time-based presentation refresh belongs to the Agenda widget, not to a polling provider.

Each instance schedules only the next relevant boundary among:

- event start;
- event end;
- advance-notice threshold;
- HA-local midnight;
- Undo expiry.

After firing, recompute and schedule the next boundary. No second/minute interval loop.

At HA-local midnight, the widget recomputes Today, lookback/lookahead ranges and reissues calendar range subscription only when the absolute range changed.

├─ advance-notice region (optional)

## 37. Update and destroy semantics

All modules validate full next context/config before mutating mounted state.

### Providers

On update:

- validate next context/config first;
- increment generation before old remote callbacks can publish;
- clean obsolete local/remote subscriptions;
- activate new config/context;
- reconcile capability state from new source set.

On destroy:

- local/remote unsubscribe best-effort;
- unregister capability handles;
- late callbacks cannot publish.

### Action module

- register `task.update` on mount;
- unregister on update/destroy when registry/context changes;
- never retain raw `hass` references outside adapter context.

### Widget

On update:

- preserve mounted root identity where feasible;
- validate config before mutation;
- resubscribe only when capability/range/context changes;
- retain instance isolation;
- close only overlays owned by this instance via stale-safe Overlay close handle.

On destroy:

- remove capability/range listeners;
- cancel scheduler/Undo timers;
- disconnect ResizeObserver and DOM listeners;
- close only this instance's overlay;
- late async mutation completions cannot modify detached DOM.
