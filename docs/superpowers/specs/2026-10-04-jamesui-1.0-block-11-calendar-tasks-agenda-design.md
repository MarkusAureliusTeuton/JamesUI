# JamesUI 1.0 – Block 11 Calendar, Tasks and Agenda Design

_Date: 2026-10-04_
_Status: conversational design approved; written spec pending user review_

## 1. Purpose

Block 11 builds the real household Agenda domain on the clean JamesUI 1.0 architecture. It introduces:

- `provider.calendar` for explicitly configured Home Assistant `calendar.*` sources;
- `provider.tasks` for explicitly configured Home Assistant `todo.*` sources;
- a dedicated task-update action module exposing `task.update`;
- `widget.calendar-agenda` as the reusable presentation/interaction layer.

The widget must work as calendar-only, task-only or combined Agenda, support multiple independent widget instances, respect host-layout bounds, and never access raw Home Assistant APIs directly.

Success means:

- configured calendar events and tasks are displayed truthfully with Home Assistant timezone semantics;
- running, upcoming, historical, all-day and multi-day events behave consistently;
- tasks can be completed, undone for about five seconds and edited in Block 11;
- overdue tasks are carried into Today without rewriting their true due date;
- JamesUI-owned advance notices are available without pretending that source reminders exist;
- one unavailable source does not break healthy sibling sources;
- no stale backend data is silently presented as current;
- no final Start composition, loader-wide instance orchestration or production cutover occurs in this block.

## 2. Binding project constraints

Foundation rules remain binding:

- modules use `create(context, config)`, `mount(target)`, `update(nextContext, nextConfig)`, `destroy()`;
- widgets consume capabilities and actions only;
- providers/actions may use the Home Assistant Adapter;
- user/control commands go through the Action Registry;
- providers own Home Assistant data subscriptions;
- the Event Bus is not a second domain-state layer;
- no raw `hass`, Config Service, Router, Health Service, Design System object, Module Registry or Module Loader is given to the Agenda widget;
- no monkey-patches, Prototype overrides, version-polish layers, duplicate implementations or permanent compatibility shims;
- r11 remains production/reference until the later controlled cutover;
- OnePlus Pad 2 portrait remains the primary visual target;
- page scrolling belongs to the host layout, not the Agenda widget.

Cross-page sizing/scroll rules remain in `docs/JAMESUI_1_0_LAYOUT_PLANNING_NOTES.md`.

## 4. Architectural choice

Three approaches were considered:

1. **Range-based calendar capability + live task snapshot + dedicated semantic task action** — selected.
2. One large shared 1–365-day calendar snapshot for all configured calendars — rejected because it over-fetches and over-updates unrelated consumers.
3. Provider derives one union range from every widget-instance config — rejected because it couples providers to page/widget configuration orchestration.

The selected design keeps calendar reads range-based because each Agenda instance can need a different historical/future window. Tasks fit a live source snapshot because Home Assistant exposes each complete `todo.*` list as a subscription stream. Mutations remain semantic actions rather than leaking `todo.update_item` service syntax into the widget.

## 5. Current Home Assistant contracts this design relies on

### Calendar

Current Home Assistant developer documentation defines `calendar/event/subscribe` with `entity_id`, `start` and `end`. The subscription immediately returns the current event list for that range and pushes updates when the calendar entity changes. If event retrieval fails, the subscription payload uses `events: null`.

Important limitation: although Home Assistant's internal `CalendarEvent` model can contain fields such as `uid`, `recurrence_id`, `rrule` and status, the documented `calendar/event/subscribe` payload exposes only fields that have values among:

- `start`
- `end`
- `summary`
- `description`
- `location`

Block 11 therefore must not depend on calendar UID/recurrence metadata for display identity, deduplication or dismiss persistence.

Source reference:
`https://developers.home-assistant.io/docs/core/entity/calendar/`

### Todo

Current Home Assistant exposes `todo/item/subscribe` for one `todo.*` entity. It sends an initial `{items: [...]}` update and then pushes later list updates. Todo items include the truthful fields represented by Home Assistant's `TodoItem` model:

- `uid`
- `summary`
- `status`
- `due`
- `description`
- `completed`

The Todo entity exposes supported-feature flags including update, due-date, due-datetime and description support.

Sources:
- `https://developers.home-assistant.io/docs/core/entity/todo/`
- `https://github.com/home-assistant/core/blob/dev/homeassistant/components/todo/__init__.py`

### Todo update action

Home Assistant `todo.update_item` can update an existing task using its UID. Supported updates include rename, `needs_action | completed`, due date, due date/time and description. Current Home Assistant service validation permits `null` for due/description fields, so those extended fields can be explicitly cleared when the source supports them.

Sources:
- `https://www.home-assistant.io/actions/todo.update_item/`
- `https://github.com/home-assistant/core/blob/dev/homeassistant/components/todo/__init__.py`

## 7. `calendar.events` capability

`calendar.events` is a read-only range service published through the Capability Registry. It is not a user command and therefore does not belong in the Action Registry.

The available capability value exposes immutable metadata plus one read-side subscription function:

```text
{
  version: 1,
  time_zone: <validated HA IANA timezone>,
  configured_sources: [
    { entity_id, name }
  ],
  subscribe_ranges(request, listener) -> unsubscribe
}
```

A request contains one or more source ranges:

```text
{
  ranges: [
    {
      entity_id: "calendar.family",
      start_date: "2026-09-27",
      end_date: "2026-11-04"
    }
  ]
}
```

`start_date` is inclusive and `end_date` is exclusive, both expressed as Home-Assistant-local calendar dates. The provider converts them to the timezone-aware instants required by `calendar/event/subscribe`.

The listener receives one normalized range snapshot:

```text
{
  time_zone,
  sources: {
    "calendar.family": {
      status: "available" | "unavailable",
      reason: null | <stable reason>,
      events: [...]
    }
  }
}
```

Rules:

- each request may include only configured `calendar.*` sources;
- invalid/unconfigured source IDs are rejected by the capability interface rather than silently discovered;
- identical `(entity_id, start_date, end_date)` subscriptions may be shared internally with reference counting;
- a source payload with `events: null` becomes source-specific `unavailable`, not an empty successful calendar;
- one failed source does not make healthy siblings unavailable;
- full HA disconnection makes the top-level capability unavailable and tears down remote subscriptions;
- reconnect republishes an available service and consumers re-establish current requested ranges;
- stale callbacks from previous generations/ranges are ignored;
- `destroy()` unsubscribes every remote subscription.

### Normalized calendar event

```text
{
  occurrence_id,
  source_entity_id,
  title,
  description,
  location,
  all_day,
  start_date,
  end_date,
  start_at,
  end_at
}
```

Exactly one of these time representations is used:

- all-day: `start_date`/`end_date`, with exclusive `end_date`;
- timed: `start_at`/`end_at` as validated ISO instants.

`occurrence_id` is a JamesUI-local stable occurrence key derived only from fields actually available in the subscription payload. It must not be presented as a source UID.

Malformed events, invalid start/end ordering or mixed date/datetime representations are rejected rather than guessed.

## 8. `tasks.items` capability

`provider.tasks` owns one `todo/item/subscribe` stream per configured `todo.*` source while mounted.

Available capability value:

```text
{
  version: 1,
  time_zone,
  sources: {
    "todo.household": {
      status,
      reason,
      name,
      supported_features,
      capabilities: {
        can_update,
        can_set_due_date,
        can_set_due_datetime,
        can_set_description
      },
      items: [...]
    }
  }
}
```

Normalized task:

```text
{
  source_entity_id,
  uid,
  title,
  status,
  due: {
    kind: "none" | "date" | "datetime",
    value: null | <ISO date/instant>
  },
  description,
  completed_at
}
```

Rules:

- UID is required for an item to be mutable; malformed items without a usable UID are not exposed as editable/completable tasks;
- only `needs_action` and `completed` are accepted as normal statuses;
- due date vs due datetime remains distinct;
- datetime due values retain their real timezone-aware instant;
- description/completed timestamps are optional and remain `null` when absent;
- supported capabilities come from the real Home Assistant Todo entity feature mask;
- identical semantic snapshots are not republished merely because another callback object was received;
- one unavailable list is represented source-specifically while healthy sibling lists continue;
- full HA disconnection makes the capability unavailable and discards current item values rather than presenting stale lists as current;
- reconnect rebuilds current configured subscriptions;
- generation/source guards reject late callbacks after reconfiguration or reconnect;
- `destroy()` unsubscribes every remote subscription.

## 9. `task.update` action contract

Widget request:

```text
{
  type: "task.update",
  source_entity_id: "todo.household",
  uid: "<stable source uid>",
  patch: {
    title?,
    status?,
    due?,
    description?
  }
}
```

Patch rules:

- at least one field must be present;
- title must be a non-empty trimmed string when supplied;
- status must be `needs_action` or `completed`;
- due may set a date, set a datetime, or explicitly clear due when supported;
- description may set text or explicitly clear it when supported;
- unsupported patch fields are rejected;
- no raw Home Assistant service data is accepted from the widget.

Execution:

1. validate `todo.*`, UID and patch;
2. require a connected Home Assistant Adapter;
3. read the current Todo entity state/feature mask;
4. require `UPDATE_TODO_ITEM` and any field-specific due/description capability;
5. translate to `todo.update_item`, always identifying the item by UID;
6. return normalized Action Registry status `success | unavailable | rejected | error`.

The widget never calls generic `ha.service` for Todo updates.

## 10. Widget-instance model and validation

The same `widget.calendar-agenda` module must support multiple simultaneous independent `create()` instances in tests and future page composition.

Every instance owns independent:

- selected calendar IDs;
- selected todo-list IDs;
- domain enablement;
- presentation mode;
- look-ahead/lookback;
- density/visible-row settings;
- task ordering;
- all-day/location options;
- calendar icon/accent/rules;
- task-list icon/accent;
- advance-notice configuration;
- transient UI state and dismissed notices.

Changing one instance must not mutate another.

Block 11 does not redesign the generic Module Loader, which currently manages loaded runtime modules by module ID. Block 11 proves the widget implementation itself is instance-safe through direct parallel lifecycle tests. Generic orchestration of multiple configured widget instances remains Block 14.

### Domain enablement

Defaults:

```text
calendar_enabled = true
tasks_enabled = true
```

Invalid configurations:

- both domains disabled;
- calendar enabled with zero selected calendars;
- tasks enabled with zero selected todo lists.

Controls that become irrelevant because a parent option is disabled remain visible and understandable but disabled/greyed in the later configuration UI.

## 11. Presentation modes

### `grouped`

- starts at Today;
- groups by local calendar day;
- headings use `Heute`, `Morgen`, then localized date labels;
- calendar events and tasks are combined according to the instance ordering rules;
- no past day is automatically displayed.

### `timeline`

- starts at Today;
- presents one chronological future agenda across the configured window;
- no past day is automatically displayed;
- uses the approved point/vertical-line language.

### `day`

- shows exactly one selected local calendar day;
- horizontal swipe changes exactly one calendar day backward/forward;
- vertical scrolling handles entries within that day;
- empty calendar days remain reachable and are not skipped;
- today header example: `Heute · So, 4. Oktober`;
- other day example: `Mo, 5. Oktober`;
- empty state example: `Keine Termine oder Aufgaben`;
- small accessible previous/next controls supplement swipe so gesture is not the only navigation path;
- backwards navigation is bounded by `lookback_days` and never wraps.

Gesture handling locks direction after the initial movement: clearly horizontal means day navigation, clearly vertical means content scroll. Exact pixel/ratio thresholds are implementation constants verified by behavior tests and tablet acceptance, not user-configurable product settings.

## 12. Calendar look-ahead and day-mode lookback

Per Agenda widget instance:

```text
lookahead_days default = 30
allowed = 1..365
```

Each configured calendar inherits the instance value unless its per-calendar override is enabled. The disabled override input remains visible/greyed until activated.

`lookback_days`:

```text
default = 7
allowed = 0..365
```

Rules:

- lookback applies only to `day` mode;
- `0` means Today is the earliest reachable day;
- `grouped` and `timeline` still start at Today;
- lookback and lookahead are independent.

Task schema consistency may retain `lookahead_days = 0`, where `0` means unrestricted/not applicable, never zero tasks. It is not shown in normal task configuration unless a future source requires it.

## 13. Current, ended and historical event visibility

For Today in `grouped`, `timeline` and `day`:

- running events remain visible until their actual end;
- upcoming events are visible;
- already-ended timed events are hidden from the normal Today agenda once they end.

When `day` is viewing a past date inside `lookback_days`, the widget shows the full event history for that selected historical day rather than applying the current-time filter.

All-day events covering Today remain current for the whole local day.

## 14. All-day and multi-day projection

### All-day

Per instance:

```text
show_all_day = true
```

If enabled:

- each covered local day receives one display projection;
- time label is `Ganztägig`;
- no fake `00:00` time is created;
- all-day calendar events sort before timed calendar events inside the calendar-event portion of a day;
- task-order rules still control whether tasks come before/after calendar events;
- the detail overlay preserves the original full start/end date range.

`show_all_day = false` hides all all-day projections for that instance.

### Timed events crossing local midnight

A timed event receives one projection for every local day it overlaps.

Examples:

- start day: `18:00`;
- full intermediate day: `laufend`;
- end day: `bis 10:00`.

For a simple two-day event: start day `22:00`, next day `bis 01:30`.

The source event remains one timed event; the detail overlay always shows its truthful complete interval.

## 15. Recurring events

Home Assistant calendar integrations are responsible for expanding recurring events into individual occurrences in range results. JamesUI treats every returned concrete occurrence independently.

A shared series identity alone never causes occurrences on different dates to collapse.

Because the current subscription payload omits recurrence metadata, JamesUI does not invent recurrence editing or series semantics in Block 11.

## 16. Duplicate calendar events

After the widget selects its configured calendars, duplicate visible events collapse when these normalized fields match:

```text
title + start + end + all_day
```

The comparison normalizes whitespace/time representation consistently.

Location or description differences do not prevent collapse.

The resulting logical event retains all contributing `source_entity_id` values as provenance. Different source descriptions/locations are not arbitrarily merged into one invented value. The detail presentation may expose provenance/available source-specific details in a restrained way when needed.

## 17. Task ordering

Per instance:

```text
task_order_mode:
  chronological | tasks_before | tasks_after
```

For `chronological`:

```text
untimed_task_position:
  before | after
```

Default: `after`.

Rules:

- timed tasks participate chronologically with calendar events;
- untimed tasks use the configured before/after position only in chronological mode;
- `tasks_before` places all tasks before the day's calendar events;
- `tasks_after` places all tasks after the day's calendar events;
- irrelevant child settings are disabled/greyed in configuration;
- disabling tasks disables all task-order controls.

## 18. Overdue task carry-forward

An incomplete task with a past due date/time:

- remains visible on its original due day when that day is viewed through `day` lookback;
- is additionally carried into Today until completed;
- is not duplicated on every intervening day;
- keeps its original provider due value unchanged;
- receives no warning color, overdue badge or `seit X Tagen` copy.

Carry-forward is widget presentation logic only.

## 19. Task completion and five-second Undo

Each task row has a stable completion control separate from the row detail activation.

Completion flow:

1. execute `task.update` with `status: completed`;
2. on success, hide the row immediately using instance-local optimistic mutation state;
3. show `Aufgabe erledigt · Rückgängig` for approximately five seconds;
4. the Todo subscription remains the authoritative backend confirmation;
5. if the original completion action fails, remove the optimistic state and keep/restore the task.

Undo:

- operates on the original `(source_entity_id, uid)`;
- executes only `status: needs_action`;
- does not rewrite title, due or description;
- on successful Undo, restore the task optimistically while awaiting stream confirmation.

Multiple rapid completions retain independent task identities; they must not overwrite one global undo target.

The completion control is temporarily disabled while a mutation for the same task is in flight to avoid competing duplicate actions.

## 20. Task detail and editing

Tapping the non-completion part of a task row opens a shared overlay owned by the generic Overlay Service.

Block 11 editing includes:

- title;
- due date when supported;
- due datetime when supported;
- clearing due when the source supports the applicable due field;
- description when supported;
- clearing description when supported.

Status remains controlled through the normal completion/Undo interaction.

Only real source-supported edit controls are enabled. A source lacking an edit capability may still display a field read-only when the field exists.

Save behavior:

- compute a minimal patch containing only changed fields;
- execute one `task.update` action;
- keep the overlay open and retain user input if save fails;
- show a restrained user-readable error, not raw Home Assistant service text;
- close/refresh normally after successful confirmation/optimistic acceptance.

No create/delete/move/reorder controls are introduced in this block.

## 21. Calendar event detail overlay

Tapping a calendar event opens the shared Overlay Service with only truthful available data:

- title;
- date/time or all-day range;
- location when present;
- description when present;
- restrained source provenance when duplicate collapse combined sources.

No placeholder such as `Kein Ort` is rendered for absent optional fields.

Calendar event editing is out of scope.

## 22. Row geometry and optional location

Rows use fixed geometry:

- equal row height;
- stable time/date area;
- stable icon area;
- stable task-completion area where applicable;
- title consumes the remaining width with `minmax(0,1fr)` semantics;
- long titles ellipsize; font size never shrinks;
- icon/accent choice does not change geometry.

Per instance:

```text
show_location = false | true
```

When enabled, the widget reserves a stable second-line region so rows do not jump. Actual location text is rendered only when the event has one.

## 23. Timeline continuation and internal scrolling

The widget uses the approved vertical point-and-line language.

For the currently rendered day/segment:

- hidden earlier rows are indicated by a short dashed continuation upward;
- hidden later rows are indicated by a short dashed continuation downward;
- when no hidden content exists in a direction, the line terminates normally;
- there are no permanent up/down arrow controls;
- dashed continuation never changes row height or point alignment.

In `day` mode these continuations refer only to hidden entries inside the selected day. Horizontal day navigation remains separate.

Exact dash length/gap values are visual implementation details constrained by the existing Design System and verified during visual acceptance, not product configuration.

## 24. Visible-row modes and host sizing

Per instance:

```text
visible_items_mode = fixed | auto
```

### Fixed

```text
max_visible_items default = 5
allowed = 3..8
```

Calendar events and tasks count together. Day headings and advance notices do not count as item rows.

### Auto

The widget computes the maximum number of complete fixed-height rows fitting beneath its own current header/controls/notices inside the actual host allocation.

Rules:

- never compress row height;
- never show a partial row;
- recalculate on genuine host allocation changes;
- `max_visible_items` remains visible but disabled/greyed in configuration;
- additional content is reachable by internal vertical scrolling;
- the widget never grows its parent merely to reveal more rows;
- if the host cannot fit even one complete Agenda row in addition to required widget chrome, the placement is `too_small` rather than clipping content.

The minimum usable height is therefore derived from actual rendered header/chrome plus one complete row, not a hard-coded product pixel height.

Block 14 later expresses Start widget heights/spans through the host layout's logical grid.

## 25. Per-calendar presentation and event rules

Each selected calendar has per-widget-instance presentation:

- default semantic icon;
- default restrained accent color.

Ordered event rules may override icon and/or accent.

Supported title/text operators:

- exact (`ist genau`);
- contains (`enthält`);
- starts with (`beginnt mit`).

Rule behavior:

- first match wins;
- title is searched by default;
- description/location can be included as optional search fields per rule;
- no regex in the normal UI;
- rules are reorderable.

Presentation priority:

1. first matching event rule;
2. calendar default;
3. neutral JamesUI fallback.

Color is limited to marker/icon/fine accent; no bright full-row/card backgrounds.

Waste-calendar examples include `Gelber Sack`, `Biotonne`, `Restmüll`, `Papier`.

## 26. Per-task-list presentation

Each selected `todo.*` list may define per-widget-instance:

- default semantic icon;
- default restrained accent color.

Block 11 does not add keyword/title matching rules for individual tasks.

## 27. JamesUI advance notices

The normal Home Assistant calendar subscription payload does not expose reminder/alarm metadata. JamesUI therefore never presents source reminders it cannot observe.

Instead, Block 11 provides an explicitly JamesUI-owned **advance notice** (`Vorlaufhinweis`).

### Configuration hierarchy

Each calendar has:

```text
advance_notice_days = 0..365
```

`0` means off.

An event rule may optionally define its own `advance_notice_days = 0..365`. Omission means inherit the calendar default. A rule value of `0` explicitly disables a notice for matches even when the calendar default is non-zero.

First matching event rule still wins.

Examples:

```text
calendar default: 0
"Zahnarzt" rule: 7
"Gelber Sack" rule: 1
```

### Data-range implication

To discover events early enough, the effective calendar request end must cover at least the largest of:

- normal calendar `lookahead_days`;
- calendar default `advance_notice_days`;
- every configured event-rule `advance_notice_days` for that calendar.

Advance notice is therefore not silently limited by the normal 30-day display lookahead.

### Lifecycle

A notice becomes visible when its configured lead threshold is reached and remains eligible until event start.

At event start:

- it disappears from the dedicated notice area;
- the actual event remains in its normal Agenda position while running.

The user may dismiss a notice. Dismissal is per widget instance and concrete occurrence and prevents that notice from reappearing on the same device.

Because calendar subscription events do not expose a UID, dismissal keys use the same normalized logical occurrence signature used for duplicate handling rather than invented source identity.

### Display capacity

- at most two notices are visibly expanded in the normal compact state;
- further notices render as `+N weitere Hinweise`;
- activating that control expands the remaining notices inside the widget;
- notices do not count toward `max_visible_items`;
- their actual height still reduces the remaining Agenda row area;
- expanded notices never enlarge the host layout; internal scrolling handles overflow.

### Device-local dismissal persistence

Dismissed notice state is device-local UI state, not shared household configuration.

Use one versioned browser-local storage record scoped by widget instance. Expired entries are pruned no later than the event start/end boundary so storage cannot grow indefinitely.

A normal reload on the same tablet does not resurrect a dismissed occurrence.

## 28. Source errors, empty states and stale-data policy

### Source-specific errors

Example:

```text
Familienkalender derzeit nicht verfügbar
```

or:

```text
Einkaufsliste derzeit nicht verfügbar
```

Healthy siblings continue to render.

### Full Home Assistant outage

The widget renders a restrained overall unavailable state such as:

```text
Agenda derzeit nicht verfügbar
```

Remote cached data is not silently reused as current.

### Empty vs unavailable

Healthy source with no entries:

```text
Keine Termine oder Aufgaben
```

Calendar-only:

```text
Keine Termine
```

Task-only:

```text
Keine Aufgaben
```

An empty successful source must never be mislabeled as an outage, and an unavailable source must never be mislabeled as an empty successful source.

## 29. Refresh and reconnect strategy

### Calendar

No periodic Home Assistant polling.

The provider uses `calendar/event/subscribe` for every active shared range key. It rebuilds only when required by:

- capability consumer range changes;
- provider source configuration changes;
- HA reconnect;
- HA-local day rollover when a relative widget window shifts.

### Tasks

No periodic Home Assistant polling.

The provider uses one `todo/item/subscribe` per configured list and publishes semantic snapshot changes only.

### Local time-driven refresh

The Agenda widget/provider runtime may use local timers only for presentation-time boundaries:

- next event start;
- next event end;
- next advance-notice threshold;
- HA-local midnight/day rollover;
- Undo expiry.

It schedules the next relevant boundary rather than running a constant second/minute polling loop.

All timers/subscriptions are cleaned up in `destroy()`.

## 30. Widget structure and interaction

Logical structure:

```text
Agenda root
├─ header / mode / selected-day controls
├─ advance-notice region (optional)
├─ agenda content scroller
│  ├─ source-status rows as needed
│  └─ event/task rows
└─ transient feedback / Undo region
```

### Event row

- row activation opens event detail overlay;
- no direct mutation.

### Task row

- stable completion control performs completion;
- remaining row area opens task detail/edit overlay;
- controls do not overlap gesture/activation targets.

## 34. Update and destroy semantics

All modules validate complete next context/config before mutating mounted state.

### Providers

On update:

- generation increments before old remote callbacks can affect new state;
- obsolete subscriptions are cleaned;
- new config/context becomes active only after validation;
- capabilities are reconciled from the new source set.

On destroy:

- every local/remote unsubscribe runs best-effort;
- timers are cleared;
- capability handles unregister;
- later callbacks cannot publish.

### Widget

On update:

- preserve mounted root identity where feasible;
- unsubscribe/resubscribe only when capability/action/context identity or relevant config changes;
- retain independent instance state;
- close only overlays owned by this instance using the Overlay Service's stale-safe close behavior.

On destroy:

- remove capability/range listeners;
- cancel timers/ResizeObserver/DOM listeners;
- close only this instance's current overlay;
- leave no active mutation callbacks capable of changing detached UI.
