# JamesUI 1.0 – Block 9 `provider.weather` Design Specification

_Date: 2026-10-03_
_Status: design written; awaiting user review_

## 1. Purpose

Block 9 introduces the canonical JamesUI 1.0 weather data provider: `provider.weather`.

The provider owns Home Assistant weather-source selection, weather/forecast subscriptions, normalization, sun data, moon phase/illumination, precipitation timing and the semantic atmosphere model used by later visual modules. It publishes stable capabilities and contains no UI rendering.

Block 10 will consume these capabilities to build the visible Weather Today hero and forecast overlay. Block 9 must therefore produce truthful, unit-aware, immutable data without leaking Home Assistant entity shapes into widgets.

The r11 weather helpers are behavior evidence only. Their useful rules are reimplemented behind the new provider contract; panel coupling, Unicode/SVG rendering, background URLs and implicit fallbacks are not ported.

## 2. Scope

Block 9 delivers:

- one provider module with ID `provider.weather`;
- six independently published capabilities:
  - `weather.current`
  - `weather.daily`
  - `weather.hourly`
  - `weather.sun`
  - `weather.moon`
  - `weather.atmosphere`
- deterministic weather-source selection;
- Home Assistant forecast subscriptions for supported forecast types;
- canonical forecast normalization;
- Daily fallback aggregation from `twice_daily` or `hourly` when true Daily is unavailable/unusable;
- first expected precipitation time derived only from true Hourly data;
- sun-period normalization;
- reliable local moon phase/illumination fallback without an Internet service;
- semantic atmosphere/background-selection inputs without rendering or asset URLs;
- explicit `available`, `unavailable` and `not_configured` capability states;
- complete subscription cleanup and stale-async protection;
- one low-frequency provider refresh for time-derived values;
- the smallest required HA Adapter extension for Home Assistant timezone access;
- architecture and regression tests.

Block 9 does **not** deliver:

- Weather Today markup or styling;
- forecast overlay UI;
- icon selection/rendering;
- Alpine image rendering;
- translated weather labels;
- calendar, house or Dynamic Button behavior;
- Start-page composition;
- production bootstrap/cutover changes;
- changes to the r11 production weather implementation.

## 3. Module identity and location

The provider lives under the existing module boundary:

```text
custom_components/jamesui/frontend/modules/provider.weather/
  manifest.js
  index.js
  normalize.js
  forecast.js
  moon.js
  atmosphere.js
```

The exact helper-file split may be reduced if implementation remains clearly bounded, but weather source/lifecycle orchestration, forecast normalization, astronomy and atmosphere mapping must remain separable pure concerns rather than one large file.

Canonical manifest:

```js
{
  id: "provider.weather",
  type: "provider",
  version: "1.0.0",
  core_api: "1.x",
  depends_on: [],
  requires_capabilities: [],
  provides_capabilities: [
    "weather.current",
    "weather.daily",
    "weather.hourly",
    "weather.sun",
    "weather.moon",
    "weather.atmosphere"
  ],
  config_schema: "provider.weather/v1"
}
```

The provider consumes only the standard provider context:

```text
events
overlays
capabilities
actions
module
homeAssistant
```

It must not receive raw `hass`, Config Service, Router, Health, Module Registry/Loader, Design System or asset internals.

## 4. Provider configuration

Version-1 accepted configuration is intentionally small:

```js
{
  entity_id?: string,
  outdoor_temperature_entity_id?: string,
  moon_entity_id?: string,
  illuminance_entity_id?: string
}
```

These fields correspond to the canonical Block-5 `data_sources.weather` migration targets.

Rules:

- unknown config keys are rejected;
- supplied values must be non-empty entity-ID strings;
- `entity_id`, when supplied, must have the `weather.` domain;
- optional sensor overrides are not guessed from friendly names;
- config is validated atomically before lifecycle mutation;
- `update()` with invalid config leaves all existing sources/subscriptions/capability data untouched;
- changing valid source config triggers a controlled source/subscription reconciliation.

No precipitation threshold, colors, labels, asset names or display formatting become user configuration in Block 9.

## 5. Weather-source selection

Weather source selection has two modes.

### Explicit source

When `entity_id` is configured:

1. that exact `weather.*` entity is the only weather source;
2. no alternate weather entity is substituted when it is missing, `unknown` or `unavailable`;
3. when the configured source itself is unusable, `weather.current`, `weather.daily` and `weather.hourly` are unavailable and old forecast data is invalidated;
4. current/forecast capabilities report explicit reasons instead of silently changing source.

This prevents JamesUI from unexpectedly switching to a different location/provider.

### Automatic source

When `entity_id` is omitted:

1. inspect Home Assistant `weather.*` entities through the HA Adapter;
2. select the lexicographically first entity ID whose state is neither `unknown` nor `unavailable`;
3. if the selected automatic source later becomes unusable and another usable weather entity exists, deterministic automatic reselection is allowed;
4. if weather entities exist but all are unusable, weather capabilities are `unavailable`;
5. if no `weather.*` entity exists while Home Assistant is connected, weather capabilities are `not_configured`.

When Home Assistant is disconnected, the provider must not infer `not_configured`; HA-dependent capabilities are `unavailable` with a connection reason because discovery cannot be trusted.

## 6. Optional source rules

### Outdoor-temperature override

`outdoor_temperature_entity_id` is an explicit optional override only.

- If configured and its state parses as a finite numeric temperature, it replaces the Weather entity's current `temperature` value.
- The unit follows the override entity's unit when the override is used.
- If the override is missing/unavailable/malformed, current weather remains usable using the Weather entity temperature when available.
- No name-based or area-based outdoor-temperature sensor heuristic is added in Block 9.

This avoids the r11 risk of choosing an unrelated temperature sensor because its name contains words such as “garden” or “weather”.

### Illuminance

`illuminance_entity_id` is explicit only.

- A valid finite numeric state becomes `weather.atmosphere.ambient_lux`.
- A missing/unavailable/malformed illuminance source results in `ambient_lux: null` and does not make the whole atmosphere capability unavailable.
- No automatic illuminance discovery is used.

### Moon entity

Moon source preference is:

1. valid configured `moon_entity_id` whose state is one of the eight canonical moon phases;
2. otherwise, while connected, the lexicographically first `sensor.*` entity whose current state is one of those eight phases;
3. otherwise local astronomical calculation.

Unlike the weather source, an unusable configured Moon entity does not suppress the safe local astronomical fallback because moon phase/illumination does not depend on selecting a home/weather location.

## 7. Capability value rules

All published capability values are plain deeply immutable data.

General rules:

- numeric measurements remain numbers;
- missing optional measurements are `null`, never invented zeroes or display dashes;
- timestamps are ISO-8601 strings or `null`;
- units are explicit and remain the Home Assistant source units;
- Block 9 does not localize/format values for display;
- entity objects from Home Assistant are never published directly;
- mutable forecast/event objects are copied and normalized before publishing;
- one capability becoming unavailable must not automatically invalidate unrelated capabilities.

## 8. `weather.current`

`weather.current` represents normalized current conditions plus the next precipitation time derived from true Hourly data when available.

Canonical value:

```js
{
  source_entity_id: string,
  condition: string | null,
  temperature: number | null,
  temperature_unit: string | null,
  temperature_source_entity_id: string | null,
  apparent_temperature: number | null,
  humidity: number | null,
  dew_point: number | null,
  pressure: number | null,
  pressure_unit: string | null,
  cloud_coverage: number | null,
  visibility: number | null,
  visibility_unit: string | null,
  wind_speed: number | null,
  wind_gust_speed: number | null,
  wind_speed_unit: string | null,
  wind_bearing: number | null,
  uv_index: number | null,
  next_precipitation_at: string | null,
  next_precipitation_probability: number | null
}
```

`condition` preserves Home Assistant's normalized weather-condition identifier when it is a non-empty string. Block 9 does not translate it.

`temperature_source_entity_id` is the explicit override entity when successfully used; otherwise it is the weather source entity when that entity supplies the temperature; otherwise `null`.

The current capability may be available with some nullable fields if the Weather entity itself is usable but does not expose every optional attribute.

## 9. Forecast subscription strategy

Forecasts are owned exclusively by the provider.

The provider evaluates the selected Weather entity's `supported_features` and establishes independent Home Assistant `weather/subscribe_forecast` subscriptions for each supported type needed by the contract:

- `daily`
- `hourly`
- `twice_daily`

Rules:

- true Hourly is subscribed whenever supported because it powers `weather.hourly` and exact precipitation timing;
- true Daily is subscribed whenever supported and is the preferred source of `weather.daily`;
- Twice-Daily is subscribed when supported because it is the first Daily fallback;
- unsupported types are not requested speculatively;
- failure or unusable payload of one forecast type does not invalidate successful forecast types;
- `weather.daily` selects the highest-priority **usable** forecast source, so a failed/empty true-Daily stream may fall through to a usable Twice-Daily or Hourly stream;
- subscription callbacks are generation/source guarded so events from an obsolete source/configuration cannot overwrite current capabilities;
- source changes, disconnects, updates and destroy invalidate prior generations and unsubscribe old remote subscriptions best-effort;
- forecast data is never retained as available stale data after HA disconnect/source invalidation.

Because the current Module Loader lifecycle is synchronous, `mount()`/`update()` start forecast subscription reconciliation without returning an unresolved lifecycle promise. Any asynchronous subscription failure is caught inside the provider and reflected through capability state rather than becoming an unhandled rejection.

## 10. Home Assistant timezone boundary

Correct calendar-day aggregation cannot depend on the tablet/browser timezone.

Block 9 therefore adds one narrow method to the existing Home Assistant Adapter:

```text
homeAssistant.timeZone() -> string | null
```

Contract:

- while connected, return Home Assistant's configured IANA timezone (`hass.config.time_zone`) when it is a non-empty string;
- otherwise return `null`;
- do not expose the entire Home Assistant config object to modules;
- existing adapter disconnected-state protections remain unchanged.

The Weather provider uses this timezone for:

- deriving every canonical Daily `YYYY-MM-DD` date key;
- grouping Hourly/Twice-Daily records into home-local calendar days;
- deciding whether a future precipitation forecast occurs “today”.

If a valid Home Assistant timezone is unavailable, the provider must not silently use the browser/process timezone or source-offset date as a substitute for home-local day semantics.

In that state:

- `weather.hourly` may remain available because its absolute timestamps remain truthful;
- `weather.current` may remain available but both next-precipitation fields are `null`;
- `weather.daily` is `unavailable` with reason `timezone_unavailable`, including when a true Daily stream exists, because the canonical Daily contract requires a trustworthy home-local `date`;
- no Hourly/Twice-Daily → Daily aggregation is attempted.

## 11. Canonical Hourly forecast

`weather.hourly` is published only from a genuine Home Assistant `hourly` forecast subscription.

Twice-Daily is never relabeled as Hourly.

Canonical value:

```js
{
  source_entity_id: string,
  units: {
    temperature: string | null,
    pressure: string | null,
    precipitation: string | null,
    wind_speed: string | null,
    visibility: string | null
  },
  items: [
    {
      datetime: string,
      condition: string | null,
      temperature: number | null,
      apparent_temperature: number | null,
      precipitation: number | null,
      precipitation_probability: number | null,
      humidity: number | null,
      pressure: number | null,
      wind_speed: number | null,
      wind_gust_speed: number | null,
      wind_bearing: number | null,
      cloud_coverage: number | null,
      uv_index: number | null
    }
  ]
}
```

Normalization rules:

- entries without a valid parseable `datetime` are dropped;
- remaining entries are sorted ascending by timestamp;
- numeric fields are finite-number-or-null;
- probability/percentage fields are clamped to the semantic 0–100 range only when source numbers are finite; malformed source values become `null` rather than being guessed;
- no display rounding is applied except where the underlying capability contract explicitly defines it.

An empty/malformed Hourly event cannot publish `available` with fake items; it results in an explicit unavailable `empty_data` or `invalid_payload` reason.

## 12. Canonical Daily forecast

`weather.daily` uses the highest-priority usable source in this order:

```text
true daily
→ otherwise twice_daily aggregation
→ otherwise hourly aggregation
→ otherwise unavailable
```

A source is usable only when its subscription succeeded and normalization yields at least one valid item. Daily publication additionally requires a valid Home Assistant timezone.

The published value identifies its origin:

```js
{
  source_entity_id: string,
  forecast_source: "daily" | "twice_daily" | "hourly",
  units: { ...same unit family... },
  items: [
    {
      date: "YYYY-MM-DD",
      datetime: string,
      condition: string | null,
      temperature_high: number | null,
      temperature_low: number | null,
      precipitation: number | null,
      precipitation_probability: number | null,
      humidity: number | null,
      pressure: number | null,
      wind_speed: number | null,
      wind_gust_speed: number | null,
      wind_bearing: number | null,
      cloud_coverage: number | null,
      uv_index: number | null
    }
  ]
}
```

### True Daily normalization

For a real `daily` item:

- `temperature` maps to `temperature_high`;
- `templow` maps to `temperature_low`;
- the original valid datetime is retained;
- `date` is derived from that instant in the Home Assistant timezone;
- the source condition and optional measurements are copied/normalized directly.

### Twice-Daily aggregation

Records are grouped by Home Assistant local date.

For each day:

- `temperature_high` is the maximum finite temperature/temperature-high information available across the day's records;
- `temperature_low` is the minimum finite `templow`/temperature information available;
- the `is_daytime === true` record is preferred as the representative condition/`datetime`; otherwise the earliest valid record is used;
- precipitation amounts are summed across the component forecast periods when finite;
- precipitation probability is the maximum finite probability;
- humidity, pressure and cloud coverage are arithmetic means of finite values;
- wind speed and gust are maxima;
- UV index is the maximum finite value;
- wind bearing comes from the representative condition record when finite, rather than inventing a vector average.

### Hourly aggregation

Records are grouped by Home Assistant local date.

For each day:

- high/low are max/min of finite hourly temperatures;
- precipitation amount is summed;
- precipitation probability is the maximum;
- humidity, pressure and cloud coverage are arithmetic means;
- wind speed/gust and UV index are maxima;
- the representative condition/`datetime` comes from the valid record closest to local 12:00; ties choose the earlier record;
- wind bearing comes from that representative record when finite.

Daily items are sorted ascending by `date` and capped at a maximum of seven calendar days.

## 13. First expected precipitation

A precise statement such as “rain from 14:00” is allowed only from true Hourly data.

Block 9 uses a fixed product rule inherited from the useful r11 behavior:

A true Hourly record is precipitation-relevant when either:

- finite `precipitation_probability >= 40`, or
- finite `precipitation > 0`, or
- the normalized condition is one of `rainy`, `pouring`, `lightning-rainy`, `snowy-rainy`, `hail`.

The provider selects the earliest matching Hourly item that:

- is not before the current instant;
- falls on the current Home Assistant-local calendar day.

It publishes the original ISO datetime in `weather.current.next_precipitation_at` and the finite probability when present.

Daily/Twice-Daily data may communicate daily precipitation probability through `weather.daily`, but may never be converted into an artificial clock time.

If no true Hourly data, no trustworthy Home Assistant timezone or no same-day matching item exists, both next-precipitation fields are `null`.

## 14. `weather.sun`

Source is exclusively the standard `sun.sun` entity through the HA Adapter.

Canonical value:

```js
{
  source_entity_id: "sun.sun",
  is_up: boolean | null,
  elevation: number | null,
  azimuth: number | null,
  period: "day" | "golden" | "twilight" | "night" | null,
  next_rising: string | null,
  next_setting: string | null
}
```

Period derivation when elevation is finite:

```text
elevation < -6°  → night
-6° to < 1°      → twilight
1° to < 12°      → golden
>= 12°           → day
```

If elevation is unavailable but the entity state is definitively `above_horizon` or `below_horizon`, the provider may fall back only to `day` or `night`. It must not fabricate `golden` or `twilight` without elevation.

Missing/unavailable `sun.sun` makes `weather.sun` unavailable but does not invalidate weather or moon capabilities.

## 15. `weather.moon`

Canonical phase identifiers are exactly:

```text
new_moon
waxing_crescent
first_quarter
waxing_gibbous
full_moon
waning_gibbous
last_quarter
waning_crescent
```

Canonical value:

```js
{
  phase: string,
  illumination_percent: number,
  waxing: boolean,
  phase_source: "home_assistant" | "calculated",
  illumination_source: "calculated",
  source_entity_id: string | null,
  source_issue: string | null
}
```

Phase behavior:

- use the selected Moon entity's recognized phase when valid;
- otherwise use the local astronomical calculation;
- if an explicitly configured Moon entity is missing/unavailable/invalid, retain that diagnostic in `source_issue` while still publishing the reliable calculated result;
- the local result is never described as Home Assistant-sourced.

Illumination is calculated locally even when phase comes from a Home Assistant Moon entity so the capability has one predictable illumination contract.

### Local astronomical calculation contract

The fallback must be a pure local calculation with no Internet/API/runtime package dependency.

It must **not** reuse the old r11 shortcut of only `fixed epoch + constant synodic month` as the production algorithm.

The implementation uses UTC Julian-day based solar/lunar geometry sufficient to determine geocentric Sun–Moon elongation for phase and illuminated fraction. The code must document the astronomical formula source/derivation and any third-party formula provenance/license if formulas are adapted rather than independently implemented.

Derived values:

- normalize geocentric lunar elongation to `[0°, 360°)`;
- illuminated fraction uses the elongation-derived phase angle and is returned as `illumination_percent` in `[0, 100]`;
- `waxing` is true from new moon through (but not after) full moon according to normalized elongation;
- the eight phase buckets are equal 45° sectors centered on the canonical phases:
  - 0° new moon
  - 45° waxing crescent
  - 90° first quarter
  - 135° waxing gibbous
  - 180° full moon
  - 225° waning gibbous
  - 270° last quarter
  - 315° waning crescent
- exact sector-boundary behavior is deterministic and covered by tests.

Block 9 does not calculate moonrise/moonset, altitude, azimuth or observer-specific orientation because those require observer coordinates and are unnecessary for the accepted Start experience.

## 16. Moon reliability acceptance

Because the user explicitly selected the calculated fallback only if it is trustworthy, Block 9 treats astronomy verification as an acceptance requirement, not an optional unit test.

Tests must include published astronomical reference timestamps covering multiple lunations and at minimum:

- new moon;
- first quarter;
- full moon;
- last quarter;
- waxing and waning dates away from boundaries.

Acceptance expectations:

- the calculated phase bucket at reference phase events matches the canonical event phase;
- calculated illumination is near the physical reference expectation (approximately 0% at new, 50% at quarters, 100% at full) within an explicitly documented tolerance appropriate to the implemented low-cost astronomy model;
- waxing/waning direction matches reference chronology;
- malformed dates are rejected rather than producing a plausible-looking moon value.

If implementation cannot meet these reference tests reliably, Block 9 must not silently weaken the tests; the local fallback must be removed and the capability must revert to Home Assistant-only semantics before merge.

## 17. `weather.atmosphere`

This capability provides semantic scene inputs only. It never returns CSS, an image element or an asset URL.

Canonical value:

```js
{
  weather_class: "clear" | "cloudy" | "rain" | "snow" | "fog" | null,
  period: "day" | "golden" | "twilight" | "night" | null,
  scene_key: "clear-day" | "cloudy-day" | "rain-day" | "snow-day" | "fog" | "dusk" | "clear-night" | "cloudy-night" | null,
  ambient_lux: number | null
}
```

Weather-class mapping:

```text
sunny, clear-night                 → clear
partlycloudy, cloudy, windy,
windy-variant, exceptional        → cloudy
rainy, pouring, lightning,
lightning-rainy, hail,
snowy-rainy                       → rain
snowy                             → snow
fog                               → fog
unknown/unrecognized              → null
```

Scene-key mapping follows the retained Alpine asset family without exposing its file paths:

- fog always maps to `fog`;
- known weather during `golden`/`twilight` maps to `dusk` except fog, which remains `fog`;
- night + clear → `clear-night`;
- night + any other known weather class → `cloudy-night` because there is no approved separate rain/snow-night asset;
- day + clear → `clear-day`;
- day + cloudy → `cloudy-day`;
- day + rain → `rain-day`;
- day + snow → `snow-day`;
- unknown weather class does not get forced to cloudy; `scene_key` remains `null` unless another independently valid semantic mapping applies.

The actual mapping from `scene_key` to local WebP is a later asset/widget responsibility.

`weather.atmosphere` is available only when enough current/sun data exists to provide meaningful semantic atmosphere information. HA disconnect must not leave a stale atmosphere snapshot marked available.

## 18. Capability status and reason semantics

Capability Registry status remains the existing normalized contract:

```text
available
unavailable
not_configured
```

Block 9 uses concise machine-readable reason strings. At minimum the implementation distinguishes:

```text
home_assistant_disconnected
source_missing
source_unavailable
sources_unavailable
unsupported
subscription_failed
invalid_payload
empty_data
timezone_unavailable
no_weather_source
sun_unavailable
```

Rules:

- `not_configured` is used only when HA is connected and automatic discovery proves that no Weather entity exists;
- an explicit configured weather source that is missing is `unavailable`, not `not_configured`;
- unsupported Hourly is `weather.hourly: unavailable` and must not invalidate Daily/Current;
- true Daily unsupported/failed may still produce available Daily through usable Twice-Daily/Hourly aggregation;
- HA disconnect immediately invalidates HA-dependent available snapshots rather than leaving stale data exposed;
- calculated Moon may remain available while HA is disconnected because it is independently recomputed and is not stale HA data;
- if a previously HA-backed moon phase becomes unavailable/disconnected, the provider switches that capability to a calculated phase rather than retaining the stale entity phase.

## 19. Lifecycle and data flow

The provider follows the standard synchronous module lifecycle:

```text
create(context, config)
mount(target)
update(nextContext, nextConfig)
destroy()
```

The provider renders no DOM; `target` is ignored except for lifecycle compatibility.

### `create()`

- validates provider context shape needed for Block 9 (`capabilities`, `homeAssistant`, module identity);
- validates configuration;
- performs no remote subscription side effect.

### `mount()`

- registers all six declared capability handles;
- subscribes to HA connection changes;
- subscribes/reconciles relevant weather-domain, selected entity, `sun.sun`, optional override and optional Moon/illuminance sources;
- performs an immediate synchronous state reconciliation from adapter-visible states;
- starts guarded asynchronous forecast-subscription reconciliation;
- starts exactly one provider-owned low-frequency refresh timer (five-minute cadence) for time-derived values only: calculated Moon and `next_precipitation_at`/probability from already-cached true Hourly data;
- the refresh timer must not poll Home Assistant or call forecast APIs;
- repeated mount must not duplicate capability providers, subscriptions or timers.

### `update()`

- validates next config fully before mutation;
- increments/invalidates the async source generation before replacing subscriptions;
- preserves Capability Registry ownership handles while replacing underlying source subscriptions;
- publishes new status/data only from the newly selected generation;
- does not expose stale old-source data after the update boundary;
- preserves the single refresh timer rather than creating additional timers.

### `destroy()`

- invalidates the active async generation;
- removes all local HA Adapter subscriptions;
- invokes all remote forecast unsubscribe functions best-effort and absorbs cleanup promise failures;
- clears the refresh timer;
- unregisters all six capability handles;
- is idempotent;
- post-destroy remote callbacks/timer work cannot publish.

## 20. Pure helper boundaries

To keep provider orchestration understandable and independently testable, calculations are pure functions wherever practical.

Expected pure responsibilities:

- finite-number/null normalization;
- weather source selection from normalized adapter entity lists;
- current-condition normalization;
- Hourly normalization;
- Daily normalization/aggregation;
- Home Assistant-local date grouping with explicit IANA timezone input;
- first precipitation selection with explicit `now` + timezone parameters;
- sun-period derivation;
- moon astronomy from an explicit Date/time input;
- atmosphere class/scene-key mapping.

Pure helpers must not read `window`, `document`, raw `hass`, localStorage or implicit process/browser locale/timezone state.

## 21. Testing strategy

### Manifest / registry

- provider manifest validates;
- exact six capabilities are declared;
- no unrelated dependency/capability is introduced.

### Config/source selection

- explicit source always wins;
- explicit missing/unavailable source never falls back;
- automatic source is deterministic and may reselect only in automatic mode;
- no-source vs all-sources-unavailable statuses are distinct;
- optional temperature/illuminance failures do not collapse unrelated capabilities;
- invalid updates are atomic.

### HA Adapter timezone

- connected adapter returns configured IANA timezone;
- missing/invalid/disconnected config returns `null`;
- raw HA config is not exposed as a new module context object.

### Forecast

- supported-feature subscriptions are exact and independent;
- real Hourly stays Hourly;
- Daily priority is highest-priority usable true Daily → Twice-Daily → Hourly;
- malformed forecast entries are safely filtered;
- Daily aggregation follows the exact numeric rules in this spec;
- representative Hourly condition is closest to local noon;
- Home Assistant timezone rather than process/browser timezone determines local dates;
- no timezone makes Daily unavailable rather than guessed;
- stale source-generation events cannot overwrite current data;
- disconnect clears stale available forecast capabilities;
- failed one-type subscription does not collapse the others.

### Precipitation

- only true Hourly can produce `next_precipitation_at`;
- threshold/condition/positive-precipitation rules are covered;
- past records are ignored;
- tomorrow's rain does not become “today at ...”;
- Daily/Twice-Daily never creates a clock time;
- five-minute refresh advances/removes stale next-precipitation values without polling HA.

### Sun

- elevation thresholds are exact at boundaries;
- elevation missing falls back only to day/night from horizon state;
- missing/unavailable sun is explicit.

### Moon

- HA phase preference and deterministic auto-discovery;
- invalid/missing configured Moon falls back to calculated result with diagnostic metadata;
- astronomy reference tests from section 16;
- deterministic eight-sector boundaries;
- illumination constrained to 0–100;
- no network/runtime dependency;
- calculated Moon is refreshed by the single provider timer and can remain truthful during HA disconnect.

### Atmosphere

- every canonical HA weather condition maps correctly;
- unknown condition does not become fake cloudy weather;
- fog/dusk/night mappings follow the exact rules;
- atmosphere contains scene keys, never asset URLs;
- explicit illuminance is nullable and independent.

### Lifecycle

- mount/update/destroy do not leak local/remote subscriptions;
- repeated mount does not double-register capability providers;
- exactly one time-derived refresh timer exists per mounted provider instance;
- destroy clears it and is idempotent;
- async callback/timer after destroy/update cannot publish.

### Architecture

Permanent guards must reject:

- direct `hass` access inside `provider.weather`;
- Config Service import/use;
- UI/DOM/CSS/icon/asset rendering inside provider;
- legacy `Panel.prototype` or r11 imports;
- network fetch/XHR for weather/moon data;
- browser/process timezone/locale used for forecast-day semantics;
- hard-coded Alpine URLs;
- changes to production `jamesui-entry.js`.

Full `Validate JamesUI` regression remains green for Blocks 0–8 and retained r11 behavior.

## 22. Review focus before merge

Whole-branch review must explicitly verify:

1. **Truthfulness:** no Daily/Twice-Daily data creates false Hourly precision or rain times.
2. **Source stability:** explicit Weather source can never silently switch; automatic mode is deterministic.
3. **Timezone correctness:** all Daily grouping/date keys and “today” semantics use HA timezone or refuse derivation.
