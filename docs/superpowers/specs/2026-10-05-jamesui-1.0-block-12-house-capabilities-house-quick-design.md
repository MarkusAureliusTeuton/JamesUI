# JamesUI 1.0 – Block 12 House Capabilities and House Quick Design

_Date: 2026-10-05_
_Status: conversational design approved; written spec pending user review_

## 1. Purpose

Block 12 introduces the real House-domain read layer and the reusable `widget.house-quick` status/navigation widget on the clean JamesUI 1.0 architecture.

House Quick is not a control surface. It is a compact set of status buttons that answer at a glance what is happening in the home and navigate to later detail/control pages.

The Block 12 domain consists of:

- heating zones;
- normal lighting;
- ambient lighting;
- household-device status;
- configurable energy monitoring.

Windows/doors, ventilation and scenes are intentionally not part of House Quick. Scene control remains a separate widget/topic in Block 13.

Success means:

- all displayed data is backed by explicitly configured real Home Assistant / KNX-backed sources;
- no House Quick button reads raw Home Assistant state directly;
- KNX remains the source of truth for heating grouping and control semantics;
- lighting and ambient lighting are mutually exclusive groups;
- household-device states are normalized into one reusable contract;
- energy buttons can use different sources, averaging windows and thresholds;
- button severity is consistent across all House Quick domains;
- every visible button can navigate semantically to its later detail page;
- every House Quick widget instance can independently select and order its buttons;
- no scene control, final Start composition, final detail pages or production cutover is implemented in this block.

## 2. Binding project constraints

Foundation rules remain binding:

- modules use `create(context, config)`, `mount(target)`, `update(nextContext, nextConfig)`, `destroy()`;
- widgets consume capabilities and actions only;
- providers may use the Home Assistant Adapter;
- user interactions go through the Action Registry;
- providers own Home Assistant subscriptions/history access;
- widgets receive no raw `hass`, Home Assistant Adapter, Router, Config Service, Health Service, Design System object, Module Registry or Module Loader;
- r11 remains production/reference until controlled cutover;
- r11 behavior may be used as evidence, but its monolithic implementation and raw service calls are not ported;
- no monkey-patches, Prototype overrides, version-polish layers, duplicate implementations or permanent compatibility shims;
- OnePlus Pad 2 portrait remains the primary visual target;
- page scrolling remains a layout concern, not a House Quick concern;
- final Start lower-deck composition and generic page/widget orchestration remain Block 14.

## 3. Product decisions fixed by this design

### House Quick is status + navigation

Each visible item is a status button. The button shows a real aggregated state and, when a matching destination exists, navigates to the corresponding later detail/control page.

House Quick does not toggle lights, change heating values, start devices, activate scenes or call Home Assistant services directly.

### Included button families

Block 12 supports:

1. heating-zone buttons;
2. one normal-lighting button per widget instance;
3. one ambient-lighting button per widget instance;
4. one household-devices button per widget instance;
5. any number of energy buttons.

A widget instance may show any subset of those buttons in any order.

### Explicit source assignment only

Runtime behavior never guesses membership from entity names such as `ambient`, `plug`, `device`, room names or other naming heuristics.

Configuration UIs may later suggest likely entities, but only persisted explicit assignments are authoritative.

### Multi-instance behavior

Every `widget.house-quick` instance owns its own:

- visible button selection;
- button order;
- heating-zone subset;
- energy-button selection;
- energy averaging windows;
- energy warning/critical thresholds;
- navigation destinations.

The same provider object/source may be referenced by multiple widget instances.

## 4. Architecture

Block 12 uses four House providers plus one widget:

```text
provider.house-heating
  -> house.heatingZones

provider.house-lighting
  -> house.lights
  -> house.ambientLights

provider.house-devices
  -> house.devices

provider.house-energy
  -> house.energy

widget.house-quick
  <- consumes all five capabilities
  -> uses Action Registry only for navigation
```

The providers normalize Home Assistant / KNX-backed data into JamesUI-owned domain contracts. `widget.house-quick` only composes and presents those contracts.

This intentionally avoids one large `provider.house` monolith. Later detail pages can independently consume the same domain capabilities without depending on the Start widget.

## 5. Shared source-binding rule

Provider configuration uses explicit source bindings. A binding identifies a Home Assistant entity and, when necessary, one attribute or a boolean-state mapping.

Conceptually:

```text
binding:
  entity_id: required
  attribute: optional
  true_values: optional, only for boolean semantics
  false_values: optional, only for boolean semantics
```

The exact validated schema is finalized in the implementation plan, but these rules are binding:

- entity assignment is explicit;
- no name-based runtime classification;
- source values are normalized by providers, not widgets;
- `unknown`, `unavailable` or missing configured entities are never treated as valid current values;
- providers may keep a top-level capability available while marking only affected configured objects/sources unavailable;
- Home Assistant disconnect invalidates current provider output rather than silently retaining stale values as current.

## 6. Shared House Quick presentation status

All House Quick buttons resolve to exactly one presentation status:

```text
critical > warning > active > neutral
```

Meaning:

- `critical`: real fault/error or the configured critical energy threshold is reached;
- `warning`: real warning, configured source/device is unreachable, energy warning threshold is reached, or required averaging/history quality is insufficient;
- `active`: the represented normal function is currently active;
- `neutral`: normal inactive/idle state.

Important rules:

- unavailable/unreachable real sources are shown as `warning`, not as a quiet grey state;
- an available software/firmware update is information only and does not create `warning`;
- heating demand is information only and does not create `active`;
- severity always overrides activity: a running device with a fault is `critical`, not merely `active`.

Visual mapping uses the existing JamesUI design system:

- `neutral` -> normal surface;
- `active` -> normal JamesUI active/accent treatment;
- `warning` -> warning token treatment;
- `critical` -> error token treatment.

The widget does not invent hardcoded colors outside the Design System.

## 7. Heating capability

### Module contract

```text
id: provider.house-heating
type: provider
version: 1.0.0
core_api: 1.x
depends_on: []
requires_capabilities: []
provides_capabilities:
  - house.heatingZones
config_schema: provider.house-heating/v1
```

### KNX ownership

JamesUI does not build a heating zone by averaging individual rooms and does not derive the target temperature from room configuration.

The actual grouping and regulation semantics belong to KNX. For example, a logical `Wohnen` zone may represent Küche + Esszimmer + Wohnzimmer + Lounge, but Block 12 does not know or recalculate that room membership.

Home Assistant exposes the values required to represent the KNX zone; the provider normalizes them into one JamesUI zone object.

### Heating-zone object

Each configured zone has at least:

```text
id
name
current_temperature_c
target_temperature_c
heating_demand
auto_regulation_enabled
availability / reason
```

`id` is a stable JamesUI configuration ID and not a display label.

### Required displayed semantics

A zone button always attempts to show:

- zone name;
- current actual temperature;
- target temperature;
- whether a heating demand exists.

Conceptual example:

```text
Wohnen
21,4 °C · Soll 22,0 °C
Heizanforderung
```

or:

```text
Wohnen
21,4 °C · Soll 22,0 °C
Keine Heizanforderung
```

### Heating button status

The button's normal active appearance is controlled only by:

```text
auto_regulation_enabled === true
```

Heating demand does not control the active appearance.

If required configured heating-zone signals are unreachable, `warning` overrides `active`.

No heating fault model is introduced in Block 12 beyond source-unreachable warning semantics unless an explicitly configured provider signal is later added by a separately approved design change.

### Multiplicity

Any number of heating zones may exist, and any House Quick widget instance may show any subset of them.

Each zone is rendered as its own button.

## 8. Lighting capability

### Module contract

```text
id: provider.house-lighting
type: provider
version: 1.0.0
core_api: 1.x
depends_on: []
requires_capabilities: []
provides_capabilities:
  - house.lights
  - house.ambientLights
config_schema: provider.house-lighting/v1
```

### Explicit mutually exclusive groups

The provider config owns two explicit entity sets:

- normal lights;
- ambient lights.

A configured light entity may belong to exactly one of those two sets.

Configuration that places the same entity in both groups is rejected rather than double-counted.

### Normalized lighting item

Each item exposes enough normalized data for current and future consumers:

```text
id / entity_id
name
on
available
reason
```

### Aggregate contract

Each capability provides at least:

```text
items
total_count
on_count
unavailable_count
```

The denominator is the number of explicitly configured lights, including configured lights currently unreachable.

### Display

The primary House Quick text is natural-language count form:

```text
3 von 8 an
```

not `3/8 an`.

When relevant, unreachable sources may be surfaced as additional compact information without replacing the primary count.

### Button status

For both normal and ambient lighting:

- any unreachable configured source -> `warning`;
- otherwise `on_count > 0` -> `active`;
- otherwise -> `neutral`.

The two groups are visually and semantically distinct buttons even if they share the same base icon family.

## 9. Device capability

### Module contract

```text
id: provider.house-devices
type: provider
version: 1.0.0
core_api: 1.x
depends_on: []
requires_capabilities: []
provides_capabilities:
  - house.devices
config_schema: provider.house-devices/v1
```

### Purpose

Household appliances can expose very different Home Assistant entity models. The provider therefore normalizes explicitly configured source signals into one JamesUI device object rather than exposing device-specific raw entities to House Quick.

### Device object

A device object can represent:

```text
id
name
active
update_available
warning
fault
reachable
reason
```

Unsupported/unconfigured optional signals remain semantically absent rather than being treated as `false` data from an invented source.

Reachability is derived only from explicitly configured source bindings. No device is auto-added merely because Home Assistant discovers it.

### Aggregate contract

`house.devices` provides at least:

```text
items
active_count
update_count
warning_count
fault_count
unreachable_count
```

### Display

Examples:

```text
2 aktiv · 1 Update
```

or, when an actual issue exists:

```text
2 aktiv · 1 Störung
```

The implementation may use compact secondary rows/badges rather than forcing all counts into one line, but the semantics above remain visible and truthful.

### Button status

- `fault_count > 0` -> `critical`;
- else `warning_count > 0 || unreachable_count > 0` -> `warning`;
- else `active_count > 0` -> `active`;
- else -> `neutral`.

`update_count` never changes the color/severity by itself.

## 10. Energy capability

### Module contract

```text
id: provider.house-energy
type: provider
version: 1.0.0
core_api: 1.x
depends_on: []
requires_capabilities: []
provides_capabilities:
  - house.energy
config_schema: provider.house-energy/v1
```

### Explicit energy sources

The provider config contains any number of named power sources, for example:

- total house consumption;
- heat pump;
- wallbox;
- another explicitly selected sub-load.

Each source has a stable source ID and an explicit Home Assistant binding.

The provider normalizes supported source units to watts as the canonical internal value.

Unsupported/missing units or unusable values make that source unavailable rather than being guessed.

### Why `house.energy` is a query capability

Averaging window and thresholds belong to each energy button/widget instance. Therefore the provider must not depend on widget-instance configuration.

`house.energy` is a provider-owned query/subscription service, following the same architectural principle already used by range-based calendar data:

- provider owns Home Assistant current-state subscriptions and history/statistics access;
- consumer requests a configured source plus averaging window;
- provider returns current power and the average for that requested window;
- multiple consumers may request the same source with different windows;
- identical active requests may share provider-side work/cache;
- stale query services become invalid after provider update/rebind/destroy.

Conceptually:

```text
house.energy service:
  version
  configured_sources[]
  subscribe_windows(request, listener) -> unsubscribe

request item:
  source_id
  window_minutes

result item:
  source_id
  current_power_w
  average_power_w
  window_minutes
  quality
  reason
```

The implementation plan may refine function names, but the ownership boundary above is binding.

### Averaging semantics

The configured energy evaluation is based on an average over the requested trailing time window, not a single peak.

The provider uses Home Assistant recorder history/statistics through the Home Assistant Adapter so a useful average can exist immediately after JamesUI restart instead of waiting for a complete new live window.

Where raw/history state durations are used, the calculation must be time-weighted rather than a naive arithmetic average of irregularly sampled values.

If Home Assistant cannot provide sufficient history to evaluate the requested window reliably:

- current power may still be shown when valid;
- threshold evaluation is not guessed;
- the result quality indicates insufficient history;
- the House Quick button resolves to `warning` until a reliable average exists.

### Energy-button configuration

Thresholds are widget/button configuration, not provider configuration.

Each energy button defines at least:

```text
source_id
average_window_minutes
warning_threshold_w
critical_threshold_w
```

Rules:

- `critical_threshold_w` must be greater than `warning_threshold_w`;
- the averaging window must be a positive validated duration;
- configuration UI may display values as W or kW while persisted/canonical comparison uses watts.

### Energy display

Primary value is always current power, automatically formatted as W/kW as appropriate.

Example:

```text
Energie
1,84 kW
Ø 15 min: 2,10 kW
```

Showing the evaluated average as compact secondary information is required whenever thresholds are active so a yellow/red button remains explainable even when instantaneous power has already fallen.

### Energy button status

Given a valid average:

- `average_power_w >= critical_threshold_w` -> `critical`;
- else `average_power_w >= warning_threshold_w` -> `warning`;
- else -> `neutral`.

Energy does not use `active` merely because consumption is non-zero.

Source unavailability or unreliable history/average quality resolves to `warning`.

## 11. House Quick widget

### Module contract

```text
id: widget.house-quick
type: widget
version: 1.0.0
core_api: 1.x
depends_on: []
requires_capabilities:
  - house.heatingZones
  - house.lights
  - house.ambientLights
  - house.devices
  - house.energy
provides_capabilities: []
config_schema: widget.house-quick/v1
```

The widget may still render healthy configured button families if one sibling capability is unavailable. It must not become an all-or-nothing blank surface because one provider fails.

### Configured button list

The widget config owns an ordered `buttons` list. Array order is presentation order.

Conceptual entries:

```text
heating zone:
  id
  type: heating_zone
  source_id: <zone id>
  navigation

normal light:
  id
  type: lights
  navigation

ambient light:
  id
  type: ambient_lights
  navigation

devices:
  id
  type: devices
  navigation

energy:
  id
  type: energy
  source_id: <energy source id>
  average_window_minutes
  warning_threshold_w
  critical_threshold_w
  navigation
```

Within one widget instance:

- heating-zone entries may repeat for different zone IDs;
- energy entries may repeat for different source IDs or even the same source with intentionally different windows/thresholds if explicitly configured;
- normal lights are shown at most once;
- ambient lights are shown at most once;
- devices are shown at most once.

A second widget instance is completely independent and may reuse any of the same provider sources.

### Icons

Use the shared icon registry only. Existing defaults are sufficient for Block 12:

- heating -> `home.climate`;
- normal light -> `home.light`;
- ambient light -> `home.light` unless a later approved icon distinction is added;
- devices -> `home.device`;
- energy -> `home.energy`.

A configured icon override may reference another registered semantic icon ID, but no raw SVG/emoji/icon-font path is introduced.

## 12. Navigation contract

Every House Quick button may define one semantic navigation destination.

Conceptually:

```text
navigation:
  route: <JamesUI route id>
  target_id: optional semantic detail target
```

Examples:

```text
heating zone Wohnen -> climate route + target_id=zone:wohnen
lights              -> lighting route + target_id=lights
ambient lights      -> lighting route + target_id=ambient
household devices   -> devices route
energy house total  -> energy route + target_id=house_total
```

The whole button is the navigation affordance.

The widget dispatches navigation through the Action Registry. It never receives or calls the Router directly.

Block 12 must not invent placeholder detail pages merely to make these routes exist. If a destination is not yet part of the router, the Action Registry may reject the navigation without side effects. Later detail-page blocks make those semantic targets real.

`target_id` is part of the forward-compatible destination metadata. Current core navigation may ignore metadata it does not yet consume; Block 12 must not add hidden global selection state as a workaround.

## 13. Capability availability and partial failure

### Provider top-level state

For each provider:

- no configured sources -> relevant capability is `not_configured`;
- Home Assistant disconnected -> relevant capability is `unavailable`;
- provider runtime/config failure -> relevant capability is `unavailable`;
- otherwise capability may remain `available` while individual configured objects carry per-source availability/reason.

### Widget behavior

The widget independently resolves every configured button.

Examples:

- energy unavailable does not hide lighting;
- one unavailable light produces a lighting warning but still shows `x von y an` using known states;
- one broken household device produces warning/critical aggregate without hiding healthy devices;
- an unavailable heating signal marks that zone warning without breaking another zone.

No stale disconnected value is represented as current/healthy data.

## 14. Visual behavior

House Quick follows the existing Alpine-chic JamesUI visual language, but Block 12 does not finalize Start-page geometry.

Required presentation properties:

- each configured entry is clearly a tappable status button;
- status color treatment is secondary to readable text, not the only indication of meaning;
- labels and values remain readable on OnePlus Pad 2 portrait;
- buttons respect the host widget bounds;
- the widget may internally lay out/wrap its own buttons but must not control page scrolling;
- no headings such as legacy `ZUHAUSE` are required by this contract;
- no scene controls appear inside the widget;
- no r11 CSS is copied as an architecture dependency.

Final Start placement, exact grid widths and lower-deck geometry remain Block 14.

## 15. Out of scope

Block 12 explicitly does not implement:

- windows/door status buttons;
- ventilation status buttons;
- scene buttons or scene activation;
- direct light toggling;
- heating setpoint changes;
- opening/closing heating circuits;
- appliance control;
- energy-control actions;
- the full heating detail page;
- the full light/ambient-light detail page;
- the full device detail page;
- the full energy detail page;
- generic page-level arbitrary widget-instance orchestration;
- final Start lower-deck composition;
- production cutover;
- r11 deletion.

## 16. r11 behavior retained vs rejected

### Retained conceptually

- truthful aggregation of real Home Assistant state;
- compact high-level House status;
- status-first navigation toward later details;
- device activity/update/health as meaningful household information.

### Rejected from the new architecture

- monolithic `_houseSummary` ownership inside the legacy panel;
- runtime name heuristics for source membership;
- blanket inclusion of every `light.*`, `fan.*`, update sensor or battery sensor;
- window/door and ventilation buttons in House Quick;
- direct raw Home Assistant service execution from UI code;
- scenes mixed into the House status widget;
- hardcoded demo climate data;
- r11 render/CSS/prototype-wrapping patterns.

## 18. Implementation boundaries

The implementation plan must preserve the following sequence:

1. provider contracts/config validators and tests;
2. normalized House provider behavior and tests;
3. energy query/history service and tests;
4. House Quick config/model/status resolution and tests;
5. House Quick DOM/styles/navigation and tests;
6. integration/lifecycle/regression tests;
7. whole-branch review;
8. fresh unchanged-head validation before merge;
9. merge and main-CI verification;
10. update project status/roadmap/handover once at Block 12 completion.

No product code is implemented before the written spec and implementation plan are approved.

## 19. Acceptance criteria

Block 12 is complete only when:

- all four providers exist as clean JamesUI 1.0 modules;
- all five approved House capabilities are provided;
- House Quick consumes capabilities/actions only;
- normal and ambient lights are explicitly assigned and never double-counted;
- heating zones reflect KNX-defined zone semantics without JamesUI room aggregation;
- every heating zone displays actual temperature, target temperature and heating demand;
- heating activity color is based on auto regulation on/off, not heating demand;
- household-device status distinguishes activity, information-only updates, warnings, faults and unreachable sources;
- energy buttons support arbitrary configured sources, windows and warning/critical thresholds;
- energy threshold evaluation uses historical trailing-window averages and does not silently guess when history quality is insufficient;
- current energy power remains the primary displayed value and evaluated average is explainable;
- House Quick button status follows `critical > warning > active > neutral`;
- every widget instance owns independent button selection/order/configuration;
- button clicks use semantic navigation through the Action Registry only;
- windows/doors, ventilation and scenes are absent from House Quick;
- final Start composition remains untouched;
- tests and CI are green at the defined review/merge gates.
